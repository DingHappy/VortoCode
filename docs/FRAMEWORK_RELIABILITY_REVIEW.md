# 项目推进框架可靠性检查（2026-10-30）

本轮核对常驻助理、Codex 监管、开发目标提交/验收、单次硬预算与任务幂等入口。基线为合并 #664 后的 `5728869`。这是这些关键路径的代码检查与离线故障复现，不是全仓库安全审计，也不证明原生客户端、真实模型或常驻主机通过验收。

总体判断：已有的隔离执行、人工审批和证据分层应继续复用。下一步优先统一状态保存、任务认领与通知回执的失败处理；增加更多自动角色不能弥补这些断点。

## 本轮已修复

### P1：监管台账异常会退回空状态及默认设置

位置：`src/scheduling/codex_supervisor.py::_load/load_config/_save_progress`。

原来读取或 JSON 解析失败返回 `{}`。后续巡检会按首次快照保存，旧判断标记丢失；配置也会回到包含 `nudge=True` 的默认值。错误恢复因此可能重新开启原已关闭的判断、忘记已消耗的尝试。

修复后只把文件不存在视为首次运行，读取失败、非法 JSON 或已知关键字段结构损坏均明确报错并保留原文件。监管工具显示记录不可用，不声称修改成功。写入复用原 `write_json` 的临时文件、同步与原子替换。

### P1：跨执行者的监管认领不是原子操作

位置：`src/scheduling/codex_supervisor.py::supervise_once/_save_progress/save_config`。

原来两个执行者可同时读取未认领记录，再分别保存并判断同一轮。受控测试暂停首个执行者的认领保存，第二个执行者进入，修复前模型替身调用两次。

修复后同一运行端的巡视共用非阻塞跨进程锁，竞争者直接跳过，不排队重跑。配置与进展保存另用短事务锁；模型等待期间仍可关闭主动判断，完成时继续核对最新设置与授权。取消释放巡视锁，已保存的认领仍阻止同轮重跑；保存失败也不宣称判断成功。修复后相同测试只调用一次。

## 尚未修复，按建议顺序处理

### P1：开发目标保存失败仍可能提交执行

位置：`src/web/routers/goals.py::_start_goal`、`src/workflow/workbench/goals.py::GoalLedger.create/update_contract/set_verifier/record_evidence`。

这些路径存在忽略 `save()` 返回值的情况。离线注入 `GoalLedger.save=False` 后，`_start_goal` 仍调用一次任务替身的 `submit`，原目标文件仍是 draft。创建或验收也可能返回只存在于内存中的结果。相比之下，私人目标和任务运行器已有明确的保存失败检查，合同不一致。

建议将一次目标执行的认领、稳定任务身份和任务关联一起设计：保存失败不得开始执行；提交后关联保存失败应保留可核对的任务身份，不能简单重试再提交。复用原任务台账/幂等入口，不新增任务数据库。还需覆盖响应丢失、提交已完成但关联写入失败、恢复与重复请求，再统一目标修改/验收的保存失败语义。

### P1：监管动作通知未受理，草稿仍可能永远等不到主人

位置：`src/scheduling/codex_supervisor.py::_supervise_once` 末尾的 `drafts` 投递、`src/scheduling/codex_watch.py` 动作台账。

复现：首轮成功生成 proposed 动作，但确认卡通知返回 false；后续再巡检，动作仍 proposed，模型不重复调用，确认卡投递累计仍只有一次。因为 `drafts` 是本轮内存列表，后续只看到已有待批准动作，不再构造待投递通知。动作可在查询入口找回，但主动推进链路停住；现有“留待下轮巡检”的日志不代表实际会补发。

建议在原动作上保存通知状态，后续只补送同一个动作，不再次判断或起草；补发前复核轮次、交接和动作状态，过期/撤回不补。渠道超时与明确未受理分开记录，次数及时间窗口有界。通知受理不等于用户批准，更不等于动作执行成功。

### P2：预算仍以入口/轮次为界，无法限制整个目标的反复推进

位置：`src/scheduling/codex_supervisor.py`、`src/scheduling/dispatch_review.py`、`src/agents/bounded_check.py`、`src/llm/hard_budget.py`。

目前监管有每轮数量和等待时间限制，任务重试链有三次上限，单次只读检查有严格适配器预算；这些合同不是同一个目标的累计预算。单次硬预算模块尚未接入上述监管/复盘入口。新建任务或新的 Codex 轮次仍会开始新的额度，不能宣称已经解决跨轮次的无限推进。

建议先为明确交接的一项工作绑定稳定身份和持久尝试记录，分别约束模型判断次数、执行次数、等待时长与未知费用预留。沿原状态机传递身份，达到上限转人工；不让模型自己刷新额度。未经可信适配器支持，不把估计 token 数当作账单硬上限。
