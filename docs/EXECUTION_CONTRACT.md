# 可扩展执行合同 v1

目标：让助理用稳定的数据合同理解不同执行核心，同时保留各核心的会话、工具与审批。当前先统一只读执行快照，不增加任务数据库、执行池、调度器或自动插件加载器。

实现入口：`src/agents/backends/execution.py`。现有 MainAgent、外部 CLI 包装器、ACP 与 Codex 会话适配器均提供 `execution_report`，遵守结构化的 `ExecutionReporter` 协议；无需继承同一个核心基类。

## 1. 分清三个层次

| 层次 | 职责 | 权威来源 |
| --- | --- | --- |
| 业务事项 | 目标、任务、验收与后续决策 | 现有 workflow / scheduling 台账 |
| 执行观测 | 某次执行的身份、状态、进展、结果和错误 | 实际核心的适配器 |
| 原生执行 | 模型循环、工具、登录、进程和审批 | 自有 Agent 或外部核心 |

执行快照是源数据的投影，不负责认领任务、扩大权限或宣布 Goal 达成。`ToolRuntime` 管自有工具执行；本合同不会把外部核心的工具全部替换成 VortoOne 工具。

## 2. 执行身份

`ExecutionRef` 字段：

| 字段 | 含义 |
| --- | --- |
| backend_id | 适配的核心名称，开放字符串，未来增加厂商不修改中心枚举 |
| instance_id | 宿主确定的执行实例，区分相同核心的不同主机/连接/运行实例 |
| run_id | 一次执行尝试的身份；重试应生成新尝试，不能拿同一编号冒充新执行 |
| task_id | 可选的原业务任务关联，继续由原任务台账管理 |
| session_id / turn_id | 可选的原生会话/轮次标识，保持不透明，不从正文猜测 |
| scope | process 或 runtime，明确身份的有效范围 |

默认身份为进程范围，重启后变化。它可以隔离同一进程中的报告，但不能用于持久恢复。需要跨重启关联时，由可信宿主传入现有 runtime 身份，并关联原台账；本模块不创建身份数据库。

MainAgent.run_turn 与 run_worker 接受可选 execution_ref。外部 CLI 只启动新会话，因此传入的引用不能伪造已有原生 session/turn。CodexBackend 接受宿主 instance_id，原生轮次来自实际 RPC 回执。

身份是关联信息，不是授权令牌。不能依据解码后的 backend_id 自动加载模块、选择任意主机或继承权限。

## 3. 快照与状态

`ExecutionSnapshot` 包含 schema_version、ref、state、observed_at、native_state、progress、result、error、features。

- state：queued / running / waiting_user / finished / failed / cancelled / unknown。
- observed_at：适配器确认本条观察时的 Unix 秒数；不能单靠不同主机的墙钟判断事件先后。
- native_state：保留原生状态，便于解释无法映射的新状态。
- progress：简短进展及可选步骤计数。没有权威步骤数据时不伪造百分比。
- result：执行产出摘要、证据引用和已报告的用量；出现结果不自动表示验收通过。
- error：稳定错误码、说明、重试提示及副作用是否可能已发生。
- features：如 execution.observe、control.steer、result.text。名称可扩展，只说明适配能力，不等于当前可用、已登录或已获批准。

请求受理仍由 `ControlReceipt` 表达，不并入 finished。停止回执不代表已经停止；新轮次回执不代表工作完成。

## 4. 现有来源如何接入

### 自有 MainAgent

每次 run_turn 创建新的执行身份，工具事件更新进展，原有文本返回值保留。返回最终文本时记为 finished；没有可核对的文本时保守记 unknown；异常和取消保持原异常控制流。持久暂停信号 ToolTurnYield 映射 waiting_user。

报告在原回合清理处收尾，不用新任务池管理执行。最终文本包括“完成了”也不生成验收证据。

### 外部 CLI

WorkerRun 保留原字段及 ok 语义，新增 execution_report 投影和可选 on_snapshot 观察回调。回调失败不改变实际执行结果。

CLI 进程退出与 Agent 回合完成分开：包装器检查结构化提问前不宣布 finished；需要用户信息时为 waiting_user，缺少提问通道时为 failed，提问是否形成持久暂停无法确认时为 unknown。取消时只有观察到进程终态才报 cancelled，否则保持 unknown。

已有“执行者不可用后由内置 Agent 接手”的策略不变；last_run 保留失败的 CLI 尝试，而包装器 execution_report 指向实际接手者。旧执行者的失败不能作为新执行者的结果。

### ACP 一次性会话与原专员任务

AcpSession 保留 AcpResult 和原权限、文件、时限及一次同会话 followup 规则，新增 execution_ref / on_snapshot 与只读 execution_report。会话标识来自实际握手；其它会话的更新不进入结果。启动、工具进展到最终状态都有快照，终态在清理进程之后发布；清理回执不明为 unknown，取消异常照常向上传递。end_turn 且有文字只代表执行结束，空结果或未知停止原因保持 unknown，不补造证据和用量。观察回调失败记异常类型，不改变协议或权限。

`workflow/staff/executions.py` 将 native 专员与固定项目开发专员的报告绑定原任务的 collaboration.execution：含原轮次、进程实例、尝试及快照，沿用原事务写入。更换尝试、轮次、实例、已知原生会话身份，或终态之后的回调均不能覆盖当前报告；较旧时间和重复快照不落盘。这是同一宿主内的回调约束，不替代跨进程有序上报合同。

已有 staff_directory / GET /api/staff / staff_list 在 recent_tasks 中返回可空的 execution 只读投影。无字段、坏记录或不支持版本可读并返回 null；旧实例、旧轮次或已停任务的活动报告降为 unknown，并说明 stale 原因。摘要有界并脱敏，不复制完整交付正文；任务状态、验收、审批、用量记账和重启核对仍由原服务管理，报告不参与恢复或自动重跑。旧团队开发路径及外部 CLI 的任务贯通留待后续。

staff_list 返回执行报告时，可信宿主用现有 SourcedToolText 标记整份结果为不可信来源，沿用原运行层的污点传播与历史出处机制；执行器文字不能通过目录查询洗成可信指令。没有执行报告的普通目录查询保持原来源属性，不在执行报告中授予或压制污点。三端行为合同覆盖这两种情况。

Desktop 专员名录使用本地请求开始时间 `checkedAt`，沿用共用读取有效期 `SOURCE_FRESH_MS`（两分钟）。到期只触发一次本地重绘，窗口重新聚焦或恢复可见时也复核时效；不自动轮询、执行或重试任务。过期、时间缺失/无效/回退、读取失败时保留旧资料，执行观察显示 unknown，主人需显式刷新后才能继续页面操作。慢响应不在到达时续期；写入前的名录复核同样不能超出读取窗口。成功读取才更新核对时间，失败不刷新旧时间；切换连接或关闭页面会取消旧计时和回调。原服务的任务状态、摘要/nonce/轮次/实例核对及审批卡有效期继续独立生效。

### Codex 已有会话

read_state 提供原 phase 与共同快照，控制器核对两者是否一致，以及核心/实例/会话/轮次是否匹配。原生等待批准或回答映射 waiting_user，仍走 Codex 原生审批。控制回执携带对应执行引用，但不改变已观察到的运行状态。

Codex 观察员也在现有精简 thread 报告内携带 `execution`，与控制适配器共用原生状态映射；列举时核对加载会话身份并显式读取最新轮次。观察员的 instance_id 标识当前观察进程，不承诺 Codex 服务跨重启恢复。心跳更新时间不进入变化摘要，生产者身份或轮次变化仍会触发上报。

常驻助理在接收及现有 `GET /api/codex/status` 读取时核对 schema、核心/会话/轮次及新旧状态是否一致，只投影有界的观测字段；丢弃报告携带的制品证据、结果、错误和额外能力声明。身份只用于关联，不据此执行操作。原错误和回复继续通过既有精简字段展示。

- 缺少 `execution` 字段：旧版观察员，今日工作保持旧字段兼容。
- `execution: null`：无轮次、版本不支持、状态矛盾或身份无效，今日工作保留 unknown；不回退成旧字段的 running。
- 有效共同快照：今日工作核对会话/轮次与报告时效后读取；finished 仍只进入待验收，不进入已核实完成。

旧版常驻服务会忽略新增执行字段；新版服务在尚未接受有序上报前继续接受旧版观察员。有序上报启用后拒绝旧格式覆盖，升级规则见 [观测顺序与重传](OBSERVATION_ORDER.md)。Python 和 TypeScript 共用 `tests/fixtures/execution_observation_v1.json` 验证执行协议兼容。此兼容规则只覆盖这条观测链路，不声明其他前端接口已迁移。

状态读取与提醒隔离：

- 控制适配器开始新读取时清空旧报告；失败或取消后不保留旧成功。并发读取各自返回其结果，只有最后发起的读取可以更新适配器公开报告，迟到的旧读取不能覆盖新来源。
- 状态 API 的摘要、明细和接收时间来自一次加载，不在响应中混用两份报告。无时区、非法或未来的接收时间不作为当前状态依据。
- 等待提醒绑定主机、观察实例、会话、轮次和等待类型；更换来源或轮次、等待类型变化，以及超过 30 分钟未收到报告后重新计时。旧提醒标记不压制新轮次提醒。旧版提醒记录缺少作用域时，从下一份有效报告开始重新计时。
- 新版快照失效或不可确认时，查询摘要与巡视保留待核对，不依据旧字段消耗模型预算或拟继续/叫停建议。模型审阅期间来源实例变化，即使轮次号和正文相同，也丢弃旧结论。

观察员已通过前序游标、代次和序号核对整份快照的替换，超时重传保留原请求，接收端重复确认不刷新状态。明确的新观察循环可以读取当前游标后接替，旧循环不自动抢回。完整事件回放/补收仍待接入；同一轮内未携带原生请求 ID 的多次批准也不能仅凭等待旗标区分为不同问题。

## 5. 结果、证据与费用

- ExecutionResult 只保存摘要，不从正文提取“验收通过”。
- ExecutionEvidence 明确证据 ID、执行引用、类型、结论、时间以及目标 revision / verified_revision。
- 快照拒绝另一执行的证据；matches_revision 只核对身份、提交与通过标记，不证明证据真实性，也不替代业务标准或用户验收。
- 当前来源不会仅因文本、进程退出码或轮次结束而自动生成验收证据。既有目标与提交验证仍走原有权威判定，尚未全部迁移到本合同。
- 用量和费用未知时使用 null。明确报告的 0 可以保留；非法值、布尔值或不可表示的报告保持未知，不能补成零。
- 计数使用非负 JSON 安全整数；时间与费用必须为有限非负数。

## 6. 版本与扩展规则

共同快照上的失败恢复决策见[执行恢复合同](EXECUTION_RECOVERY.md)。只有可信、身份匹配且确认未开始的失败才可能允许备用接手；possible/unknown 不通过自动重跑消除。当前已接入实验性 CLI 与开发/审查编排，不改变已有会话控制的禁止自动 fallback 规则。

1. 当前 schema_version=1。新增可选字段可继续使用 v1，旧读者忽略未知字段；不要修改既有字段含义。
2. 未识别状态降为 unknown，保留 native_state；不能把未知状态映射为空闲或成功。
3. 不兼容变更使用新的主版本。不支持的版本明确拒绝，不静默降级。
4. 新核心和 feature 使用开放名称，避免中心枚举不断增长。私有能力可用 vendor 前缀。
5. 必需身份、已知字段类型和证据归属严格检查。数据解码不授予任何执行权限。
6. 不把“符合快照合同”等同于支持全部控制方法。一次性执行者和常驻会话继续使用各自生命周期接口。

## 7. 新核心的接入步骤

1. 给出实际使用场景，确定一次性执行、已有会话控制或两者中的哪一种。
2. 在显式配置下绑定原生客户端；声明实际能力及身份范围，保留其权限/审批和凭据边界。
3. 把原生状态与产出转换为 ExecutionSnapshot，提供只读 execution_report。
4. 需要会话控制时实现 SessionControlBackend；不支持的操作不暴露、不模拟，不从报告 features 推断授权。
5. 跑合同测试：版本、未知状态、来源/轮次错配、取消、请求不明、提问、结果与证据归属、用量缺失。
6. 单独记录真实版本、真实执行及断线恢复验收。离线假核心测试不能代替这些证据。

增加核心优先修改适配器及其测试；仅新增协议确有共性的字段，不在业务界面遍布厂商分支。不根据远端字段自动安装、下载或导入执行插件。

第 3 步：`agents/backends/entry.py` 提供 OneShotRequest / ExecutionBinding / execute_once。宿主显式传入可信函数与能力集合；入口核对 backend、所需能力和有限时限，并调用原宿主 check 复核当前授权。只调用一次，返回值和异常原样传回；不重试、接手、认领任务或根据远端名称加载程序。已有 session/turn 引用不能冒充一次性新执行，也不通过重跑模拟恢复。

首批绑定为 `team_engines.run_developer`，固定 OpenCode 开发岗位、原模型和一次性目录，仍调用原 run_external / AcpSession；原环境隔离、权限逐次复核、一次同会话 followup、时限与进程清理不变。固定项目专员从原 execute_development 注入此绑定；旧团队开发保留原入口。

第 4 步：`ExternalWorkerAgent.run_turn` 用显式绑定把 Codex / Claude CLI 转交 `execute_once`，仍由原 `run_worker` 管理进程、协议解析、时限和清理。绑定固定执行者、目录、system 与本次读写模式；预期执行引用原样传入，没有引用时新建进程级尝试，不能携带已有 session/turn。调用前后复核原无人值守拒绝规则。实验开关仍默认关闭，提问、污点、用量和可信环境过滤保持；失败后的接手仅由原恢复合同决定，入口不增加重试。`last_run` 保留 CLI 尝试，实际接手者的报告仍来自原包装器。已有 Codex 会话控制随后单独迁移，不能用新 CLI 进程冒充原会话恢复。

第 5 步：同一 `entry.py` 提供不可变 SessionRequest 与 `control_existing`，显式来源须匹配宿主提供的会话适配器。原观察员的已批准动作实际使用此入口，再交回 `control_session` 重新读取原生状态、核对实例/轮次、能力和受理回执；这些检查仍只有原控制器一份。消息的自动建议/主人明确指令范围保持，停止始终绑定原轮次。此方法不经过 OneShotRequest，不启动 CLI、不复制上下文、不自动重发。写入后的回执不明仍向原动作记录为 unknown，取消仍向上传播；真实会话和安装版本验收另算。

第 6 步：Desktop `executionObservation` 同时解码今日 Codex 与专员最近任务的 v1 报告。任务报告另核对原服务 round/stale 包装和 task_id，缺失/错绑/坏版本保持不可用，stale 报告和断线显示 unknown；不从报告推断任务成功、批准或主人验收。来源、UTC 时间、进度和执行身份按需展开，外部文字转义，不显示能力开关。Codex 原生及旧格式解释留在 `codexExecution` 来源适配，产品投影只读共同状态；显式坏报告不回退旧字段。没有新 API、第二套报告存储或自动执行行为，iPhone 尚无这些报告的读取界面。
