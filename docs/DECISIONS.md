# 关键技术决策(ADR)

记录"为什么这么选",方便后续回顾和挑战。

> ADR-001～007 是项目早期阶段的决策（当时的定位是从零生成新项目的多角色流水线），多数已被后续实现取代，保留作历史，不作为当前设计依据。当前方向从 ADR-008 起。

## ADR-001:不基于 OpenHands 整体集成,只借鉴其 Sandbox 思路

**选项**:
- A. 直接 fork OpenHands 改造
- B. 引入 OpenHands 作为 sublib
- **C. 自写 Sandbox 层,借鉴其工具协议设计** ✅

**决定**:C

**理由**:
- OpenHands 设计是"单 agent + 重工具",我们要"多 agent + 轻协调",架构不匹配
- 整体集成会引入大量与我们流程冲突的状态管理
- Sandbox/工具协议这一层是它最有价值的部分,可以参考实现
- 自写更可控,LLM 调用走自己的网关也更顺

**代价**:重复造一部分轮子(约 2 周工作量)

## ADR-002:工作流引擎自写,不用 LangGraph / Temporal

**选项**:
- A. LangGraph(Agent 工作流主流方案)
- B. Temporal(企业级)
- **C. 自写状态机 + Postgres 持久化** ✅

**决定**:C(第一版),Phase 2 后视情况迁移到 LangGraph

**理由**:
- LangGraph 抽象偏 Agent 聊天,对"严格状态机 + 人工介入"支持不够直接
- Temporal 重,小团队不值得
- 自写一个基于 Postgres 的简单 FSM 几百行代码,完全够 MVP

**风险**:并发/分布式扩展时可能要重写

## ADR-003:LLM 调用统一走自建 One API 网关

**决定**:所有 Agent 通过 `OPENAI_API_BASE` 指向自己的 One API 实例

**理由**:
- 成本可见(按 agent 维度 tag)
- 模型路由灵活(开发用 Sonnet,审核切 Opus)
- Prompt 缓存复用
- 与已有 [[ai-token-relay-direction]] 项目协同

**注意**:One API 网关本身要先稳定,这是 hard dependency

## ADR-004:第一版只做"从零生成新项目",不做"修改已有项目"

**理由**:
- 已有项目要做代码索引、依赖分析、影响范围分析,复杂度高一个量级
- MVP 阶段先证明"端到端能跑通",再扩展
- Phase 2 再加增量开发能力

**反对意见**:从零生成是 toy 场景,真实价值在改已有项目
**回应**:认可,但先把流程跑通再加难度

## ADR-005:Agent 之间通过结构化产物通信,不传聊天历史

**决定**:Agent 输出严格 schema(Pydantic),不允许自由对话

**理由**:
- 聊天历史会越滚越长,上下文爆炸
- 结构化产物可以被工作流引擎理解 / 校验 / 回放
- 跨 Agent 错误更容易定位

**代价**:灵活性降低,某些复杂协作需要绕路

## ADR-008：冻结任务协作的高级功能，保留隔离开发流水线核心（2026-10-22）

**背景**：
- Code 侧（任务协作台账、工作台、隔离开发流水线及 Desktop 对应面板）超过 1.5 万行，约占后端四成。
- 实际使用：常驻电脑上两个月只跑过 1 次开发计划；助理派活两周 1 张任务单。写代码已交给 Mac 上的 Codex，VortoOne 每天真在用的是常驻助理与 Codex 监管。
- 2026-10-22 用 `python -m evals` 跑 10 个固定场景（mimo-v2.5-pro，HEAD a8ed403）：落地、诚实、干净都是 100%，共 6 分 22 秒、约 45 万 token。流水线质量没问题，问题是没人用。

**选项**：
- A. 维持现状，继续按任务协作 PRD 往下做
- **B. 保留流水线核心，冻结任务协作的高级功能** ✅
- C. 连流水线一起收缩

**决定**：B

- **保留并照常维护**：隔离开发流水线（`dev_auto` / `dev_isolated` / `dev_resume`、worktree、验证、落 `vorto/*` 分支）、助理派活（`assistant_dispatch`、`dispatch_stats`、`attention`、`decisions`）、后台任务台账基础（`tasks`、`handoffs`、`followups`、`dev_graph`）。
- **冻结**：任务协作的高级扩展——覆盖记录扫描、归档与退役（`task_scan`）、反向发现与依赖接力（`task_dependents`、`task_dependencies`）、任务链执行额度（`task_chain_budget`）、自动检查授权与报告（`continuations`、`continuation_checks`、`check_reports`）、模型证据与对比（`model_evidence`、`model_comparison`）、跨 runtime 收件箱与看板投影（`runtime_inbox`、`dashboard`）。
- 冻结的含义：**不加新功能**；安全问题和明确的 bug 照修；内核重构需要时可以跟着改接口。暂不删除，等确认没有依赖、也确实没用后再单独提删除。

**理由**：维护成本花在没人用的地方，挤占了每天在用的助理和 Codex 监管。流水线核心质量好、体量小，又是派活的执行引擎，留着成本低。

**重新评估的条件**：派活或 Desktop Code 模式的真实使用明显增加（例如一周超过 5 张任务单），或用户明确要做团队协作。

## ADR-009：手机端定为只读伴侣，写入能力等 P1 稳定后再议（2026-10-26）

**背景**：
- #595 合入了约 2 万行手机端代码：同仓库浏览器只读入口、共享 TypeScript 通信包（`packages/mobile-client`）、SwiftUI iOS 客户端、独立的非执行手机网关（`src/web/mobile_server.py`），以及 HTTPS、DDNS、证书续期部署模板，另有一个交互原型（`prototypes/mobile-assistant`）。
- 这些代码合入前，路线图和决策记录里都没有手机端。项目说明写的对外入口只有 Desktop、无头 CLI 和钉钉派活。
- 手机端需要公网入口，攻击面因此扩大。原型目录合入当天就引来 3 个依赖升级 PR。
- 当前路线（`CURRENT_ARCHITECTURE.md`）：P0 让今日工作可信，P1 让常驻助理与 Codex 的真实链路稳定。

**选项**：
- A. 手机端作为完整客户端继续扩展（聊天写入、审批、推送、远程接管）
- **B. 手机端定为只读伴侣，写入能力等 P1 稳定后再议** ✅
- C. 撤出手机端，回到 Desktop + CLI + 钉钉

**决定**：B

- **范围**：在手机上看常驻助理已有的资料，即今天的事项、目标、进展，以及需要我决定的事。这是 P0「今日工作」和「找到用户」在手机上的延伸，不另起一套目标或任务数据。
- **暂不做**：聊天写入、审批与确认、推送、手机远程接管、跨主机助手目录。要做其中任何一项，先在这里补一条决策。
- **安全边界不放宽**：
  - 公网只暴露非执行的手机网关和精确路由白名单；
  - 手机凭据不升级为管理员身份；
  - 新增手机路由默认需要管理员令牌，要豁免必须登记进 `src/web/auth.py` 的 `MOBILE_SELF_AUTHENTICATED`（由 `tests/unit/test_mobile_auth_exemptions.py` 钉住）。
- **原型不是产品代码**：`prototypes/` 只作设计参考，不随产品维护，不合并它的依赖升级。设计定稿后单独提删除。

**理由**：只读伴侣直接服务现有的四个问题，成本可控。写入和审批会把手机变成第二个执行入口，在常驻链路还没真机验收之前加进来，会把排查面扩大一倍。

**重新评估的条件**：P1 的常驻助理和 Codex 链路完成真机验收，并且手机入口有持续的真实使用（例如连续两周每周有 3 天以上打开）。


### ADR-009 修订：手机端改为主人终端之一，写入按阶段开放（2026-11-01，随 ADR-011）

- **定位**：手机 App 从只读伴侣改为主人终端之一（与 Desktop、桌面设备并列，见 ADR-011）。先只做 iOS。
- **开放写入的前提**：P1 场景 F、G 通过；手机经 WireGuard 直连常驻主机；设备密钥签名、批准签动作摘要、`owner_device` 能力档案已落地并有契约测试。前提未满足时维持只读。
- **范围（MVP）**：今日、等你决定（批准 / 拒绝）、随手记、撤销、推送。自由对话放在 MVP 稳定之后。手机不出现 Desktop 没有的写入能力。
- **安全边界**：~~新增的写入路由只经 WireGuard 可达，不开放公网 HTTP 端口~~（已由下方「ADR-011 修订」改为走公网 HTTPS 入口 + 新手机钥匙需主人批准）；手机凭据不升级为管理员身份；新增手机路由继续登记 `MOBILE_SELF_AUTHENTICATED` 并由测试钉住。现有只读网关是否继续经公网暴露，另行评估。
- 原决定中的「暂不做」清单由本修订取代；「原型不是产品代码」一条继续有效。

### ADR-011 修订：手机写入走现有公网 HTTPS 入口，新手机钥匙需主人批准（2026-11-01）

**背景**：常驻主机已有公网 HTTPS 手机入口（独立 Caddy，只放行列出的路径，证书走 DNS 验证）。iPhone 已能经它登录，而 WireGuard 还要在 NAS 上给手机单独开通。原定「写入路由只经 WireGuard 可达」意在让账号密码之外再多一道门。

**决定**：手机写入路由加进现有公网入口的放行名单，不要求 WireGuard。用钥匙信任补上「只剩账号密码一道门」的缺口：

- 信任挂在钥匙上，不挂在设备记录上。第一台手机首次使用即信任；名单一旦建立（即使之后被移空），新的钥匙对都停在「待确认」，主人在 Desktop 助理面板对过手机上显示的核对码才批准生效。同一台手机重新登录用的是同一对钥匙，不用再批。
- 有手机申请或获得写入权限时，常驻助理各推一次通知；Desktop 可以移除已信任的手机，移除后这对钥匙立刻签不过任何写入。
- 其余不变：每个写请求要设备签名和一次性 nonce；批准只认需要 Face ID 的批准钥匙并核对动作摘要；手机凭据不升级为管理员身份；入口其余路径照旧 404。

**理由**：偷到账号密码的人能登录，但拿不到写入能力，除非主人在 Desktop 上批准。这与「WireGuard 密钥 + 账号」的强度相当，又不需要为每台手机配置 VPN。

**代价与重新评估**：写入路由暴露在公网上，攻击面比只在 WireGuard 里大（解析缺陷、拒绝服务）。如果出现可疑的钥匙申请，或需要开放比个人数据更高风险的写入（`IRREVERSIBLE`、对外发送），回到 WireGuard。

## ADR-010：Codex 默认只看，逐个会话交接后助理才插手（2026-10-28）

**背景**：
- Mac 上的观察员把所有打开的 Codex 会话都报给常驻助理，监管对其中任何一个做完一轮的会话都会判断下一步、拟话，卡住时拟叫停。
- 这些会话大多是主人自己正在驾驶的活。P1 验收时屏幕上同时开着 9 个会话，其中只有 1 个是测试用的。
- 助理按会话名找目标，同名时取第一个。验收中出现了两个同名的「编写 add 函数」，一个在测试目录，一个在主人的工作仓库，助理拟的话可能落进工作仓库那个。

**选项**：
- A. 维持现状：所有会话都可以拟话和叫停，靠每条都要人批准兜底
- **B. 默认只看，主人逐个会话交接后才插手；主人在驾驶时不插话** ✅
- C. 只看不插手，取消拟话和叫停

**决定**：B

- **只看**：所有会话照常汇报进度，失败、卡住、在等批准都照常提醒。
- **插手要交接**：拟话、补充要求、叫停只对交接过的会话。交接按会话进行，不是全局开关；交接要过确认门，收回直接生效；会话关闭或监管判断已经做完，就自动收回。
- **按 id 定位**：拟动作要落到唯一的会话 id（或进度里的 id 尾号）；名字有歧义时拒绝，不猜。批准卡片和通知写明目录。
- **驾驶时不插话**：交接之后，如果最新一轮是主人自己在 Codex 里发起的（不是助理发出的话），这一轮不判断下一步、不拟话。

**理由**：Codex 是主人自己的工具，VortoOne 是在旁边帮着看的助理。逐条批准只能挡住「发什么」，挡不住「发给谁」：同名、多会话时，人在手机上很难分辨。只读汇报出错的代价低，插手出错会污染主人正在干的活，所以默认值要放在只读一侧。

**不改的部分**：隔离开发流水线把 Codex CLI 当执行者（每次一个独立 worktree），不受这条约束。

## ADR-011：个人 Agent 做底座，其它能力以插件接入；主人终端与团队通道分开（2026-11-01）

**背景**：
- 真实使用（见 ADR-008）：开发计划和派活用得少，每天在用的是常驻助理和 Codex 监管。开发能力是一种能力，不是产品本身。
- 功能焊在一起：`scheduling/` 下有四个 Codex / 助理巡视模块；「主人在不在电脑前」的判断只存在于 Codex 模块里，别的来源用不上；数据源、执行者、渠道三种接口各自独立（`src/plugins/`、`agents/backends/control.py`、`im/channel.py`），新增一种能力要改 gateway、scheduling 和前端好几处。
- IM 入口整体按不可信处理（`taint.py` 的 `channel` 来源），主人在 IM 里记一件事也要确认；同一个 IM 既当主人的遥控器，又是将来给别人发通知的通道。
- P1 场景 A～E 已真机通过。

**选项**：
- A. 维持现状，按入口和功能继续叠加
- **B. 个人 Agent 做底座；其余能力以插件接入；主人终端与团队通道分开** ✅
- C. 改用现成的个人 Agent 框架，把本仓库的安全内核移植过去

**决定**：B

- **底座**：身份与信任、事项台账（个人目标的扩展，唯一一本）、个人模型（记忆）、动作与自主度、主动循环（调度、早晚报、打扰预算）、投递路由、Agent 运行时。底座不出现具体业务。
- **插件**：数据源、工具、执行者（沿用 `SessionControlBackend` 与执行快照合同）。第一批 SDK 只从现有代码里抽数据源和工具两种能力（日历、邮件、Notion、运维四个真实用例）；执行者只做登记；渠道能力等团队通知立项时再定。隔离开发流水线作为插件登记，不搬代码。第三方能力只走 MCP。
- **主人终端**：App（iOS 先行）、Desktop、桌面设备（语音音箱一类）。终端是底座的客户端，不是插件；插件不能新增终端，也不能直接往终端推送。桌面设备不能批准任何外发或不可逆动作，语音输入只产生提议。
- **团队通道**：钉钉 / Telegram 远期只用于通知团队成员，每次发送都是外发、需要确认；对方的回复按外部内容处理。**近期维持现状**：IM 里的对话、派活、审批冻结，只修 bug；主人的通知在 App 推送稳定前继续走 IM，双发对照后再切换。
- **授权（`decide()` 不改）**：扩展 `trust.py` 的操作类别，不另起一个维度——`OWN_DATA`（属于主人、可撤销的本地数据：事项、提醒、记忆提议）、`DRAFT`（只产生草稿）、`IRREVERSIBLE`（删除、付款、合并主分支；与 `INTERACT` 一样任何档位都不免）。FULL 档对 `DELIVER` 保持现状，只在 Desktop 本机 `local` 会话里可免；新增 `owner_device` 能力档案，上限为 `OWN_DATA` + `DRAFT`；`unattended` 不变。
- **必须与功能同时落地的防线**：
  1. 台账字段记录出处（主人亲手输入 / 外部来源）；读到外部出处的字段照常标污点；污点回合里的 `OWN_DATA` 动作只生成提议卡，不执行。
  2. ~~手机经 WireGuard 直连常驻主机，不开放公网 HTTP 端口~~（见「ADR-011 修订」：走公网 HTTPS 入口，新手机钥匙需主人批准）；手机会话使用 `owner_device` 档案，没有命令执行、桌面控制和任意文件写入。
  3. 批准签的是动作摘要（对象 + 正文哈希 + 原轮次），服务端核对一致才执行；多个终端重复批准时先到先得。
  4. App 端死人开关：主机长时间没有回应时由手机本地提醒；需要立即处理的通知在一个终端未确认时逐级换到下一个终端。
  5. `OWN_DATA` 工具必须登记撤销；撤销 = 状态回退 + 列出已经发生、撤不回的下游影响。
- **落地顺序**（每阶段稳定两周再开下一阶段）：0 P1 场景 F、G，本 ADR，清理 → 1 `trust.py` 类别、操作日志与撤销、台账出处，先在 Desktop 上让个人事项免确认 → 2 iOS App MVP → 3 投递路由与最小 SDK。桌面设备、信号日志与归并、团队通知放在之后。

**理由**：
- 底座定在「个人」，与实际使用一致；新增能力从改多处变成写一个插件。
- 主人终端用设备密钥和生物识别认主人，比按 IM 账号认人更强；确认只需点一下之后，不需要为了省事放宽规则。
- 安全判定处不变，扩展的是输入（操作类别、能力档案），继续由内核一处决定问不问。

**不改的部分**：`decide()` 判定；污点回合一切预授权失效；无人值守 fail-closed 且不给出网工具；ADR-008 的冻结范围；ADR-010 的交接规则。

**需要随实现更新的契约**：`tests/unit/test_three_end_contract.py` 的能力矩阵（新增 `owner_device`）；`tests/unit/test_layering.py`（插件只经 SDK 导入）。

### ADR-011 修订：对外发送每次由主人确认（2026-11-10，#825）

主人已确认：对外发送（`DELIVER`）在任何授权档位都要逐次确认，FULL 和 `--yes` 均不能代替主人批准。
本修订替代上文「FULL 档对 DELIVER 保持现状」及 ADR-012 中对外发送可设「总是允许」的规则。

- 无头 `vc agent --yes`、`vc agent --attach --yes` 和 `vc pipeline advance --yes` 问不到人时，不再能开 PR、推送、发布制品或发送文件；本地实现和落分支仍可按原允许类别执行。
- 制品首次发布及每次更新都属于外发；之前批准过同一制品，不构成下一次更新的授权。
- 交互入口由主人逐次确认。attach 的类别来自现有协议字段；缺失或未知时不自动放行，需人工核对。
- 不可逆、交互和污点规则保持原有约束；仍由确认门统一决定放行、询问或拒绝。

## ADR-012：主人终端向 Muse 一类的个人 Agent 应用靠拢，Desktop 与 App 同构（2026-11-02）

**背景**：ADR-011 定了「个人 Agent 底座 + 主人终端」，但 App 仍是只读伴侣加几个写入页，Desktop 的助理模式和 App 结构不同。丁开心把目标定为 Muse 这一类个人 Agent 应用（你把目标说一次，它在后台一直推进；你在对话里交代、批准、查看、撤销），并要求 Desktop 和 App 都这样。

**决定**：

- **对话是中心，两端同构**：板块为 对话 / 动态 / 目标 / 资料库 / 我（App 三个标签：对话 / 动态 / 我，目标并入动态）（2026-11-07 起 App 结构改按 ADR-017：不放底栏，抽屉 + 头像详情）。App 作为第三个入口接入现有主要聊天（`gateway/main_conversation.py`，与 Desktop、Telegram 共用一段）。审批、凭据、连接、目标细化、建定时都以卡片出现在对话里。动态、权限、审批历史、定时、想法都是常驻助理上的同一套接口，两端只做展示，每阶段同时上线。Desktop 默认进入助理模式，「工作台」保留为第二个模式。
- **审批范围可选**：这一次 / 本任务 / 本定时任务 / 总是（类别、连接器、网站、收件人）/ 拒绝。仍由 `gate.decide()` 一处判定，扩展的是预授权输入。不变的硬规则：污点回合一切预授权失效；`IRREVERSIBLE`、`INTERACT` 任何范围不免；Telegram 里不能设「总是允许」；「对外发送」类的「总是允许」只能在 Desktop 上设；App 上设的「总是允许」30 天到期，每次新增都通知。
- **批准按风险分级**：普通批准（你的事项、草稿、Codex 建议 / 叫停）用日常钥匙点一下；对外发送、不可逆、设「总是允许」用批准钥匙（Face ID）。级别由服务端拟卡时决定并签进动作摘要，App 不能自行降级。
- **污点看上下文，不只看本回合**：历史消息带出处标记，回合起点只要上下文里仍有外部内容就视为污点，直到压缩或滚出窗口。共享主要聊天后，主人终端的干净输入不能「洗白」历史里的外部内容。
- **新增能力档案**：`owner_device`（App 回合：READ + OWN_DATA + DRAFT，无命令执行、无任意文件写、无浏览器操控、无委派开发；对外发送只出审批卡）；`scheduled_web`（定时任务可上网，但看不到目标、记忆、对话和本地文件）与 `scheduled_private`（能读私人上下文但不能上网），一个定时任务二选一；两者都不能对外发送或直接改东西，动作一律变审批卡。
- **Telegram 保留**为主人本人的备用对话渠道（改 ADR-011「IM 对话冻结、稳定后按使用情况删除」中关于 Telegram 的部分）；钉钉对话照旧冻结。
- **落地顺序**：阶段 A 对话为中心（前提：历史污点、`owner_device`、手机会话重启可恢复、手机网关发布脚本）→ B 托付（审批范围、权限与审批历史、定时任务两档案）→ C 主动（想法、目标细化、上手引导、记忆导入）→ D 范围（凭据、连接、资料库、本机数据、语音）。

**理由**：
- Muse 的体验优势集中在入口与交互（对话里完成一切、审批范围可选、权限与历史可见、主动建议），这些与本仓库的安全内核不冲突。
- 我们比它硬的部分（污点态预授权失效、撤销列出撤不回的影响、数据在自己的机器上）保留，并补上共享对话后暴露的历史污点缺口。

**不做**：每人一台云端虚拟机、回答对比、订阅、智能家居、自带邮箱、共享代理互聊、虚拟试穿。

**不改**：`decide()` 判定位置；无人值守 fail-closed（新档案是在其上开最小口子）；ADR-008 冻结范围；ADR-010 交接规则；新手机钥匙需主人批准（ADR-011 修订）。

**需要随实现更新的契约**：`tests/unit/test_three_end_contract.py`（`owner_device`、`scheduled_web`、`scheduled_private` 三列）；历史污点的契约测试（Telegram 消息进主要聊天后，下一个 Desktop / App 回合的 OWN_DATA 动作必须弹卡）。

### ADR-012 修订：后台推进的提议先过自动审核，低风险的可以不等主人（2026-11-02）

**背景**：后台主动推进目标只会拟提议，每一条都要主人批，体验离「它一直在推进」还差一步。Codex 开源的 guardian 与 Dot 的「自动审核 + 暂停」给出了做法：需要批准的动作先交给隔离的审核模型。

**决定**（丁开心 2026-11-02 定的放行表）：
- 后台推进拟出的东西先交审核模型（只看提议、所属目标与规则，没有工具），结论 放行 / 拒绝 / 交给主人。
- **只有两类可以被放行**：改主人自己的事项（把「下一步」写进目标卡，可撤销）；给常驻电脑登记项目派活（开发流水线只开分支和 PR，合并仍要主人；每天最多 3 张，可调）。
- 给 Codex 发话 / 叫停、对外发送、花钱、删除：永远交给主人。读过外部内容（污点）后拟的：不送审，交给主人。这些硬规则在送审前由代码判定，审核模型只能更严。
- 审核拒绝：撤回任务单，该目标暂停自动推进 24 小时，推送理由。审核失败或输出无法解析：交给主人，不放行。
- 每次审核写一行记录（`.vortocode/dispatches/auto_review.jsonl`）。`VORTOCODE_AUTO_REVIEW=0` 关闭。

**不改**：`decide()` 判定与对话回合里的确认；污点规则；IRREVERSIBLE / INTERACT 任何档位不免。本修订只作用于后台推进这一条自主线。

## ADR-013：主 agent 负责制——子 agent 只从登记角色创建，生命周期归任务服务，结果经主 agent 回到主人（2026-11-03）

**背景**：主人平时只面对一个主 agent（ADR-012）。委派与子任务记录已经存在（`CollaborationService` / `TaskLedger`），
但主 agent 不能提议新角色，后台子任务的结果只推到 Desktop，查在办工作要用多套工具。缺口分析见
[子 agent 生命周期](SUBAGENT_LIFECYCLE.md)。

**选项**：
- A. 维持现状
- **B. 沿用现有任务记录，补三处衔接（结果推送、在办汇总、角色提议）** ✅
- C. 仿照 OpenMausBot 新建一张统一的子任务表

**决定**：B（丁开心 2026-11-03 按建议确认）

1. 主 agent 是主人唯一的日常对话对象；子 agent 的问题与结果都经主 agent 的对话与推送出现。
2. 子 agent 只能按登记角色创建。新角色由主 agent 提议、主人批准；工具面限 read / deliver / dev；污点回合不能提议；
   read 型可在手机上批，deliver / dev 型只在 Desktop 用批准钥匙批。
   2026-11-12 主人修订：专员体系按 [STAFF_DESIGN.md](STAFF_DESIGN.md) 的 D1 使用 Desktop 普通主人确认，移除专员专用硬件钥匙；普通级别的签名手机写入按 L6 后续接入。岗位组合与禁用动作规则不变，专员不能获得 deliver 权限。
3. 生命周期的权威记录是现有任务服务（进程内 `CollaborationService` / `TaskLedger`，跨主机为任务单）；主 agent
   模型不持有状态，模型不可用时主人仍能查看、回答、停止。
4. 后台子任务的完成待验收、失败 / 中断、等回答，由代码拼一句经总助手通道推送，不唤醒模型；读过外部内容的
   子任务只说「有结果待核对」，不带标题、不转述结果。
5. 主 agent 通过一个只读汇总入口查看所有来源的在办工作，各来源的权威记录不变。
6. 落地顺序：G2 结果推送 → G3 在办汇总 → G1 角色提议（等审批卡类别落地后）。

**理由**：进程内子任务已统一在一套有轮次校验、执行与验收分开的记录上，再建一张表只会多一个要对账的来源；
主人感受到的缺口在「结果到不到得了我」和「它能不能自己找对帮手」。

**不改**：`gate.decide()`；污点规则；子 agent 不递归；ADR-008 冻结范围；ADR-010 交接规则；多 bot 设计 V1 的准入默认值。

**需要随实现更新的契约**：`tests/unit/test_three_end_contract.py`（`role_propose` 在各档案下的可用性：
`owner_device` 只能提 read 型，`unattended` 不可用）。

## ADR-014：大任务开任务上下文，由主 agent 协调职责分明的成员（2026-11-03）

**背景**：主人希望大任务由多个角色协作完成，成员可用不同模型和框架（自有 agent、Codex、Claude Code、DeepSeek
Harness、OpenCode、Pi 等），由主 agent 管理与协调；不要固定流水线，也不设群主层。ADR-013 的 G1（主 agent 提议
新角色）只在项目会话生效，常驻助理用不上。设计见 [任务上下文](TASK_CONTEXT.md)。

**选项**：
- A. 固定流水线（开发流水线按单选执行者）
- B. 频道群聊，成员自由接话
- C. 三层：主 agent → 群主 → 成员
- **D. 两层 + 任务上下文：主 agent 在独立上下文里协调成员** ✅

**决定**：D（丁开心 2026-11-03 确认，默认额度与默认 `open` 档按设计稿）

1. 大任务由主 agent 提议开任务上下文，主人批准；小任务照旧由主 agent 直接处理。
2. 成员之间不直接交流，全部经主 agent；成员按角色卡装配，工具面为封闭枚举，权限逐层收窄。
3. 任务上下文的根是 `TaskLedger` 中 `kind="team"` 的任务，成员派活是挂在根下的协作子任务；协调记录与主对话分开。
4. 开放档位 `open` / `private` 二选一：有联网成员就看不到私人资料。默认 `open`。
5. 预算、无进展判定、停止、重启规则由代码执行；协调人不能宣布完成，只能交主人验收。
6. 任务中途的对外 / 不可逆动作由代码按原始提议生成审批卡。
7. 成员执行框架经适配器接入：自有 agent、ACP 通用适配器（DeepSeek Harness、OpenCode 等）、Pi、Codex、Claude Code。
   能看到工具调用的框架，由我们的确认门判定其权限请求；看不到的只从外部限制，结果按外部内容处理。
8. 不设群主层；协调人字段预留，满足设计稿 §9 的条件再升级。
9. 取代 ADR-013 的 G1。

**对既有决定的修改**：
- ADR-008：冻结范围不变。任务上下文的额度另记在根任务的 `team` 字段，沿用 `task_chain_budget` 的规则（先落盘
  预留再执行、预留不退款），不复用其接口（它绑定 API 下派的单轮合同）。
- 多 bot 设计 V1：「完成唤醒 = 0」对任务上下文的根改为「成员结果唤醒协调人，受唤醒次数额度约束」；「bot 之间
  自由派活」仍关闭，成员不能派活。

**不改**：`gate.decide()`；污点规则（污点态预授权失效、历史污点）；无人值守 fail-closed；ADR-010 交接规则；
`IRREVERSIBLE` / `INTERACT` 任何范围不免。

**需要随实现更新的契约**：`tests/unit/test_three_end_contract.py`（协调人、联网研究员两种装配）；
`tests/unit/test_layering.py`；`open` 档协调人读不到记忆与目标、预算用尽不能再派、无进展转 `waiting_owner`、
污点结果不进主对话正文。

**修订（丁开心 2026-11-04）**：去掉任务上下文的额度（子任务数、轮数、步数、累计时限、唤醒次数）与「加预算」，
确认卡不再列额度；用量只计数给主人看。上面第 5 条中的「预算」与「对既有决定的修改」里关于额度、唤醒次数额度约束的
表述随之失效：完成唤醒改为「成员结果唤醒协调人，不设次数上限」，防空转只靠无进展判定（连续 3 次没进展或同一错误
3 次转「等你」）和成员单轮执行时限。

## ADR-016：Desktop 以会话为中心（2026-11-05）

**背景**：ADR-014 / 015 之后，产品形态是「一个主 Agent + 若干任务小组」：小组已是群聊，小组交付与等你决定会作为消息进入主对话（#761）。但设计规范（2026-10-27）仍按「功能放在哪」组织：侧栏放 3～5 个功能入口，其中「动态」「定时」「目标」打开的就是助理面板对应的标签；等你处理散在顶栏胶囊、侧栏角标、面板圆点和小组状态四处，点开后又被例行巡视淹没；打开 App 是空的新对话而不是主要聊天。2026-11-05 在 0.2.45 上逐页截图核对。

**选项**：
- A. 维持「五层入口」，只修细节
- **B. 以会话为中心：侧栏只放会话，等你处理集中到主要聊天顶部，右侧面板随会话类型变化** ✅
- C. B 的基础上把助理面板也改成「当前会话详情」，审核记录、身份移进设置

**决定**：B（丁开心 2026-11-05 确认；C 被否：主要聊天右侧保留现在仿 Muse 的助理面板）

1. 侧栏只放会话：新对话、搜索；主要聊天置顶（角标 = 等你的件数）；任务小组；旁聊（默认最近 5 条）；底部常驻电脑和设置。去掉「动态」「定时」「目标」三个重复入口；资料库、定制移进设置。
2. 打开 App 直接进主要聊天并停在最新一条；问候页改为主要聊天的空状态。
3. 等你处理只在主要聊天顶部出现一次，去掉顶栏任务胶囊。例行巡视（Codex 半小时进度）在「动态」里折叠，有变化的那条单独显示。
4. 主要聊天右侧保留助理面板（头像名片 + 五个标签），结构与样式不变；目标改为弹窗编辑，审核记录合并重复项。任务小组右侧是小组详情（成员、验收标准、用量、交付分支）。
5. 对话里的工具名与内部编号收进「详情」，正文用一句话说明。
6. 视觉规范、状态词、确认卡不变；iPhone 按同一结构跟进（ADR-012 同构）。

**理由**：入口按会话组织后，同一件事只有一个位置；最常用的主要聊天成为起点；小组与主对话的消息形态一致，Desktop 与手机的结构也能对齐。

**需要随实现更新的**：`docs/DESIGN_SYSTEM.md` 第 1～4、8 节（本 ADR 同步修订）；`desktop/scripts/check-installed.mjs` 的手工核对清单（随各批迁移更新）。

## ADR-017：iPhone 对齐 Desktop，设计语言两端共用（2026-11-07）

**背景**：Desktop 已按 ADR-016 改成以会话为中心，iPhone 还停在 ADR-012 的三个标签（对话 / 动态 / 我），两端不再同构。手机设计另有 2026-10-25 的四项底栏草案，三份文档互相对不上。iPhone 用系统默认样式（`List`、`.bordered` 按钮），和 Desktop 的 `--vc-*` 视觉没有关系。手机回复靠每 2 秒轮询，做完才一次性显示，也看不到任务小组和旁聊。2026-11-07 对照用户提供的 Muse 手机截图逐项核对。

**决定**（丁开心 2026-11-07 确认）：

1. iPhone 结构照搬 ADR-016，形式学 Muse。全屏主要聊天；顶部居中头像，下面一句话说明后台在做什么。左侧抽屉等于 Desktop 侧栏：主要聊天、任务小组、旁聊、搜索、设置。点头像打开助理详情，五段等于 Desktop 右侧面板：动态、目标、审核记录、定时、身份。「等你处理」在主要聊天顶部，和 Desktop 同一来源。
2. **不放底部标签栏**。动态、目标已收进头像详情；点子、资讯这类页面没有内容，不占位。
3. **设计语言只有一个出处**。`design/tokens.json` 生成 Desktop 的 `tokens.css` 和 iPhone 的 `DesignTokens.swift`，测试检查生成文件没有过期或被手改。审批卡、等你处理、动态记录行、执行过程、小组气泡、头像名片、状态胶囊两端结构一致。状态词两端同一份：`design/copy.json` 用同一个脚本生成 Desktop 的 `lib/copy.generated.ts` 和 iPhone 的 `Copy.swift`（M1 起：面板五段、会话入口、审批类别 / 级别 / 来源 / 范围、状态词）。
4. **深色两端统一**，用 Desktop 现有的深色（画布 `#1a1a19`、侧栏 `#141413`、卡片 `#222221`），手机不另设纯黑。
5. 能力边界不变：手机对话仍按 `owner_device` 档案运行，执行留在常驻电脑上。
6. 分批：M0 文档与共享变量 → M1 结构对齐 → M2 流式回复与执行过程 → M3 小组与旁聊 → M4 TestFlight 与真机验收。M3 的新手机接口涉及 97 的 Caddy 白名单，改前先问主人。M2 实际没有新接口：在原有的回合状态接口里加「到目前为止的回复」和执行步骤，手机回合进行中每秒读一次（2026-11-07）。

**理由**：入口按会话组织在 Desktop 上已经验证过，手机照搬后两端一一对应。变量和组件只有一个出处，改一处两端一起变，不会再各长一套。Muse 的形式（长对话、头像、抽屉、审批卡）与我们的安全内核不冲突。

**不做**：底部标签栏；兴趣资讯动态；手机直接跨应用执行；钱包、订阅。

**需要随实现更新的**：`docs/MOBILE_APP_DESIGN.md`（本 ADR 同步重写）；`docs/DESIGN_SYSTEM.md` 第 5 节（变量出处）；`mobile/ios/README.md`（随 M1 更新页面说明）。

## ADR-018：产品改名 VortoOne（2026-11-08）

**背景**：产品已经从「AI 编码 Agent」变成常驻个人助理（ADR-011、ADR-016、ADR-017），原名 VortoCode 里的「Code」让人以为只是写代码的工具。iPhone 准备上 TestFlight，App Store Connect 里的 App 还没建，现在改名成本最低。

**决定**（丁开心 2026-11-08 确认）：全部改成 **VortoOne**，包括内部标识和仓库名。为了不断登录、推送、数据和 97 上的服务，分五批做，每批合并、部署、核对后再做下一批：
