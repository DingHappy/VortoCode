# 任务上下文：主 agent 协调多个职责分明的成员（设计稿 v0.1）

状态：待评审，未实现。日期：2026-11-03。附 ADR-014 草案（§11），主人确认后移入 `DECISIONS.md`。

## 0. 结论

主人只面对主 agent。遇到大任务（多角色、多轮、可能跨天），主 agent 为它开一个**任务上下文**：一张任务单 +
一份成员表 + 一段独立的协调记录。主 agent 在这个上下文里按需派活、追问、请成员互审、决定返工和完成；成员各按
角色卡做本职，可以用不同模型，后续也可以用不同框架（Codex、Claude Code）。主对话里只看到开工、需要你决定、
完成这几件事。

两层结构：你 → 主 agent → 成员。不设「群主」这一层，但任务上下文的协调人可以单独配置模型和角色，等使用证据
表明需要时再升级成群主，记录不变（§9）。

不是流水线：没有固定的步骤顺序，下一步找谁由主 agent 判断。也不是群聊：成员之间不直接互发，所有交流都经主 agent。

## 1. 来源与取舍

| 参考 | 采用 | 不采用 |
| --- | --- | --- |
| OpenMausBot 的 Chief of Staff 与运行时契约 | 协调人派活、成员不自由互聊；每根任务的预算；无进展判定；被打断的回合只重跑一次 | 默认 Full access；每个 bot 一个常驻外部进程；频道里多 bot 自由接话 |
| 本仓库 `CollaborationService` | 派活 → 执行 → 审查接受或返工（最多 3 轮）→ 成员可提问；执行完成与验收分开；轮次校验拒绝迟到结果 | — |
| 本仓库 `task_chain_budget`（ADR-008 冻结） | 根任务上的执行额度：任务数、轮数、步数、累计时限，预留不退款 | 不改它的默认值，只给任务上下文的根显式传额度 |
| ADR-012 定时任务两档案 | 「能上网」和「能看私人上下文」二选一 | — |

## 2. 现状与缺口

| 已有 | 位置 | 对本设计的意义 |
| --- | --- | --- |
| 子任务生命周期 | `workflow/tasks/collaboration.py`、`tasks.py` | 成员的每次派活就是一条协作子任务，不新建记录 |
| 根额度 | `workflow/tasks/task_chain_budget.py` | 任务上下文的根，管所有成员的累计额度 |
| 角色卡 | `.vortocode/agents/*.md`（`agents/subagents.py`） | 成员的职责、工具面、模型；工具面是封闭枚举 |
| 结果推送 | `scheduling/task_notices.py`（G2） | 完成、失败、等回答推给主人 |
| 在办汇总 | `scheduling/work_status.py`（G3） | 增加「任务上下文」一段 |
| 历史污点 | `agents/taint.py`（ADR-012） | 主对话与任务上下文分开记录，污点不互相串 |

缺口：

1. 常驻助理（General 范围）没有委派能力，不能派成员。
2. 没有「任务上下文」这层记录：一张根任务单把成员、协调记录、预算串在一起。
3. 成员完成后没有人自动接手下一步：多 bot 设计 V1 把「完成唤醒」定为 0。
4. General 范围没有可用的成员角色：现有只读研究员要读项目文件，常驻助理没有项目目录。
5. 主人看不到任务上下文的完整记录（界面）。

## 3. 概念

| 名称 | 是什么 | 权威记录 |
| --- | --- | --- |
| 主对话 | 主人与主 agent 的主要聊天（Desktop / App / Telegram 共用一段） | `gateway/main_conversation.py` |
| 任务上下文 | 一个大任务的根：目标、验收标准、成员表、预算、开放档位、状态 | `TaskLedger` 中一条 `kind="team"` 的根任务 |
| 协调记录 | 主 agent 在这个任务里的对话历史：派了什么、成员回了什么、为什么返工 | 会话存储，键 `team-<根 id>`，与主对话分开 |
| 成员 | 按角色卡装配的执行者；一次派活是一条挂在根下的协作子任务 | 协作子任务（`collaboration`） |
| 角色卡 | 职责、工具面（封闭枚举）、模型、单次步数 | `.vortocode/agents/<名>.md` |

## 4. 生命周期

```
主 agent 在主对话里提议开任务上下文（任务卡：目标、验收、成员、预算、开放档位）
   → 主人批准（档位越高，批准要求越严，见 §6.2）
   → 创建根，协调人醒来，开始第一轮
   ↻ 协调人派活 / 追问 / 请互审 → 成员执行 → 结果写回子任务 → 协调人被唤醒
   → 需要主人决定：代码按原始提议生成审批卡，经主对话推给主人；协调人暂停等结果
   → 协调人判断完成：对照验收标准逐条给证据 → 根进入「待主人验收」
   → 主人验收 / 退回 / 停止
```

根状态：`proposed → running ⇄ waiting_owner → review → done / failed / cancelled`。

- **协调人不保存状态**：每次醒来只读根、子任务和协调记录。模型不可用时，主人仍能看状态、回答、停止。
- **唤醒来源**：根刚创建；成员完成、失败、中断、提问；主人在审批卡或主对话里回了话。没有定时空转。
- **完成由主人验收**：协调人只能把根交到「待主人验收」，不能自己宣布完成。

## 5. 成员与协调人的工具

协调人（主 agent 在任务上下文里）的工具：

| 工具 | 作用 |
| --- | --- |
| `team_assign(member, instruction, expected)` | 给成员派一件事，`expected` 写清交回什么；生成一条协作子任务 |
| `team_review(task_id, verdict, note)` | 接受或返工某条结果（沿用 `task_review`，返工走 `task_followup` 的轮次规则） |
| `team_cross_review(task_id, reviewer)` | 请另一个成员审查某条结果；审查员只拿到结果和验收标准 |
| `team_ask_owner(question)` | 需要主人的信息或决定：推到主对话，根进入 `waiting_owner` |
| `team_submit(summary, evidence)` | 对照验收标准逐条给证据，交主人验收 |
| `team_status()` | 只读：成员、在办、预算用量 |

协调人**没有**：联网、对外发送、改文件、执行命令、改成员权限、开新的任务上下文。

成员（第一个切片只开放两种角色卡，都在 General 范围可用）：

| 角色 | 工具面 | 模型 | 说明 |
| --- | --- | --- | --- |
| 研究员 `web-researcher` | 只读联网：`web_search`、`web_fetch` | 默认便宜模型 | 读到的外部内容使本次子任务为污点 |
| 审查员 `reviewer` | 无工具 | 与研究员不同的模型 | 只看交给它的结果和验收标准，给出问题清单 |

开发成员（Codex / Claude Code 在隔离 worktree 里写）放到第二个切片（§10）。

## 6. 安全

### 6.1 两种开放档位，二选一

| 档位 | 成员能做什么 | 协调人能看什么 |
| --- | --- | --- |
| `open`（默认） | 可以有联网成员 | 只有主人批准的任务卡；**看不到**记忆、目标、对话、本地文件、插件数据 |
| `private` | 成员都不能联网 | 可以带主人批准时选定的私人资料（某个目标、某段记忆） |

理由与 ADR-012 定时任务两档案相同：私人资料和出网成员放在同一个任务里，被注入的协调人就能让联网成员把私人资料
放进请求地址带出去。这条由装配代码保证，不靠提示词。

### 6.2 批准

| 动作 | 批准方式 |
| --- | --- |
| 开 `open` 任务上下文（只含研究员 / 审查员） | 普通批准，手机可批 |
| 开 `private` 任务上下文 | 普通批准，卡片列出带入的私人资料 |
| 带开发成员、对外发送类成员（第二个切片起） | 批准钥匙，只在 Desktop 批（#723 合并前：只在 Desktop 本机会话确认） |
| 加预算、加成员、换模型 | 重新批准，卡片显示前后差异 |
| 任务中途需要的对外 / 不可逆动作 | 代码按成员的原始提议生成审批卡（对象 + 正文哈希 + 来源子任务），不经协调人转述 |

### 6.3 污点

- 子任务读过外部内容，就带 `tainted`；协调人读到它的结果，本回合为污点，协调记录里这条带出处标记（ADR-012 历史污点）。
- 任务上下文的污点**不进入主对话**：主对话里关于任务的消息由代码拼（状态、轮次、预算、有无待决策，同 G2）。
  协调人写的总结只在主人打开或主 agent 明确去读时出现，并标为外部内容。
- 污点态下协调人的一切免确认授权失效（现有规则），它提出的任何动作都变审批卡。

### 6.4 权限逐层收窄

成员 ⊆ 角色卡 ⊆ 任务上下文的开放档位 ⊆ 主 agent 当前档案 ⊆ 主人授权。装配时求交集，任务中途不能放宽。
`owner_device`（手机）发起的任务上下文，开放档位上限为 `open`，不能带开发成员。

## 7. 预算与停止

每个根显式传入额度，复用 `task_chain_budget` 的结构，只对 `kind="team"` 的根生效，不改它的默认值：

| 额度 | 第一个切片默认 | 用完时 |
| --- | --- | --- |
| 成员子任务数 `tasks` | 8 | 协调人不能再派，交主人决定加预算或结束 |
| 累计轮数 `rounds` | 12 | 同上 |
| 累计步数 `steps` | 96 | 同上 |
| 累计时限 `timeout_seconds` | 3600 | 同上 |
| 协调人唤醒次数 | 16 | 同上 |
| 同时在跑的成员 | 2 | 排队，不拒绝 |

- **无进展判定**：协调人连续 3 次醒来既没派出新活、也没接受任何结果，或者同一个错误连续出现 3 次，根转
  `waiting_owner`，推送说明原因。判定用记录里的事实，不用模型自述。
- **费用**：按根记模型用量（`usage_scope`）；拿不到价格就记未知，不记为零。
- **停止**：主人随时停整个根，在跑的成员子任务一并请求取消；记「取消已请求」，确认停下后才说已停止。
- **重启**：被打断的协调人回合重跑一次，开头说明可能已有部分动作生效；第二次被打断即失败。成员子任务沿用现有
  `interrupted` 处理。

## 8. 主人看到什么

- 主对话：开工确认卡；需要你决定的卡；「待你验收」及证据摘要（代码拼）；失败或卡住的原因。
- `work_status`（G3）多一段「任务上下文」：标题、状态、轮次、预算用量、在跑的成员。
- 任务视图（第三个切片）：Desktop 和 App 都能打开，看到协调记录、成员结果、每条的模型和出处，可以停止。

## 9. 以后升级成「群主」

任务上下文记录里留 `coordinator` 字段，第一版固定为主 agent 自己（同一人设、同一模型路由）。以后需要时，只给
它配独立的模型、角色说明和汇报格式，就成了群主，根、子任务和协调记录都不用改。升级条件（满足任一）：

- 经常有 2 个以上大任务同时跑好几天，主 agent 顾不过来；
- 某类任务的协调需要专门的模型或领域知识；
- 实际观察到主 agent 在多个任务之间切换时协调质量明显下降。

## 10. 实施切片

1. **S1 只读小组（General 范围）**：任务卡提议与批准；`kind="team"` 根与协调记录；协调人工具；研究员和审查员
   两种角色卡；唤醒、预算、无进展判定；`work_status` 与 G2 推送接上。不装外部 CLI。
2. **S2 开发成员**：成员可以是 Codex / Claude Code（复用 `external_workers` 的隔离与参数规则），只在登记的
   项目里、一次性 worktree 中写；交付仍是分支和 PR，合并要主人。前提：常驻电脑装好 CLI 并登录专用账号（部署
   配置变更，单独征求主人同意）。
3. **S3 任务视图**：Desktop 与 App 同构展示（`docs/DESIGN_SYSTEM.md`），停止与加预算走审批卡。

每个切片合并前跑 `./scripts/ci-local.sh`；S1 上线后用 2–3 个真实任务观察：协调轮数、返工次数、主人介入次数、
费用，再决定是否做 S2。

## 11. ADR-014 草案

> 待主人确认后移入 `docs/DECISIONS.md`。

**ADR-014：大任务开任务上下文，由主 agent 协调职责分明的成员（2026-11-03）**

- **背景**：主人希望大任务由多个角色协作完成，成员可用不同模型和框架，由主 agent 管理与协调；不要固定流水线，
  也不设群主层。ADR-013 的 G1（主 agent 提议新角色）只在项目会话生效，常驻助理用不上。
- **选项**：A. 固定流水线（开发流水线按单选执行者）；B. 频道群聊，成员自由接话；C. 三层：主 agent → 群主 → 成员；
  **D. 两层 + 任务上下文：主 agent 在独立上下文里协调成员** ✅
- **决定**：
  1. 大任务由主 agent 提议开任务上下文，主人批准；小任务照旧由主 agent 直接处理。
  2. 成员之间不直接交流，全部经主 agent；成员按角色卡装配，工具面为封闭枚举，权限逐层收窄。
  3. 任务上下文的根是 `TaskLedger` 中 `kind="team"` 的任务，成员派活是挂在根下的协作子任务；协调记录与主对话分开。
  4. 开放档位 `open` / `private` 二选一：有联网成员就看不到私人资料。
  5. 预算、无进展判定、停止、重启规则由代码执行；协调人不能宣布完成，只能交主人验收。
  6. 任务中途的对外 / 不可逆动作由代码按原始提议生成审批卡。
  7. 不设群主层；协调人字段预留，按 §9 的条件再升级。
  8. ADR-013 的 G1 由本 ADR 取代：成员角色在任务卡里选，新角色卡的提议并入 S1 之后再评估。
- **对既有决定的修改**：
  - ADR-008：`task_chain_budget`、`task_dependencies` 为任务上下文解冻，只用于 `kind="team"` 的根；其余冻结模块不变。
  - 多 bot 设计 V1：「完成唤醒 = 0」对任务上下文的根改为「成员结果唤醒协调人，受唤醒次数额度约束」；「bot 之间
    自由派活」仍关闭，成员不能派活。
- **不改**：`gate.decide()`；污点规则（污点态预授权失效、历史污点）；无人值守 fail-closed；ADR-010 交接规则；
  `IRREVERSIBLE` / `INTERACT` 任何范围不免。
- **需要随实现更新的契约**：`tests/unit/test_three_end_contract.py`（新增协调人、联网研究员两种装配的能力列）；
  `tests/unit/test_layering.py`（任务上下文服务只经 workflow 公开 API）；新的契约测试：`open` 档协调人读不到
  记忆与目标、预算用尽不能再派、无进展转 `waiting_owner`、污点结果不进主对话正文。
