# 私人助理对标 Muse

核对日期：2026-10-15。对标对象是 Meta 的 Muse 个人助理。
产品范围保持两种模式：私人助理负责个人事项与持续跟进，Code 负责项目开发与交付。

Meta 的[产品说明](https://about.fb.com/news/2026/09/introducing-muse-personal-ai-agent/)
强调个人目标、跨应用执行、后台工作和用户批准；
[设计说明](https://introducing.muse.ai/)描述主聊天、旁聊、目标跟踪、活动记录和审批卡。
[Muse Wonder 研究说明](https://research.meta.ai/blog/muse-wonder)将相关背景的主动检索称为
Active Memory，将持续尝试、处理阻塞和必要时提问称为 Active Focus。
这些是公开产品与研究描述，不是本项目与 Muse 的同题实测结果。

## 能力差距与顺序

| 方向 | 当前基础 | 尚需补齐 |
| --- | --- | --- |
| 相关记忆 | 已确认事实、待确认提案、删除、历史对话搜索、逐回合相关记忆检索；待确认提案标出可能被它更新的旧记忆，确认时可「记住并替换旧的」 | 话题表之外的说法仍然召回不到（例如「做财务」对不上「什么工作」），这是词法检索的上限；自动识别矛盾（目前按话题与用词提示，需人确认）；用真实对话做召回评测 |
| 个人目标 | [个人目标卡](./ASSISTANT_PERSONAL_GOALS.md)支持期限、下一步、阻塞、逐条验收；用户可批准一次到点提醒、查看受理状态并明确确认看到，聊天可只读查询 | 多步骤实际办事、事件触发与真实渠道验收 |
| 主动跟进 | 定时事项、执行历史、状态变化通知及补发；安静时段（`VORTOCODE_QUIET_HOURS`，时段内攒着、结束推一条汇总；主人亲自定了时间的提醒照常到点推）；同来源同内容一小时内只推一次 | 事件触发（已有：日程开始前提醒、新邮件提醒；还缺 Notion 变更等）、提醒强度、跨事项（不同来源讲同一件事）去重 |
| 跨应用执行 | 浏览器/MCP 基础、GitHub 只读连接器；[助理插件](./ASSISTANT_PLUGINS.md)：日历（查日程、早报附今日安排；确认后新建日程）、Notion 只读（搜索、读页面与数据库）、邮件（IMAP 收件箱，早报附未读，新邮件推手机；确认后存草稿，不发送） | 改期、取消日程；邮件发送仍由用户在邮箱里完成 |
| 长任务 | 持久任务、隔离开发、恢复、审查入口；派出去的任务能提问、手机上回答；结束后助理复盘：做完逐条对照验收标准，失败诊断并起草下一次（最多 3 次，下发仍要人批）；答过的问题按项目记下，之后派活自动带上（可在对话里查看、删除）；任务卡和跑太久的提醒显示流水线做到第几步；派活可挂到个人目标的验收标准，做完一键确认记进目标（仍是用户确认，不由任务结束推导） | 推进目标时按未通过的验收标准各派一张（同一条标准不重复派）；派活成绩可随时查、周日晚报附本周数字 | 用这些数字回头调机制；更多真实场景积累 |
| 权限与透明度 | 能力范围、确认门、污点传播、工具审计 | 独立监管与凭据不可见执行的同等隔离证明尚不存在 |

先补相关记忆，再补个人目标闭环与日历/邮件连接器。继续使用已有任务、计划、记忆和通知
基础，不新增用户模式，也不以开发任务结束推导个人目标达成。

## 记忆更新：提示被取代的旧记忆（2026-10-17）

- 待确认的记忆候选附上「可能更新了」的旧记忆：同一话题（住处、工作、称呼、家人与宠物、作息、
  联系方式、饮食、汇报方式），或至少两个有意义的双字词重叠。「住在北京」和「搬到杭州」几乎没有共同用字，
  只靠词法抓不到，所以按话题归类。不调用模型。
- 确认时可选「记住并替换旧的」：先批准，成功后才删旧的；只能删除服务端此刻重新算出的相关项，
  客户端传来的其他 id 一律忽略。只点 ✓ 时旧记忆保留，拒绝时什么都不删。
- 这是提示而不是判定：话题相同不等于矛盾（例如两条不同的宠物），由人决定替不替换。

## 逐回合相关记忆

- 仅 General 助理的 Desktop/Web 与 IM 交互会话自动启用；项目 Code 与无人值守联网作业
  不自动获得个人记忆。原有非联网定时事项的人设/静态资料规则保留。
- 复用原 `recall_memory` 权限、能力、审计与工具额度门。通过只读 SQLite 查询读取
  `__longterm__`，不读取待确认或隔离提案，不创建或修复数据库。
- 复用原词法排序规则，并加一层话题归并：同一件事的不同说法算同一个话题，例如老婆/妻子/爱人，我家猫/橘猫，晚饭吃什么/不吃香菜；含虚词的双字组合不参与匹配。固定案例上，调词表用的那组命中从 6/17 提到 17/17，调好后另写的那组从 6/8 提到 7/8，跟记忆无关的提问仍然一条都不误带；候选最多 512 条，查询最多 256 字，最多 3 条结果、正文合计 600 字，
  含边界及元数据不超过 2,000 字。SQL 虚拟机工作量及锁等待也有上限。
- 不增加模型请求或下载嵌入模型。此轮不是语义检索，未命中不代表没有相关记忆。
- 资料只附到当前回合的模型请求，不复制到会话历史，也不改变冻结的系统提示。
  新批准或删除的记忆在后续用户回合重新查询；这不撤回已发送给模型的内容或删除聊天记录。
  原工具审计和活动记录仍遵循既有保留规则。
- 自动召回命中后仍按不可信资料处理；保留当前请求优先规则及原确认边界。
- 现有 `VORTOCODE_AUTO_RECALL=0` 可在新建会话时关闭自动召回，手动检索仍可用。

## 中英混合召回与干扰词（2026-10-24）

共享词法检索补齐中英混合输入：例如「VortoCode这次怎么部署」会单独识别项目名，
`safe_id`、`Next.js`、`C++` 保留完整标识符。英文词和标识符按边界匹配，单独查询 `Go`
不会因为 `Django` 含相同字母而命中；天气、笑话等问句中的常见英文功能词不参与召回。

候选中较少出现的查询词获得更高权重，完整英文词/标识符也有额外权重，减少大量通用
「项目、部署、签名包」记录挤掉准确项目名的情况。只有相关话题参与候选扫描，先用字面
检查跳过不可能命中的正则匹配。同分仍沿用调用方的重要性和记录时间顺序。

这套排序同时用于 `SessionStore.search_memories` 和逐回合自动召回；自动路径原有的
512 条候选、256 字查询、3 条输出及正文预算不变，也没有新增索引、模型请求或嵌入依赖。
候选窗口外的记忆仍可能漏掉；仅共享中文词也仍可能召回宽泛背景。它不能判定事实矛盾、
自动替换旧资料或实现任意说法的语义匹配。

新增固定合成检索案例覆盖混合项目名、英文前后缀干扰、函数名、大小写和具体词排序；
真实 SQLite 搜索及原生/提示式协议的 General 会话回归，检查相关事实进入本次模型请求、
无关英文事实排除、模型请求次数不增加，系统前缀和持久历史保持稳定。运行：

```sh
python -m pytest tests/unit/test_recall_relevance.py tests/unit/test_recall_concepts.py \
  tests/unit/test_memory_search.py tests/unit/test_assistant_active_memory.py -q
```

这些仍是合成资料上的检索与接线检查，不能当成真实用户一周使用、真实模型记忆使用效果
或 Muse 的同条件成绩。后续需要独立的真实场景记录，分别核对漏召回、误带入、过时事实
误用和用户反复解释次数；本轮没有读取实际用户记忆库，也没有更新已部署的应用和服务。

后续安装记录：该召回实现已随 2026-10-24 本机构建 `e1cbc94d` 安装并启动；这更新的是
本机应用状态，不补充真实记忆使用效果或常驻服务端部署的证明。安装与实测边界见
[Desktop 验收](DESKTOP_ACCEPTANCE.md#2026-10-24-安装与真实模型验收)。

## 验收与评分

工程回归检查同一主聊天中新批准/删除的记忆是否在下一回合生效、无关或待确认资料是否混入、
权限拒绝是否生效、上下文是否有界、检索是否额外调用模型，以及系统前缀与持久历史是否稳定。
这些检查证明流程合同，不代表模型正确理解、实际手机体验或与 Muse 持平。

后续用固定案例分别记录相关事实命中率、过时事实误用率、任务完成率、用户纠正次数和模型
token/请求成本。已有公开标准集的题目与评分标准保持不变；供应商过滤导致未完成的案例
保留未评分状态，不用合成工具测试替代正式模型分数。
