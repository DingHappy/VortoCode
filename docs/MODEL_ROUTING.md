# 主与子 Agent 的多渠道模型分工

可以让主 Agent 使用高能力模型处理规划、分发和结果核对，再让研究或实现子 Agent 使用另一模型。它们复用原运行时、任务台账、隔离工作区、确认门和验收流程；不建立另一套任务池。

## Desktop 配置

1. 在「设置 → 模型」配置默认服务与主模型。需要固定主 Agent 时，在聊天输入框选定模型；「自动」仍按原快速/强力档选择当前回合模型，与子 Agent 分工独立。
2. 需要跨渠道时，先在「其他模型供应商」登记各自的 OpenAI 兼容服务、凭据和模型。默认服务也可以通过一个中转同时提供多个模型。
3. 在「高级模型选项 → 主与子 Agent 模型分工」分别选择研究、实现和审查模型。`default:模型ID` 表示默认服务，`供应商ID:模型ID` 表示已登记渠道；模型 ID 的冒号标签保留。
4. 与上方主模型一起保存。原生确认框会列出分工，保存后按既有流程重启当前引擎；其它后台项目下次启动采用新配置。本轮开发没有修改用户的实际配置，也没有重启运行服务。

| 环节 | 配置位置 | 生效路径 |
|---|---|---|
| 主 Agent | 默认主模型、聊天输入框选择 | 原主会话规划、分发和汇总 |
| 研究子 Agent | `research` | 默认只读委派；未明确指定模型的自定义 read/deliver 角色 |
| 实现子 Agent | `implement` | 隔离实现子 Agent；未明确指定模型的自定义 dev 角色 |
| 审查子 Agent | `review` | 原隔离代码审查路径 |

留空使用默认服务模型，不保证跟随本回合在聊天框临时选择的渠道。角色文件明确的 `model` 优先；没有模型或写 `inherit` 时使用角色分工。高级调用方显式注入的测试/预算客户端保留原有优先规则，不能为了路由绕开其控制。General 仍不直接获得项目或编程工具；对登记项目的任务在目标实例执行，目标实例须配置自己的模型渠道。

这是操作者指定的分工，不按标价自动判断任务难度或自动升级模型。更便宜的单次请求可能增加返工；应按同题任务结果、重试次数和累计用量核对总成本。目前没有新增真实模型的节省比例结论。

## 常驻服务与 CLI

沿用原 `VORTOCODE_MODEL_ROLES` 配置。下例全部为虚构标识，需替换为自己的服务和真实模型 ID；不要把凭据写进角色文件、对话或公开仓库。

```dotenv
DEFAULT_MODEL=planner-model
VORTOCODE_PROVIDER_WORKER_BASE=https://worker.example.test/v1
VORTOCODE_PROVIDER_WORKER_KEY=replace-with-private-credential
VORTOCODE_MODEL_ROLES=research=worker:reader-model,implement=worker:coder-model,review=default:review-model
```

每个渠道只使用自身凭据，不拿默认服务的 Key 补另一端点。Desktop 对未登记渠道、缺凭据和包含分隔注入的角色目标拒绝保存。已知的默认服务冒号模型名会规范化为 `default:模型ID`，避免当成另一个渠道。旧配置没有角色字段时保持兼容；Desktop 未配置分工时注入显式空表，避免继承父进程中无关的角色配置。

CLI 的既有环境变量配置在渠道无效时仍会记录警告并回落默认；运行前可用 `describe_roles()` 核对是否生效。请求发出后发生服务异常，不新增自动转昂贵模型、跨渠道重放或绕过权限的策略。

## 执行记录与边界

普通委派任务在原台账记录当前轮次选择的渠道和请求模型，任务卡只展示与当前轮次匹配的记录。这里记录的是 `selected_request_target`，不证明供应商已经响应、模型内部权重或工具任务已经通过验收；旧记录不推断为本轮模型。供应商可能返回不同的模型标记，不能用配置名称证明实际权重。

子 Agent 明确切换普通模型名时，对传入的标准客户端复制配置，避免修改父 Agent 或其它并行子 Agent 的模型。新建副本的本地连接由委派/流水线调用方清理；其它调用方仍按其自身生命周期管理。显式注入的包装客户端不会被剥离来绕过预算。

子 Agent 的执行结果仍交给原父任务验收流程。选择了审查模型、写入模型目标或执行结束，都不能替代实际审查与验收。角色分工本身不增加文件、执行、联网、发送或发布权限。

## 快速决策与按需评判

`task_model_profiles` 从原任务台账读取当前会话、当前仓库内的模型表现；`task_model_assess`
用任务 ID 和精确轮次评估是否继续原模型、建议升级、先验收结果或补证据。这两个工具已接入
主 Agent 的原委派工具装配，不另建执行器或数据库。HTTP 下派通过同一委派执行器采集记录，
可以由所属会话的主 Agent 读取；这不是所有助理聊天、独立 dev 任务或跨会话的全量计量。

先走不调用模型的快速规则：已验收就结束，第三轮停止追加，等待中的任务先补输入，
失效依赖先处理依赖；同一任务两轮失败/返工建议比较其他模型。
只读角色至少有八个不同的同类任务、全部已验收、用量和单价记录齐全、验收率的 Wilson
95% 下界至少 0.65，才会建议继续原模型。扫描不完整时不使用这个稳定表现捷径。
这些是有版本的保守启发式，仍需核对当前结果，不是能力保证。

证据不足时，可在 Desktop 高级模型设置填写「模型评判器」，或显式配置：

```dotenv
# 以下全部是虚构模型标识。
VORTOCODE_MODEL_ROLES=research=default:reader-model,assess=default:judge-model
```

评判器留空关闭额外调用；配置无效时返回不可用，不回落默认付费模型。它是按需工具，
不在每次任务结束后自动调用，也不监听完成事件启动新回合。评判工具属于对外操作，继续
经过原有权限/确认门；明确注入客户端的委派装配不绕过它另开评判渠道，严格自动检查亦拒绝
此对外工具。评判输入会发送到该角色配置的模型服务，请按自己的数据和服务范围选择。

接口借鉴 [Jev 的原子问题与代码组合方式](https://docs.typesafe.ai/introduction)：
分别预测当前结果满足验收的概率、原模型下一轮解决不足的概率、需要更强模型的概率，
再由固定代码阈值组合建议。每条验收条件必须给出 met/missing/unknown；met 的引用必须
是当前结果的原文。匹配引用不证明该内容真实，需要由原审查流程核对。
普通 LLM 通过严格 JSON 验证提供这些预测；**没有集成 Jev API，也不宣称具备其类型生成保证、
延迟或校准能力**。模型原始概率标为 unvalidated。后续发起 Agent 的 accept/rework 与预测
形成 Brier 分数（越低越好），按工作模型和评判模型分别统计样本数；发起 Agent 的审查
并非独立真值，不能以此冒充公开基准或用户验收。

每轮至多尝试一次模型评判，调用前先落盘认领；同版本并发/重试返回原记录。输入超过
24,000 字符或粗估 6,000 token 时不调用、不截断证据。输出最多请求 800 token，20 秒超时，
客户端重试为零。请求失败、过滤、无效输出或中断保持未知，不自动重放。进程崩溃留下的
running 认领也不自动重试。任务变化后迟到的建议标为过期，仅保存计量，不用它推动执行。
这是请求数量与本地等待限制，**不是供应商硬费用上限或远端停止凭据**。

## 模型画像与边际成本记录

每轮原委派记录渠道/请求模型、角色工具范围、任务经过时间、按模型的已记账响应 token、精确/估算
来源、失败、发起 Agent 验收和返工。`task` 可指定 `task_type`：analysis、coding、review、
documentation、translation、extraction，默认 analysis；这是调用方标签，并非系统验证过的
语义分类。返工保留标签和历史。画像按渠道、模型、工具范围、任务类型分组，展示样本数、
验收率、返工次数、耗时中位数/P95、token 中位数/P95/最大观察值和重复轮次。
最大观察值是已见样本的边界，不能推导模型上下文或能力极限。
任务经过时间包含工具执行和确认等待，不是供应商纯推理延迟；等待用户答复之前的已记账
用量也保留在原轮次，恢复不抹掉前一轮投入。

不采用旧目录中的固定质量评分或猜测价格。运行方可通过 `VORTOCODE_MODEL_PRICES` 设置
明确的渠道单价，单位为每百万输入/输出 token。以下数字仅为演示，**不是任何模型报价**：

```dotenv
VORTOCODE_MODEL_PRICES={"default:reader-model":{"input_per_million":1,"output_per_million":2,"currency":"CNY"},"default:judge-model":{"input_per_million":3,"output_per_million":4,"currency":"CNY"}}
```

支持 USD/CNY/EUR，不换汇、不混加不同币种；缺价格、缺用量、异常轮次的总费用保持 null。
每条已记账响应保留单价快照和费用估算，缓存优惠、阶梯价、工具费和供应商未返回的费用
不在此估算内，也不把它当账单。范围包括本轮嵌套调用中进入原 `_account` 的响应；SDK
内部尝试、绕过原记账路径的请求和未完成流式响应不保证可见。`accounted_responses` 只说明
本轮正常返回且存在记账响应，不证明完整计费覆盖或模型权重。

模型画像将评判费用与执行费用分开列出。只有同一币种、每轮都有价格且全部已审查的分组，
才提供执行费用/已验收轮次，返工的费用也计入分子。评判建议另给下一轮历史均价及
均价/预测成功率，用于比较原模型继续的边际投入；它依赖未校准预测，排除新评判费用，
没有足够历史时保持未知。台账只扫描最多 512 个目录条目并返回覆盖状态，画像不跨仓库、
不跨会话汇总，不保存第二份长期模型库。

任务卡显示当前轮次的用量、耗时、费用估算及建议。任何建议都不会自动换模型、追加轮次、
扩大权限或验收任务。下一步应使用固定公开基准和真实任务对照，验证成本、质量及概率校准
后再考虑自动选模；本功能的模拟响应回归不能证明实际节省或 Jev 的线上效果。

## 原模型与候选的成本比较

任务卡的「评估模型与成本」只把请求草稿放入发起会话，用户发送后由主 Agent 读取最新
`task_status` 并调用原 `task_model_assess`。比较本身不发模型请求；评判器未配置或额外
调用未获确认时，也能返回比较和证据缺口。比较记录保存在原任务中，绑定轮次与结果版本；
任务卡仅显示当前轮次的上次比较时间，不自动刷新或把旧比较当作新的执行授权。

候选来自运行端已配置的默认模型、聊天模型清单、快速/均衡/强力档和有效工作角色配置，
不因仅配置了 assess 角色而推荐评判器去执行工作。不从项目文件或历史记录擅自增加新的
供应商目标。最多比较 64 个配置目标及当前模型，候选截断会使覆盖状态不完整。
只登记过但未真正用于相同任务类型和工具范围的模型，显示「没有同类任务记录」。
已配置不证明工具兼容、供应商响应或实际权重。默认回环无 Key 服务使用与真实客户端一致的
非秘密占位符身份，不借用云端 Key，也不以此绕过服务认证。

比较展示每个模型的任务数、验收率置信下界、任务耗时 P95，以及执行、评判、合计的
每次验收费用估算。合计以历史已知执行/返工费用加评判费用，再除以已验收轮次；不只计入
最后成功的一次。未知评判费用不当作零，不同币种不换算或混排。显示零费用要求明确的零单价。
下一轮均价仍是历史观察估算，不是费用承诺。

可参与比较的分组必须至少有八个不同的同类任务、全部轮次已结算为执行终态且已处理验收、
验收率 Wilson 95% 下界不低于 0.65，用量不含缺失/估算，执行与评判的费用、币种和单价
快照均完整。执行模型或评判器的历史单价与当前配置不一致时，仍保留历史费用，但停止使用
该分组给排序建议；单价快照超过 64 个版本时同样标记覆盖不足。

在合格的同币种分组中，代码寻找费用、质量置信下界和耗时之间的 Pareto 权衡。只有原模型
也有足够证据，且某个候选的合计费用严格更低、质量下界不低、任务耗时 P95 不高，才提示
「值得进一步核对」。更便宜但更慢、样本不足、价格变化或未结清费用都不会被包装为全面更优。
失败的依赖先处理依赖，不通过购买一次评判推断成模型能力不足。

这些是当前会话、当前仓库中的历史观察，任务难度、验收者和调用频率可能不同，不能证明
在同一道题上换模型就会获益，也不能证明某模型属于更强档。样本门槛和质量阈值是第 1 版
保守策略，尚未经过真实模型校准。公开标准题集的配对对照仍须使用原评测入口、固定题目、
冻结代码和独立评分，单独核算评判开销；本轮工程回归与界面夹具不作为模型能力题库。

固定公开题的角色隔离、请求归属、离线 token 预估和静态题型路由回测现已接入原标准评测，
使用方法及尚未验证的边界见 [模型配对与离线路由回测](./MODEL_POLICY_REPLAY.md)。

## 外部执行者（Codex / Claude Code CLI）

> **实验功能，默认关闭。** 主线由 VortoCode 自己的子 Agent 完成。只有同时设了 `VORTOCODE_EXPERIMENTAL_EXTERNAL_WORKERS=1`，下面的角色表才生效；Desktop 在「设置 → 高级模型选项」里有对应开关（打开时弹原生确认，开关后重启当前引擎）。关着时 `cli:*` 选项不提供，已选的标注「不生效」，`vc doctor` / `vc workers status` 也会说明实验功能未开启。

### 两种模式，别混

| | 本机模式 | 常驻模式 |
|---|---|---|
| 场景 | 你自己电脑上的 Desktop / 终端 | 常驻电脑（服务器）上的 VortoCode 服务 |
| 判定 | 没设 `VORTOCODE_WORKER_HOME` | 服务环境里设了 `VORTOCODE_WORKER_HOME` |
| CLI 登录与配置 | 你的个人登录；透传个人配置里的模型选择 | 只用 `$VORTOCODE_WORKER_HOME/codex`、`/claude` 两个专用目录（0700），不碰服务账号 home 下任何个人配置 |
| 在哪配置 | Desktop「设置 → 高级模型选项」 | 服务的 env 文件 / systemd drop-in |
| 登录 | 平时怎么登就怎么登 | `vc workers login codex`（设备码）/ `vc workers login claude` |
| 查看状态 | `vc workers status`、设置页 | 服务器上 `vc workers status`；本机 Desktop 通过 `/api/delegations/capabilities` 的 `external_workers` 只读查看 |

Desktop 只改本机引擎，不远程改常驻电脑的配置。

隔离 dev 流水线的「实现」和「审查」两个角色可以交给本机已安装、已登录的 Codex CLI 或 Claude Code CLI。拆解、worktree 隔离、自测重试、逐件和集成验证、确认门、开 PR 仍由 VortoCode 负责，外部执行者只负责在给定目录里写代码或给出审查结论。

```dotenv
VORTOCODE_EXTERNAL_WORKERS=implement=codex,review=claude
VORTOCODE_EXTERNAL_WORKER_TIMEOUT=1800      # 单次运行秒数，超时终止整个进程组
# VORTOCODE_CODEX_BIN=/path/to/codex        # 可选，缺省从 PATH 查找
# VORTOCODE_CLAUDE_BIN=/path/to/claude
```

- 配置只从主进程环境变量读取，不读仓库文件。只认 `implement`、`review` 两个角色和 `codex`、`claude` 两个执行者，其他值会被忽略并记警告。
- 某个角色配置了外部执行者后，它的 `VORTOCODE_MODEL_ROLES` 分工不再生效。调用方显式注入的审查模型（测试、预算客户端）仍然优先。
- 实现角色只在流水线创建的一次性 worktree 里写。Codex 使用 `-s workspace-write`；Claude 使用 `--permission-mode dontAsk` 加工具白名单（读、查找、编辑、`pytest`）。审查角色一律只读：Codex 用 `-s read-only`，Claude 不给编辑工具。
- 不使用任何 `--dangerously-*`、`danger-full-access`、`bypassPermissions` 参数。两者都不接入外部 MCP。
- **个人配置只透传「用哪个模型、哪家服务」**，hooks、插件、记忆、通知、MCP、权限放宽都不继承：
  - Codex 以 `--ignore-user-config` 运行（登录凭据照常从 `CODEX_HOME` 读），再从 `config.toml` 回填 `model`、`model_reasoning_effort`、`model_provider`、`service_tier`，以及所选 `model_providers.<id>` 的定义。所以在 config.toml 里配的第三方供应商可以用；这个供应商 `env_key` 指向的环境变量，必须在 VortoCode 引擎的环境里也存在（从 Dock 启动的 Desktop 读不到 shell 配置文件里的变量）。
  - Claude 只加载 `local` 级 settings，再从 `~/.claude/settings.json`（或 `CLAUDE_CONFIG_DIR`）回填 `model`（转成 `--model`）、`env`（作为子进程环境变量传入，不进命令行参数）和 `apiKeyHelper`。用 `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` 接第三方模型时，配在 settings.json 的 `env` 里即可，Desktop 启动时也能生效。`env` 里的 `GITHUB_TOKEN` 和 VortoCode 自己的密钥照样会被剥离。
  - 如果环境里设了 `ANTHROPIC_API_KEY`，Claude 会按 API 计费，而不是走订阅额度。
- 不保存会话：Codex 用 `--ephemeral`，Claude 用 `--no-session-persistence`。每次实现或审查都是新会话，不会出现在你自己的 `resume` 列表里。订阅额度与你平时使用这两个 CLI 共享。
- `vc doctor` 的 `workers` 一项会检查配置的执行者：命令有没有找到、有没有登录（`codex login status` / `claude auth status`），以及实际使用的模型和服务。
- 子进程环境沿用 `sandbox/policy.child_env()` 的密钥剥离，并额外去掉 `GITHUB_TOKEN`、`GH_TOKEN`：push 和开 PR 只由 VortoCode 通过确认门完成。
- 无人值守档位（cron/heartbeat）拒绝启动外部执行者。事件流里出现联网动作时，本回合会被标为污点。
- **确认未启动才自动接手**：未找到 CLI 等确认进程尚未启动的不可用情况，才可由已授权的内置 Agent 在同一 worktree 接手，并设置 `VORTOCODE_EXTERNAL_WORKER_COOLDOWN_MIN` 冷却（默认 30，`0` = 不冷却）。备用工厂不能再返回外部 CLI 适配器。进度会说明接手原因。
- 已启动的 CLI 遇限流、登录/鉴权失败、非零退出等，不能只凭错误文本认定没有副作用：标为需人工核对，不自动切换，也停止当前开发/对应审查视角的自动重试。隔离工作区保留供核对，不自动覆盖同一工作区 ID。原执行报告和已确认的问题保留，执行者也不进入自动改用内置 Agent 的冷却路径。详细合同见[执行恢复](EXECUTION_RECOVERY.md)。
- 开发任务里的实现执行者可以提问：缺少必要事实时，它会在最后一条回复里输出一行 `VORTO_QUESTION {"question": …, "options": […], "context": …}`，VortoCode 识别后调用同一个 `ask_task_question`，问题进入任务台账、推送给你、任务进入等待。回答之后，和内部子 Agent 一样在干净的 worktree 里带着问答上下文重做当前块，不续用外部 CLI 的会话。只有存在提问通道时（有所属会话的开发任务、未超过提问次数），才会把这条约定告诉执行者；没有通道时输出了这一行，按失败处理，不会当成结论。审查执行者不能提问。
