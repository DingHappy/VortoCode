# 主与子 Agent 的多渠道模型分工

可以让主 Agent 使用高能力模型处理规划、分发和结果核对，再让研究或实现子 Agent 使用另一模型。它们复用原运行时、任务台账、隔离工作区、确认门和验收流程；不建立另一套任务池。

## Desktop 配置

1. 在「设置 → 模型」配置默认服务与主模型。需要固定主 Agent 时，在聊天输入框选定模型；「自动」仍按原快速/强力档选择当前回合模型，与子 Agent 分工独立。
2. 需要跨渠道时，先在「其他模型供应商」登记各自的 OpenAI 兼容服务、凭据和模型。默认服务也可以通过一个中转同时提供多个模型。
3. 在「高级模型选项 → 主与子 Agent 模型分工」分别选择研究、实现和审查模型。`default:模型ID` 表示默认服务，`供应商ID:模型ID` 表示已登记渠道；模型 ID 的冒号标签保留。
4. 与上方主模型一起保存。原生确认框会列出分工，保存后按既有流程重启当前引擎；其它后台项目下次启动采用新配置。本轮开发没有修改用户的实际配置，也没有重启运行服务。

| 环节 | 配置位置 | 生效路径 |
|---|---|---|
| 主 Agent | 默认主模型、聊天输入框选择 | 原主会话规划、分发和汇总 |
| 研究子 Agent | `research` | 默认只读委派；未明确指定模型的自定义 read/deliver 角色 |
| 实现子 Agent | `implement` | 隔离实现子 Agent；未明确指定模型的自定义 dev 角色 |
| 审查子 Agent | `review` | 原隔离代码审查路径 |

留空使用默认服务模型，不保证跟随本回合在聊天框临时选择的渠道。角色文件明确的 `model` 优先；没有模型或写 `inherit` 时使用角色分工。高级调用方显式注入的测试/预算客户端保留原有优先规则，不能为了路由绕开其控制。General 仍不直接获得项目或编程工具；对登记项目的任务在目标实例执行，目标实例须配置自己的模型渠道。

这是操作者指定的分工，不按标价自动判断任务难度或自动升级模型。更便宜的单次请求可能增加返工；应按同题任务结果、重试次数和累计用量核对总成本。目前没有新增真实模型的节省比例结论。

## 常驻服务与 CLI

沿用原 `VORTOCODE_MODEL_ROLES` 配置。下例全部为虚构标识，需替换为自己的服务和真实模型 ID；不要把凭据写进角色文件、对话或公开仓库。

```dotenv
DEFAULT_MODEL=planner-model
VORTOCODE_PROVIDER_WORKER_BASE=https://worker.example.test/v1
VORTOCODE_PROVIDER_WORKER_KEY=replace-with-private-credential
VORTOCODE_MODEL_ROLES=research=worker:reader-model,implement=worker:coder-model,review=default:review-model
```

每个渠道只使用自身凭据，不拿默认服务的 Key 补另一端点。Desktop 对未登记渠道、缺凭据和包含分隔注入的角色目标拒绝保存。已知的默认服务冒号模型名会规范化为 `default:模型ID`，避免当成另一个渠道。旧配置没有角色字段时保持兼容；Desktop 未配置分工时注入显式空表，避免继承父进程中无关的角色配置。

CLI 的既有环境变量配置在渠道无效时仍会记录警告并回落默认；运行前可用 `describe_roles()` 核对是否生效。请求发出后发生服务异常，不新增自动转昂贵模型、跨渠道重放或绕过权限的策略。

## 执行记录与边界

普通委派任务在原台账记录当前轮次选择的渠道和请求模型，任务卡只展示与当前轮次匹配的记录。这里记录的是 `selected_request_target`，不证明供应商已经响应、模型内部权重或工具任务已经通过验收；旧记录不推断为本轮模型。供应商可能返回不同的模型标记，不能用配置名称证明实际权重。

子 Agent 明确切换普通模型名时，对传入的标准客户端复制配置，避免修改父 Agent 或其它并行子 Agent 的模型。新建副本的本地连接由委派/流水线调用方清理；其它调用方仍按其自身生命周期管理。显式注入的包装客户端不会被剥离来绕过预算。

子 Agent 的执行结果仍交给原父任务验收流程。选择了审查模型、写入模型目标或执行结束，都不能替代实际审查与验收。角色分工本身不增加文件、执行、联网、发送或发布权限。
