# 开发目标的保存与执行合同

2026-10-30。复用 `.vortocode/goals`、原 TaskLedger、TaskRunner 与工作区执行租约，不新增执行器、队列或自动批准。

## 保存必须成功

开发目标的创建、合同修改、验收器配置、证据记录及任务状态投影必须检查持久化结果。写入失败明确报错，不返回仅在内存中修改的目标作为成功。目标写入复用原临时文件、fsync、原子替换工具。

目标变更与提交使用同一短事务：进程内任务状态锁，加按目标 ID 的跨进程非阻塞锁。任务同步也使用该事务，避免旧快照覆盖新关联。开发目标的非法状态或任务关联结构不转换成可执行的草稿。

## 一次确认只对应一项任务

`POST /api/goals/{id}/run` 携带 `expected_task_id`，表示用户所见的上一项任务；首次为 `""`。任务 ID 由目标 ID、上一项任务 ID 和执行/续跑模式确定，不使用随机新身份来重试。

- 相同请求已产生任务时，只返回原任务和 `replayed=true`，即使它已经结束，也不重新排队。
- 用户刷新目标并明确开始新一轮，才携带新的上一项任务 ID 创建下一项任务。
- 不同模式竞争同一快照、过期快照、仍在执行/等待的历史任务、无法核实的任务或合同不匹配时拒绝新提交。
- 未传 `expected_task_id` 的旧客户端只对应首次执行，不能借重复请求创建后续轮次。新版 Desktop 从目标快照携带上一项任务 ID，并将重放结果显示为“找到原任务，未重复下发”。客户端与运行时应同步更新；旧运行时没有本合同保证。

提交先把固定任务 ID 与目标关联写入目标，再创建原任务台账中的准备记录、保存排队尝试标记，最后调用原 `enqueue_worker`。在进入执行池前，目标关联和任务记录都必须已经保存。原失败上下文在清除 blocker 前固化到任务 prompt。

## 失败与恢复

- 目标保存失败：不创建或启动新任务，API 返回 503。
- 任务创建或排队认领保存失败：不启动 worker，固定目标关联不改成另一个随机任务。
- 目标已保存关联但任务记录缺失/损坏：返回 409 并保留身份，需核对原存储；不猜测此前是否执行，不自动重建任务或删除关联。这种严重存储异常仍需人工修复记录。
- 准备记录存在但未完成排队、或排队后响应异常：不重放。可核实的未运行 queued 记录标为 interrupted；已运行的记录按原任务状态核对。
- 重启后未完成的保留命名空间任务按 interrupted 恢复，不自动排队。续跑或新一轮仍需显式确认。
- API 将保存失败映射为固定的 503 提示、事务竞争映射为 409，不暴露原始存储路径或底层异常。

`interrupted` 不证明远端副作用不存在；`replayed` 不表示任务成功；任务结束也不代表目标 achieved。逐条验收、commit 绑定和已有失效规则保持原合同。

## 同时创建并执行

`POST /api/goals` 默认只保存草稿。使用 `start=true` 时必须提供固定 `request_id`，格式为 1–120 位字母、数字、点、下划线或连字符。同一身份与同一合同重试只返回原目标/原任务，不覆盖后续进展；身份用于不同合同、或原文件损坏时拒绝重建。未提供身份时，先保存目标，再通过目标执行入口确认。

## 验证范围

草稿或验收器在创建后已修改时，旧的创建并执行请求不能启动变更后的合同，须刷新目标后重新确认。API 读取到提交事务之间也比较合同摘要，期间发生变化则拒绝执行。
