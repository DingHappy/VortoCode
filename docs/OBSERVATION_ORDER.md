# 观测快照的顺序与安全重传

范围：Codex 观察员到常驻助理的整份快照上报，复用 `GET /api/codex/status`、`POST /api/codex/report` 和原有 `.vortocode/codex/state.json`。不增加路由、任务数据库、执行池或事件服务。

## 协议 v1

GET 状态额外提供 `report_protocol: 1` 和 `report_cursor`（尚未启用时为 null）。新观察员先读这个游标，再采集新的原生快照。POST 原报告中新增：

```json
{
  "report_order": {
    "schema_version": 1,
    "cursor": {
      "producer_id": "codex.observer:Mac-A",
      "generation_id": "opaque-generation-id",
      "sequence": 1
    },
    "parent": null
  },
  "threads": []
}
```

parent 必须是采集前已知的完整当前游标。首次上报时可为 null；接替已有来源时必须引用它。接收端在同一个文件锁内读取旧状态、核对前序、更新报告与游标：

- 同一 producer/generation：sequence 必须为当前序号加一。
- 新 producer 或 generation：sequence 必须从一开始，且 parent 仍必须精确匹配当前游标。
- 游标相同且整份请求摘要一致：返回重复回执，不写状态、不刷新接收时间、不追加事件或再次生成提醒。
- 同一序号内容不同、前序变化、旧包晚到或跳号：409，保留当前状态。
- 另一写入者持有文件锁：503，可安全重传原报告。

排序依赖因果前序和序号，不比较两台电脑的墙钟。时间仍用于判断观测是否新鲜。producer/generation 是不透明关联信息，不授予权限，也不用于加载插件或启动核心。游标类型和继承检查位于 `src/agents/backends/observation_order.py`，存储锁留在 scheduling 层。

## 发送与接替

一个 ReportPublisher 对应一个观察循环，初始化时生成新 generation，不并发发送：

1. 启动时通过状态接口协商协议并读取游标，再采集原生快照。
2. 发送前冻结整份请求，直到回执的游标与本次请求一致才推进本地序号。
3. 超时、临时错误、503 或取消后保留原 pending 请求；同一个 publisher 恢复时先原样重传，不能换正文却沿用序号。
4. 原 pending 确认后，如果本次采集的快照已有变化，继续发送最新整份快照；不能把确认旧包误记成最新快照已送达。
5. 409 表示当前写入权已变化。旧 publisher 停止上报，不重新读取游标来自动抢回。明确重启观察循环会创建新 generation，重新读取当前游标后接替；旧循环在途的请求不能覆盖新代次。

接收端只保存最新游标和该请求的摘要。重复确认只针对最新已接受请求，不维护无限历史回执。publisher 的 pending 在内存中；进程重启后读取服务端状态并采集新快照，不声称恢复了丢失期间的所有样本。

文件锁覆盖接收端全部新旧格式报告的写入，并保留同一锁文件 inode。POSIX 的跨进程锁与竞争写入有离线回归；Windows 使用对应文件锁分支，尚未进行原生 Windows 验收。

## 升级兼容

- 旧常驻服务不声明 report_protocol：新观察员使用旧上报方式，不宣称具备顺序保证。
- 声明不支持的协议、游标缺失或格式无效：不降级成旧方式发送。
- 新服务尚未接受有序来源时，仍接受旧格式报告。
- 一旦该状态槽接受有序来源，后续旧格式上报返回 409，防止旧观察员覆盖新状态。回滚旧观察员不能静默绕过该限制。

一个状态槽当前仍只表示一份权威的 Codex 观测源，不是多台电脑报告的自动合并表。观察循环协商结果在其生命周期内固定；旧服务升级后，重启观察循环才能启用有序模式。

## 运行状态与配置

Desktop 设置 → 能力 →「让助理查看 Codex」现有卡片同时显示保存的开关与当前观察员状态，两者分开：配置在下次启动时生效，保存成功不表示观察员已经启动或连接成功。

- 本机引擎通过现有 `GET /api/status`（及原 status 快照）提供 `codex_observer` v1：是否配置、观察循环身份、当前阶段、更新时间、最近采集/确认送达时间、传输方式、未确认报告标记及固定错误码。
- 状态仅在进程内保留，不新增台账；不返回上报地址、令牌、异常正文、会话内容或执行命令。阶段可以是等待 Codex、连接、采集、上报、运行、重试、被接替或停止。
- 状态读取不使用当前选中的远端连接。Desktop 先查询原生管理的运行端清单，只读取唯一运行中的本机 General 引擎；核对回环地址，并在读取后再次核对进程、运行端和地址。来源发生变化则丢弃结果，不尝试其他目标或凭据。
- 卡片可见时每 10 秒核对，隐藏窗口降频至 60 秒。手动与周期刷新合并；卸载后迟到结果不更新卡片。读取有原快照超时边界，不启动、重启或接管观察员。
- 运行状态超过 2 分钟未更新、未来时间、无法读取或旧引擎缺少诊断时明确待核对/不支持。最近确认送达按 30 分钟窗口判断，兼容空闲时的 10 分钟心跳；旧版传输会明确说明没有顺序校验保证。
- 被接替时说明本实例停止上报且不会自动抢回；该状态不表示其他观察员已经健康，也不表示 Codex 已经停止执行。确认送达只证明报告回执，不表示工作完成。
- 旧观察循环的清理不能覆盖新循环的状态。临时错误保留未确认报告，后续核对成功才清除重试状态；诊断层不改变批准动作的执行或恢复规则。

## 保留边界

- 实现的是整份快照替换与安全重传，不是事件回放。断线期间未采集或已被后续快照覆盖的中间事件不会自动补齐；完整事件流仍应复用既有 Gateway 机制另行接入。
- 状态保存与通知投递不构成一个事务。重复上报不会重复生成提醒，但不保证进程在保存后、通知前崩溃时提醒恰好送达一次。
- 不解决 actions.json 的 sending 崩溃对账，不重发执行指令，不改变原生审批和人类确认门。
- 以上是代码与离线协议验收，尚未证明真实 Codex、常驻主机网络或已安装 Desktop 的端到端表现。
