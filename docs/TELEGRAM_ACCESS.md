# Telegram 接入与管理员邀请

## 当前可用：单主人安全配对

`vc im-pair telegram` 在部署机的交互式终端生成一次性高熵配对码。只有拿到码、在 10 分钟内从 Telegram 私聊发 `/bind <码>` 的真实发送者，才会成为这个 Bot 的 owner。服务记录 Telegram 数字 ID，不保存配对码或 token；记录按 Bot ID 隔离、保存在仓库外，文件权限为 `600`。重新运行配对命令不会覆盖已有 owner。运行中的 Bot 桥仍需 token，缺少 token 或 owner 时拒绝启动。

现有 Telegram 桥只有一条 owner 会话，并把所有回复和确认发给 owner。为避免他人的输入、历史和产出串到这条会话，Telegram 现在只接受 owner，即使白名单包含其他 ID 也不会放行。这个边界必须保留到下面的多租户能力真正完成。

## 后续产品：只接受管理员邀请

用户注册采用**管理员邀请**，没有公开自助注册或“首条消息自动成为用户”。管理员在受认证的管理入口生成单次、短期有效的邀请；邀请码只保存哈希，记录签发人、用途、期限、兑换/撤销状态。受邀者在私聊中兑换，服务从 Telegram 的 `from.id` 绑定身份，不相信用户输入的 ID。管理员可立即撤销成员、邀请和未完成任务的后续权限。邀请仅授予使用资格，不授予管理员或部署机权限。

受邀用户能真正使用 Bot 之前，必须同时完成并验证：

1. **路由隔离**：每人的私聊只进自己的会话；回复、按钮确认、通知、附件、任务结果都带不可由模型改写的用户路由。群聊默认不作为多用户工作区入口。
2. **工作区隔离**：每人独立的文件、仓库、会话历史、记忆、Artifact、任务和日志；不能从路径、工具、MCP 或后台任务读取另一个用户或管理员的状态。执行进程使用隔离容器或等效 OS 权限边界，不能共享管理员的宿主凭据。
3. **权限与额度**：新成员默认只读/低额度；按用户执行并发、模型费用、存储和速率限制，超额拒绝并可审计。写文件、外发和 PR 动作按所属工作区确认；成员不能批准管理员任务。
4. **持久化与恢复**：邀请和成员状态事务化保存，重启后仍能撤销、审计和恢复；Bot token 轮换不改变成员归属；重复更新和并发兑换不能重复创建账户。
5. **验证**：用两个独立 Telegram ID 做消息、确认、附件、任务、重启和撤销的交叉隔离测试，再做真实 Bot 验收；没有这些证据，不启用邀请兑换入口。

当前部署的下一步是完成主人 Bot 的凭据轮换、配对和单人验收。管理员邀请入口尚未实现，不能通过扩大 `VORTOCODE_TG_ALLOW_FROM` 代替它。
