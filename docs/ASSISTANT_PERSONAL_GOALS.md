# 私人助理的个人目标

助理侧栏的「目标」页用于记录个人事项：目标、逐条达标条件、下一步、阻塞、期限和下次跟进。
它与工作台的开发目标共用 Goal 数据类型及 `.vortocode/goals`，使用 `kind=personal`
区分。既有未标记类型的目标仍视为开发目标，两个入口互不读取或执行对方的目标。

## 使用流程

1. 在目标页展开「新建目标」，填写目标、每行一条的达标条件和下一步，可选填期限与跟进时间。
2. 随进展更新下一步及阻塞；清空阻塞不会消除已有的失败验收。
3. 展开一条达标条件，填写依据，再点「确认达标」或「记录未通过」。
4. 只有全部条件都有通过依据，目标才成为「已达成」。已有目标复验未通过会重新打开。
5. 聊天中询问个人目标时，助理可以按需调用 `personal_goals` 读取当前状态。

期限和跟进时间本身不建立提醒。保存进展后，展开提醒正文，核对将发送给助理已配对通知渠道
的内容，再点「批准按时提醒」。这是一次提醒，由现有助理巡检按分钟检查，不调用模型、
运行代码或启动办事任务。时间已过时，下轮巡检处理；服务离线期间不保证准时。
只有配置了通知的 General 助理运行端才能批准，本机未配置通知时会明确禁用入口。
已批准且尚未受理的提醒也显示在「定时」页和定时状态查询中；修改与暂停仍在个人目标卡操作。
目标提醒由助理巡检检查，不由 cron 作业总开关控制；需要停止时在目标卡暂停。

修改目标进展或验收会取消尚未发送的提醒批准；保存后须核对新的正文并重新批准。
「暂停提醒」只取消尚未发送的批准，不能撤回已受理或结果不明的通知。
聊天工具仍只读；创建、更新、提醒批准与验收在目标卡上操作。模型没有这些写入工具。

需要跟进编码项目时，可在既有 `codex_handover` 确认门中显式关联此目标，限定本次验收项与累计判断额度。
关联不启动 Goal 内的任务或验收器；下一步发给 Codex 仍逐条批准，目标达成仍需用户验收。
使用及停止边界见 [目标与 Codex 跟进](CODEX_GOAL_SUPERVISION.md)。

## 通知与用户回执

| 状态 | 依据与后续 |
| --- | --- |
| 等待到点 / 待重试 | 正文与时间已由用户批准，尚未受理 |
| 通知处理中 | 发送尝试已先保存，结果尚未保存 |
| 已受理 | 发送通道或原补发队列受理，不证明送达或用户已读 |
| 结果不明 | 超时、发送异常或发送期间进程中断；不自动重发 |
| 连续未受理 | 明确未受理三次后停止，等待用户重试 |
| 用户已确认看到 | 用户在卡片明确点「我已看到这条提醒」，不是自动获取的手机已读回执 |

明确未受理采用一分钟、两分钟退避，最多三次；再次批准会形成新提醒，保留最近 20 条旧记录。
结果不明时，必须先核对此前通知，再勾选接受可能重复的提醒，才能重新批准。
所有状态都与目标验收分开：收到提醒不会替代任何一条达标条件。

批准、发送认领和回执使用同一目标文件与跨进程锁；发送前先持久认领，保存失败则不发送。
锁覆盖通知调用与回执保存，通知调用使用十秒超时。恢复时发现遗留认领只标为结果不明，不猜测成功
也不自动重放。每轮最多尝试五条提醒，一项损坏或失败不阻塞其余事项。
通知复用现有台账、IM/转发和补发队列，不增加调度循环或任务库。
补发仍遵循原队列的期限、次数和容量限制；受理不是最终投递保证，也不承诺跨服务恰好一次。

## 状态与存储边界

`active` 表示推进中，`blocked` 表示显式阻塞或有未通过条件，`achieved` 表示逐条确认通过。
任务完成、通知接受和对话里的口头承诺都不会推动目标达成。
记录依据代表操作者的确认，不是对外部事实的独立核验。

创建使用客户端请求 ID 去重，同一 ID 与相同合同的重试返回原目标，不覆盖后续进展。
改变创建内容必须换请求 ID。更新与验收提交当前整数 `revision`，由跨进程锁串行核对；
过期版本和繁忙状态返回冲突，调用方刷新后再操作。写盘使用私有临时文件、fsync 和原子替换，
保存失败返回不可用，不报告成功。损坏的个人记录不会被列表当成空结果。

目标读取不会检查 Git 或运行开发验收器。目标查询工具只装配到 General 的 Web/IM
交互会话，返回有界摘要；文字可截断，列表最多五条未达成目标，可指定 ID 核对逐条依据。
资料属于不可信输入，读取沿用工具权限、回合污点与记忆提案的来源标记，不能变成执行授权。
目标文字不会预先冻结进系统提示。

## HTTP 合同

| 入口 | 行为 |
| --- | --- |
| `GET /api/assistant/goals` | 个人目标列表与期限提示 |
| `POST /api/assistant/goals` | 创建；必填 request_id、objective、acceptance_criteria、next_action |
| `GET /api/assistant/goals/{id}` | 精确读取单个目标 |
| `PATCH /api/assistant/goals/{id}` | revision 与可选 next_action、blocker、due_at、follow_up_at |
| `POST /api/assistant/goals/{id}/criteria/{criterion_id}/evidence` | revision、summary、布尔 passed，以及 confirmed=true |
| `PUT /api/assistant/goals/{id}/follow-up` | revision、布尔 enabled；启用必须 confirmed=true，结果不明时另需 acknowledge_uncertain=true |
| `POST /api/assistant/goals/{id}/follow-up/acknowledge` | revision、confirmed=true，明确记录用户看到提醒 |

日期为带时区的 ISO 时间，空字符串清空日期。创建不接受 start、status 或 verifier。
通用范围没有开发目标的 run/resume/verify 权限；即使在项目范围，也不能从开发目标入口执行个人目标。

## 回归与验收

工程回归覆盖持久化、创建去重、旧版本与并发竞争、逐条验收和复验、权限隔离、损坏状态、
只读查询、资料污点、客户端来源变化及迟到响应。浏览器使用虚构目标检查卡片操作，
不读取真实聊天或使用真实模型。

这些检查证明状态与交互合同，不是 Muse 同题能力评分，也不证明已安装的 Desktop、
线上后台执行或真实用户端已验收。真实渠道送达、实际用户回执及执行多步骤办事仍需单独验收。
