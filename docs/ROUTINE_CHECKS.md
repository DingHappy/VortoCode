# 定时工作：先检查，有新东西再调模型（设计稿 v0.1）

状态：待评审；§4.1（PR1）已实现，其余未实现。日期：2026-11-03。

## 0. 与当前方针的关系

主人面对的始终是一个总助手（[ADR-012](DECISIONS.md)、[多 bot 设计](MULTI_BOT_DESIGN.md)）。本设计只改后台
定时工作「什么时候值得花一次模型」，结果仍以总助手的身份进入同一条主人通道（`owner_reporter`，
来源 `assistant`）和早晚报，不新增 bot、入口、任务台账或调度器：挂在现有 `cron.yaml` 和巡检登记表上。

## 1. 现状：哪些周期性路径在调模型

| 路径 | 位置 | 现在什么时候调模型 | 已有的节制 |
| --- | --- | --- | --- |
| 插件提醒（日程、新邮件） | `plugins/*.reminders` 经 `assistant_watch._plugin_reminders` | 不调 | 去重键、读不到不提醒 |
| 早报 / 晚报 | `assistant_watch._compose_body` | 当天有素材才调；无事早报一行、晚报不发 | 模型失败发数据版；外部内容只附在正文后、不进模型 |
| 目标推进 | `scheduling/goal_advancer.py` | 每个进行中目标每 12 小时判断一次（有在途任务单时跳过） | 安静时段不跑、每轮最多 3 个 |
| cron prompt 作业 | `scheduling/cron.py:run_job` | 每次到点都开一个带工具的隔离会话（build 模式），不管有没有新东西 | token 预算、出网逐作业申报 |
| 心跳 | `scheduling/heartbeat.py:run_heartbeat` | 无 backlog 时每次值班跑一回合 | 便宜模型、activeHours、`HEARTBEAT_OK` 静默 |

早晚报与插件提醒已经符合「先检查」。缺口在后三项：

- **目标推进会重复打扰**（从代码路径推断，未见真机记录）：目标卡和任务单都没变时，每 12 小时仍重新
  判断一次；结论是 `ask` 时每次都推同一个问题，`suggest` 与现有下一步相同时也再推一次。推送去重窗口
  默认 60 分钟（`notices._dedup_window_seconds`），挡不住 12 小时的重复。
- **cron prompt 作业没有「没新东西就不跑」**：例如「看看有没有重要邮件」这类作业，每次都是完整会话。
- **新邮件提醒是逐封推**：没有重要性判断，打扰预算（ADR-011）只能靠每轮条数上限。

## 2. 借鉴来源与取舍

参考 OpenMausBot 的 proactive routines 设计文档（只读了文档，未核对其实现）：

| 采用 | 不采用 |
| --- | --- |
| 检查是纯代码；没有新条目就不开回合，只记「检查过」 | 它默认 Full access、靠审批级别兜底 |
| 读取失败不等于没有新东西：游标不动、退避、显示问题 | 依赖第三方连接平台与专用分拣小模型 |
| 新条目批量交给一次运行，按记录（records）给，按 id 去重 | 例程可起草回复（我们无人值守下写动作一律拒绝，见 §5） |
| 模型答结构化 JSON，读不懂就算这次失败、不推送、条目留到下次 | 早报卡片原地编辑（我们已有早晚报） |
| 游标只在结果保存后前移；状态只存 id 和时间 | |
| 重叠、补跑、退避、每日次数上限 | |

## 3. 目标与非目标

**目标**

1. 没有新东西就不开模型回合，也不推送。
2. 有新东西时，只把新的那几条作为数据交给模型。
3. 模型结果必须是可校验的结构；校验不过 = 失败，不推送，条目下次重给。
4. 读取失败与「没有新东西」分开表达，连续失败通报一次。
5. 同一个判断不重复打扰主人。

**非目标**

- 不改 `gate.decide()`、污点规则、无人值守 fail-closed。
- 不实现 ADR-012 的 `scheduled_web` / `scheduled_private` 两档案（属阶段 B，另做）；本设计带检查的回合
  没有工具，比 `scheduled_private` 更窄，不依赖它。
- 不改心跳（理由见 §4.4）。
- 不做自动回信、自动发送、自动建日程。

## 4. 设计

### 4.1 PR1：目标推进加输入指纹（最小、独立、先做）

`goal_advancer.advance_once` 在调用 `judge` 前计算指纹：

```
fp = sha256(_material(goal, linked, projects) + due_bucket(goal, now))
due_bucket ∈ {"none", "later", "within_48h", "overdue"}
```

- 指纹与上次判断时相同，且上次判断不足 `REJUDGE_MAX`（默认 7 天）→ 跳过：不调模型、不推送。
- 指纹变了（目标卡、验收项、任务单状态、可派活项目任何一项变化）或跨过到期桶 → 照常判断。
- 记录放在巡检状态 `watch.json` 已有的 `goal_advance` 旁边：
  `goal_advance_fp: {goal_id: {"fp": ..., "at": ..., "action": ...}}`，只存哈希、时间和动作名。
- 主人回答了 `ask` 的问题，通常会改目标卡（下一步、阻塞），指纹随之变化；没改就不再追问。
- 判断读不懂（`parse` 返回空）或调用失败时不记指纹，下个周期照常重判。
- `suggest` 的下一步与目标卡上现有的下一步相同时不推送。
- 被指纹跳过的目标不占每轮 `MAX_PER_PASS` 的名额。

状态：已实现（随本设计稿同一个 PR）。

### 4.2 PR2：检查合同与 cron 作业字段

新模块 `src/scheduling/checks.py`（scheduling 层，可导入 `plugins`，与 `assistant_watch` 同向）：

```python
@dataclass(frozen=True)
class CheckItem:
    id: str                    # 来源内稳定的 id，例如邮件 UIDVALIDITY:UID
    kind: str                  # "mail" | "calendar" | "runs"
    fields: Dict[str, str]     # 短字段，已截断；不放正文全文
    external: bool             # 外部来源 → 进模型时按不可信数据给

@dataclass(frozen=True)
class CheckResult:
    ok: bool
    items: List[CheckItem]     # 只含游标之后、且未判断过的条目
    cursor: Dict[str, Any]     # 本次读到的位置；调用方决定何时保存
    error: str = ""            # ok=False 时的一句原因，不含凭据和正文
```

检查函数的规则：只读、有超时、不调模型；失败返回 `ok=False`，绝不返回「空且成功」。

`cron.yaml` 新增三个可选字段，**不写这些字段的作业行为完全不变**：

```yaml
- name: 重要邮件
  schedule: every 15m
  checks: [mail]          # 先跑检查；没有新条目就不开回合
  deliver: notify         # notify：按条推送 | brief：并入下一份早晚报
  max_runs_per_day: 24    # 模型回合上限，超出的条目等下次
  prompt: |
    下面是新邮件的发件人和主题。挑出需要我今天回复或处理的，说一句为什么。
```

运行顺序（`run_job` 中，`checks` 非空时）：

1. 跑检查。失败 → 不调模型，游标不动，计入连败；连败达阈值通报一次（复用 `CronState.record_result`
   与 `_escalate_streak`）。
2. 没有新条目 → 只更新该作业的 `checked_at`，不写运行台账、不通知。「定时」页显示「检查过 · 没有新的」。
3. 有新条目 → **一次不带工具的模型调用**（与早晚报、目标推进同一形态：`llm.chat`，非 `run_isolated_session`），
   条目放进数据块，外部条目用内核认的不可信边界包裹。
4. 校验答案（§4.3）。不通过 → 本次失败，不推送，游标不动，同一批下次重给。
5. 通过 → 先保存「已判断 id + 新游标」，再按 `deliver` 投递；推送用 `cron:<作业>:<条目 id>` 作去重键。
   保存后、投递前崩溃 → 条目不会重给（已判断），投递由现有补发队列负责。

**带 `checks` 的作业不能同时有 `allow_web`，也没有工具**（v1 两者互斥，加载时报错）。需要工具或出网的
作业继续用不带 `checks` 的原方式。

可靠性规则：

| 情形 | 处理 |
| --- | --- |
| 上一次模型调用还没结束 | 照常检查，不交付新条目，等它结束 |
| 电脑睡眠后醒来 | 错过的多次检查合并成一次 |
| 模型调用失败 | 15 分钟后重试，每次翻倍，最多 4 小时；整个连败只通报一次 |
| 当天回合数到 `max_runs_per_day` | 条目留到次日，「定时」页显示原因 |
| 进程刚启动 | 首次检查推迟 2 分钟 |

v1 检查种类：

| kind | 数据来源 | 游标 / id | 外部 |
| --- | --- | --- | --- |
| `runs` | `.vortoone/runs/` 运行台账中已结束的运行 | 结束时间 + run id | 否 |
| `mail` | `plugins/mail` 未读、非群发邮件的发件人与主题 | UIDVALIDITY + UID | 是 |
| `calendar` | `plugins/calendar_ics` / `caldav` 未来 36 小时日程 | 开始时间 + 标题的哈希 | 是 |

`runs` 先上线，用内部数据跑通整套机制，再接两类外部来源。

### 4.3 结构化答案

模型只能回一个 JSON 对象：

```json
{"quiet": true}
{"items": [{"id": "<给定 id 之一>", "why": "一句话，不超过 40 字", "urgency": "now|today"}]}
```

校验：必须能解析；`id` 必须是本批给出的 id；`why` 截断到 40 字；多余字段丢弃。任何一项不满足即整次失败。

推送正文由代码拼：来源字段（发件人、主题、时间）取自检查结果，模型的 `why` 标为「助理判断」。
模型文字里的链接、按钮、指令一律不变成动作（与 `cron.py` 里「模型输出只出诊断、不触发处置」一致）。

### 4.4 心跳不改

心跳的检查单是自由文本（「看看 CI 是不是绿的」），代码判断不了有没有新东西；它已经有便宜模型、
activeHours 和静默。主人若想省，可以把具体条目改写成带 `checks` 的 cron 作业。

### 4.5 PR3：邮件分拣，与逐封提醒对照

提供「重要邮件」作业样例（默认不启用）。启用后与现有逐封新邮件提醒**双发对照一周**，比较漏报和打扰
次数，再由主人决定是否用分拣替代逐封提醒（`VORTOONE_MAIL_NOTIFY`）。这一步不自动切换。

## 5. 安全分析

- 检查走插件已有的凭据读取与撤销规则；撤销凭据后下一次检查失败并显示，不回退到旧数据。
- 外部条目进模型时带不可信边界，回合是污点态。v1 带检查的回合没有工具，污点不会让任何动作被放行，
  也没有出网通道可外传私人数据。
- 模型能影响的只有「选哪几个 id」和一句理由；推送对象恒为主人，正文由代码组装。
- 不写记忆：带检查的回合不经过记忆写入路径（污点回合本来也不进长期记忆）。
- 无人值守下写动作（如存邮件草稿）经确认门直接拒绝；本设计不绕过这一点。以后要「替你拟回复」，应变成
  等主人批准的提议卡，属于 ADR-012 阶段 B/C 的范围。
- 状态文件只存 id、哈希、时间和计数，不存邮件正文、主题或日程标题。

## 6. 状态存储

`cron_state.json` 增加保留键 `__checks__`（与已有 `__fails__` 同一写法）：

```json
{"__checks__": {"重要邮件": {"cursor": {"uidvalidity": 1, "uid": 4821},
                             "judged": ["1:4819", "1:4820"],
                             "checked_at": "2026-11-03T10:15:00+08:00",
                             "runs_today": {"date": "2026-11-03", "count": 3},
                             "backoff_until": null}}}
```

`judged` 最多保留 500 个，按先进先出淘汰。目标推进的指纹存 `watch.json`（§4.1）。

## 7. 测试（离线、断行为）

| 场景 | 断言 |
| --- | --- |
| 检查成功、没有新条目 | 模型替身未被调用；无通知；`checked_at` 更新；运行台账无新行 |
| 检查失败 | 模型未调用；游标不变；连败到阈值只通报一次 |
| 模型答案无法解析 / 含未给出的 id | 不推送；游标与 `judged` 不变；下次同一批重给 |
| 保存后、投递前中断 | 下次不重给；补发队列投递一次 |
| 外部条目 | 进模型的消息带不可信边界 |
| `checks` 与 `allow_web` 同时出现 | 加载作业时报错，作业不运行 |
| 不带 `checks` 的作业 | 与现有行为一致（现有 cron 测试全绿） |
| 目标指纹不变、未满 7 天 | 不调模型、不推送 |
| 目标卡或任务单状态变化 / 跨过到期桶 / 满 7 天 | 重新判断 |
| 当天回合数到上限 | 不调模型，条目保留 |
