# 多 bot 方案：第一轮对抗审核

审核对象：设计原稿 `033396f`，对应实现基线为 #676 的 `a2cfc7b`。本轮只修改设计与审核
记录，没有修改产品代码。发现的问题是设计准入缺口，不是已确认发生的生产越权事故。

结论：原稿 **request changes**。5 项 P1、2 项 P2；已将规范修订写入
[设计 v1.1](MULTI_BOT_DESIGN.md)，运行时实现与故障轨迹仍待完成。规范修订不等于审核项
已取得实现通过证明，不能据此开放完整 V1b 或自动接力。

方法：逐项构造反例，核对现有领域合同，运行两个仅临时文件的离线代码探针。
探针没有调用真实模型、机器人、业务网络 API 或运行中服务；未借“多角色一致同意”作为验收依据。
本轮未使用独立审核 Agent，也不声称做过第三方审核。

## R1 / P1：每张任务单的新 owner 会断开原根预算

**反例**：第一张研究单使用 owner A 建根，第二张“继续研究”单沿现有助理派活方式生成
owner B。若继承原根会被拒绝；若为跑通而创建新根，又获得新的额度。

现有证据：

- [assistant_dispatch.approve](../src/workflow/tasks/assistant_dispatch.py) 首次批准时按
  dispatch_id 设置新的 remote_session；这是当前开发派活的语义，不能原样当作研究链归属。
- [task_chain_budget.prepare / _root](../src/workflow/tasks/task_chain_budget.py) 要求前置/根与
  成员 owner_session 一致；[DispatchService.submit](../src/workflow/tasks/dispatch.py) 的任务
  身份也包含 owner。同一个请求字符串换 owner 不是原请求的重放。
- 离线探针：根 A 保存后，以 owner B 调用既有 prepare 继承该根，返回
  `任务链前置记录或归属无效`；以 B 新建根则被允许。仅验证合同与元数据，未执行任务。

**修订**：一个由用户确认的新 work，在一个 Project 内固定一个协调代理 owner 和 root。
继续、换角色、返工不新建 owner/root；缺失原 work 映射则暂停。新根/预算扩充必须作为明确
新操作展示，由宿主固定身份。远端还须核对该受范围约束的调用身份，session 字符串不是授权。

**关闭条件**：两个真实入口先后提出同一 work 的后续任务，仍消耗原根；改 owner、伪造 root、
删除关联、换角色和同一 request_id 重传均不能取得新额度。V1b 在此证明之前不下发。

## R2 / P1：本地取消与 Project 认领没有共同生效点

**反例**：General 已写取消并向用户说“已停止”，但 Project 未收到；先前在网络中的首次
提交随后到达，Project 查不到取消状态，创建并运行。只遍历当前已知任务取消也会漏掉它。

这是跨进程顺序的设计反例，不是实际取消 RPC 的执行结果。原稿写了“先保存停止代次”，
但没有指定谁保存、哪个提交是生效点、首次提交尚不存在时如何阻止它。

**修订**：Project 原任务记录是禁止后续认领的权威；与创建/预留/恢复/认领在同一领域事务
边界核对。General 先显示取消请求待确认，Project 持久提交后才显示禁止后续启动。对首次
提交的原 request_id 也要留下同记录内的取消 fence，迟到提交不能重建。已认领执行的停止
另记回执，不能推导远端已停止或供应商不再计费。

**关闭条件**：取消先到/提交先到、Project 断线、确认丢失、回答恢复与认领并发均跑轨迹；
Project 持久取消之后不再新认领。当前无此完整合同，V1b 保持门禁，不增加旁路取消库。

## R3 / P1：角色 revision 不等于实际执行快照

**反例**：批准角色 research 的 A 版，队列等待时修改 Project 的同名角色文件，仍写 tools=read，
但更换 prompt、model 或限制。旧请求指纹未变，实际装配却读取 B 版。

现有证据：

- [DispatchService.submit](../src/workflow/tasks/dispatch.py) 的幂等摘要覆盖提交参数，不覆盖
  实际角色文件和模型配置。[execute_dispatch](../src/agents/dispatch.py) 校验角色工具面，
  [delegation 的 _sub_for/build_subagent](../src/agents/delegation.py) 在执行装配时读取角色。
- 离线探针修改同名 read 角色的 system_prompt，再以原参数读取同一请求：角色定义已变，
  请求仍返回 replayed=True，原提交摘要不变。探针的 runner 不执行，不据此声称已经越权执行。

**修订**：授权同时绑定宿主撤销代次与 Project 不可变角色快照；摘要覆盖说明、工具限制、
路径范围、模型/供应商配置引用和执行限额。执行必须使用批准的快照，并持续核对撤销代次；
不能靠“重读后还是 read”或旧请求摘要替代。后续角色任务单独创建、沿原 root 消耗预算。

**关闭条件**：批准后/入队后/装配中修改角色或供应商，旧授权均不能执行新快照；相同角色名
不能覆盖此变化。此项属于 V1a 角色装配与 V1b 下发门禁。

## R4 / P1（条件路径）：只读 GET 仍可外传私有材料

**反例**：私有代码研究 bot 同时启用可由模型提供 URL/query 的 web 工具；它把读到的内部
内容放进公网查询。HTTP 没写服务器状态，但内容已经离开项目。污点只描述信任，不能撤回传输。

[build_web_tools](../src/agents/tools/web.py) 明确将 web_fetch/search 标为只读、外向工具。
原稿允许公开检索另行启用，却没有规定必须与私有项目上下文隔离。本轮没有发任何测试请求。

**修订**：V1 私有项目研究禁用公网工具。未来公开研究另建不带私有历史、文件能力或内部
产物的上下文，只接受用户审阅的公开问题，回流结果保留污点；模型/供应商选择也进快照。

**关闭条件**：工具面与上下文检查能证明私有任务无公网出口，公开任务拿不到私有材料。
这是可选公网路径的阻断；不据此否定现有纯离线只读研究路径。

## R5 / P1：重启和 A→B→A 会复活数值相同的旧授权

**反例**：旧回调使用 generation=1，重启后从 1 开始；或者绑定/角色删除后按旧名称与 revision
重建。只比较这些值，旧清理、旧批准和排队请求会看起来仍对应当前对象。

这是原稿 generation/配置 revision 定义不完整的推演。原稿已要求旧 finally 不移除新路由，
但没规定代次跨重启及撤销恢复时是否仍唯一，不能据这句话证明防重用。

**修订**：句柄身份使用随机 runtime_incarnation 加当前 generation；可执行授权另核对持久
撤销代次与 Project 保存的 root 授权代次。重建名称不复用已撤销授权。正常重启先核对存量
任务；完整有效且尚未认领的批准可以沿用，不重复确认或退款，已认领/未知动作不重放。
句柄换代不等于撤销全部业务授权。恢复备份先核对，不声称任意回滚可检测。

**关闭条件**：重启、迟到 finally、A→B→A、删后重建、恢复备份等轨迹不恢复已撤销/缺证明
批准；完整有效批准仍能恢复且不再问同一确认。Project 未确认撤销时 UI 显示待核对。
V1a 生命周期与 V1b 授权均需证明。

## R6 / P2：以 binding_id 去重会在重绑定后重做消息

**反例**：同一渠道账号的事件 E 已在 binding A 处理，删除绑定后建立 B，渠道重传 E。
原稿的 `(binding_id, type, event_id)` 得到不同输入身份，E 又能驱动一次模型回合。
这不证明原产品已重做，而是原稿定义本身容许的反例。

**修订**：去重身份来自渠道和已验证账号、必要的渠道会话范围、事件类型及原事件 ID，
不依赖可重建绑定、内部 conversation 或连接代次。原受理目标另行固定，不因重新绑定改投。
裁剪/损坏不能把已处理事件恢复成新事件；去重覆盖无法证明时暂停受理，不能只用聊天尾部。

**关闭条件**：跨账号同事件 ID 分开处理，同账号换密钥/重连/重绑定只受理原事件一次；
去重状态丢失/压缩时保持不重复准入。本项是 V1a 恢复验收要求，落盘布局仍需实现证明。

## R7 / P2：本地汇报成功、远端 ack 丢失后会重复汇报

**反例**：控制端已保存并展示任务结果，然后 Project acknowledge 超时并重启。Project
收件箱仍显示未处理；若只看远端 handled，再次生成同一结果的汇报、通知或模型请求。

[CompletionInbox](../src/workflow/tasks/handoffs.py) 用结果 revision 记录项目侧处理回执，
但与 General 的会话保存不在一个原子事务内。原稿“汇报成功后再确认”没有封闭这段窗口。

**修订**：在原会话中与正文一起持久 report_id，绑定 Project 持久身份、任务/结果版本和
原协调会话。恢复发现本地已提交汇报时只补远端 ack，不重新生成模型汇报或新通知身份；
通知仍受原策略约束，不声称网络回执丢失时恰好一次显示。

**关闭条件**：在本地保存后、通知后、远端 ack 前后分别中断，恢复不新增汇报模型回合或
同一正文；新结果 revision 仍能独立汇报。此项是 V1b 结果往返门禁。

## 离线证据与验证边界

本轮临时探针输出如下，全部来自真实领域函数与临时记录，runner 无执行行为：

```text
different_dispatch_owner: 任务链前置记录或归属无效
new_owner_new_root_allowed: True
role_definition_changed: True
submission_contract_unchanged: True replayed: True
```

其他反例为设计级事件顺序推演，没有伪装成已经跑过的产品测试或真机事故。审阅代码中
确认已有文件工具做仓库范围与敏感路径校验，因此没有把它报成已存在的任意路径读取漏洞；
角色策略需要更小范围时，仍须额外证明路径级限制，不能只依靠自然语言要求。

文档修订解决的是规范矛盾和缺失合同：实现状态仍为未实现，实际关闭需要以上轨迹逐项
通过。第一版应先完成角色装配和多入口的 A/B 切片；C/D 只有稳定 work/owner/root、角色快照、
Project 取消准入和回报补确认齐备后才开放。自动接力、完成唤醒、跨项目链与微信仍在后续。
修订没有新增任务库、API、自动评估角色，也未解冻 ADR-008 全部高级协作模块。
