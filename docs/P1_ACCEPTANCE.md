# P1 真机验收清单：常驻助理与 Codex 链路

`CURRENT_ARCHITECTURE.md` 把「真实链路稳定」列为 P1：常驻助理与 Codex 的状态、批准、补充、停止、通知和重连，都要精确对应到主机、会话和轮次；受理和完成要分开；超时和崩溃不能盲目重放。本清单是这一条的可重复验收步骤。离线测试证明不了这些，只能在真机上跑。

## 怎么跑

- **在哪跑**：用已安装的正式版，或 `cd desktop && npm run dev:app`。dev 版用单独的应用标识，可以和正式版同时开着，配置互不影响；它在钥匙串里另用一组 `.dev` 条目，没有常驻电脑的令牌，正好可以模拟「常驻电脑连不上」。
- **截图**：只截 App 窗口，不截整个屏幕。
- **怎么记录**：每个场景都记版本或提交、时间、结果（通过 / 失败 / 不适用）和证据，证据可以是截图、通知原文或台账记录。失败就开 issue 或 PR，并链接回本清单。
- **什么时候跑**：发版前跑 A、B；改到连接、恢复或 Codex 控制时，跑受影响的场景。

## 场景

### A. 冷启动：常驻电脑离线

1. 上次退出时停在助理模式，并且已登记常驻电脑。
2. 让常驻电脑连不上：断网、停掉服务，或者用 dev 版。
3. 启动 App。

**预期**：横幅提示常驻电脑暂时连不上，先用本机助理。本机通用工作区是已连接状态，主要聊天可以发消息。**不能**出现「本地引擎已经启动，但工作区连接失败」，右上角也不能停在「未启动」（这是 #600 修的问题）。

### B. 常驻电脑恢复上线

1. 在场景 A 的状态下，恢复常驻电脑。
2. 等后台自动重连，或手动点「重新连接」。

**预期**：重连到常驻电脑的主要聊天，和其它设备登记的是同一段对话。本机临时会话里的消息不丢。正在回复时不会自动切走。

### C. 运行中断网与重连

1. 连着常驻电脑时发一条需要多步才能完成的任务。
2. 任务进行中断开网络 30 秒，然后恢复。
3. 再断一次网，这次超过 1 分钟；断网期间在输入框发一条消息，然后恢复。

**预期**：连接状态如实显示断开、再恢复：断网后半分钟左右显示断开，不会一直停在「已连接」。任务在常驻电脑上继续跑。恢复后能看到断网期间的进度。不会重复发送同一条消息。断网期间发的消息要么送到，要么放回输入框并提示没确认送达，不会悄悄丢掉。断线后的自动重连只连回常驻电脑，不退回本机。

### D. Codex：批准一条建议

1. 在一个专门的测试目录里开一个 Codex 会话，在对话里让助理把它交接过来（要你确认）。其它会话不交接。
2. Codex 在这个会话里跑一轮，监管给出一条下一步建议。
3. 在 Desktop 或手机上批准它。

**预期**：没交接的会话只出现在进度汇报里，不会出现拟好的建议或叫停。卡片写明会话目录和 id 尾号。建议只发往产生它的那一个会话和那一轮。显示的是「已受理」，不是「已完成」。如果那一轮已经结束、会话已经关闭或已有新一轮，草稿标成过期，不再发送。

### E. Codex：补充指令与停止

1. Codex 运行中，在 Desktop 上给当前这一轮发一条补充指令。
2. 然后请求停止这一轮。

**预期**：补充指令带上当前轮次的身份。停止只针对原来那一轮；如果已经开了新一轮，旧的停止请求会被拒绝，不会停错。回执只表示受理，是否真的停下要看后续状态。

### F. 写请求结果不明

1. Codex 控制请求发出后，在收到回执前断网，或者杀掉常驻服务。
2. 恢复连接。

**预期**：

- 界面明确显示「结果无法确认」，不会自动重发，也不会当作成功或失败。
- 断网期间观察员留着回执，恢复后补报，动作落到实际结果（已受理或失败）。
- 观察员进程被杀、回执丢了时，认领 10 分钟后动作标成「结果无法确认」，并推一条提醒。之后这个会话的监管照常拟下一步，不再一直卡在「还有动作没办完」。

### G. 通知送达

1. 在 Mac 前和离开 Mac 两种情况下，分别让 Codex 失败一轮。
2. 再让它卡住，等它给出需要拿主意的事项。

**预期**：人在 Mac 前时，纯进度只记进台账，不推送；失败、卡住、需要拿主意、待批动作照常推送。通知原文里不出现内部编号，同一件事只说一次。
