## 0. 要解决的问题

主人定的原则是：不分模式，由安全监管决定每个动作放行到什么程度。专员体系上线后，监管给出的结果几乎全是「问主人」：

- 专员在后台固定按最严档位运行，除了读以外的每个动作都生成一张审批卡。
- 开通一个常设专员要分别批准岗位、专员、部门、每条例行工作，四到五次逐项主人确认。
- 自动审核全部关闭。
- 服务重启后，进行中的专员任务和例行工作都停下等主人逐个核对。
- 主要聊天里，自动检索记忆会让回合带上污点，污点回合里一切免确认授权失效。

审批太多的后果不只是烦。主人会习惯性点「批准」，审批就失去了意义，这比少问几次更危险。本文的目标是：**把主人的注意力留给真正需要判断的动作，其余的用确定的规则放行，并保证事后能核对、能撤销。**

本文不放宽的东西见第 2 节。

## 2. 不放宽的东西

以下规则本文一条都不动。任何实现如果发现需要动它们，停下来问主人。

1. **对外发送、替主人在浏览器里操作、不可撤回的动作**：任何档位、任何岗位都要主人逐次确认。
2. **污点**：回合读过外部内容后，一切免确认授权失效。A1、A2 的放行在污点下同样失效，变回审批卡。
3. **无人可问时默认拒绝**：无人值守会话问不到人就拒绝，不静默放行。
4. **永远留给主人的动作**（`STAFF_DESIGN.md` 5.5）：付款、删除主人的数据、以主人名义对外发送、改账号与安全设置。专员只能准备到最后一步。
5. **登记本身**：新建或扩大岗位、专员、部门、例行工作的权限，始终由主人批准；需 Desktop 核对的仍由携带主人令牌的 owner 写入路由确认。A3 减少的是次数，不是核对的内容。
6. **验收**：「要验收」的任务只有主人能点通过（评审文档 8.12）。
7. **写文件和执行命令**：专员的这两类动作仍然由主人在 Desktop 逐次确认。已批准的开发任务在自己的一次性副本里写文件、跑固定测试是现有例外，范围不变。
8. **存邮件草稿**：每次确认（主人此前已定，A8 维持）。

## 3. 设计

### 3.1 岗位级的常设放行（A1）

现状：`build_staff_member` 给每个专员装配的确认门固定是最严档位，所以事项专员每改一条待办都要一张卡。

改动：

- 岗位的 `grants` 增加一个字段 `standing`，取值是 `own_data`、`draft` 的子集，默认空。它必须是 `operations` 的子集。
- 登记或修改这个字段属于扩大权限：必须走提议，必须由主人在 Desktop 明确确认，提议卡上单独列出「以下动作将不再逐次询问」。
- 装配专员时，`standing` 里的类别在确认门里视为已预先授权。实现上只给确认门加一个「本会话额外免确认的类别集合」，取值范围在内核里写死为这两类，传别的类别直接报错。
- 放行的每个动作照常写审计记录，来源标为「岗位常设放行」，并且：
  - `own_data` 类必须有登记的撤销（这是该类别已有的定义），动作记入操作日志；
  - `draft` 类只限不离开本机的草稿。声明了「每次确认」的工具（存邮件草稿）不受 `standing` 影响，照常出卡。
- 以下情况 `standing` 不生效，变回审批卡：回合带污点；岗位或专员版本与任务派发时不一致；任务来自团队且该专员担任协调人。

结果：事项专员、健康与习惯专员这类只动主人自己数据的岗位，日常工作不再出卡；主人在晚报里看到它们做了什么，每条可以撤销。

### 3.2 任务内同类放行（A2）

现状：主要聊天里已经有「本轮同类动作不再问」（`scoped_approval.py`），限 `own_data`、`draft` 两类、10 次、10 分钟。专员任务没有对应机制。

改动：

- 审批卡的批准多一个选项：「这件任务里同类动作不再问」。只有卡片的类别是 `own_data` 或 `draft`、卡片不带污点、工具没有声明「每次确认」时才显示。
- 选了之后，在该任务的当前轮次上记录一条放行：类别、剩余次数（从 9 开始）、岗位与专员版本。后续同类动作直接执行并消耗次数。
- 失效条件：次数用完；任务返工进入下一轮；岗位或专员版本变化；回合带污点；任务暂停后恢复；服务重启。
- 这条放行存在原任务记录里，不新建文件。它不是权限，不能被别的任务或别的专员使用。
- 高风险类别（写、执行）的卡片没有这个选项。

### 3.3 一张开通单（A3）

现状：开通日程专员要依次批准岗位、专员、单人部门、一条例行工作，共四次逐项确认；邮件专员有两条例行工作，共五次。

改动：

- 新增一种提议 `bundle`，内容是一组有先后依赖的登记：最多 1 个岗位、1 个专员、1 个部门、4 条例行工作。
- 开通单的摘要覆盖全部条目的完整内容。主人在 Desktop 上看到的是一页：岗位能做什么、能看什么、是否联网、每条例行工作的时间和时区、`standing` 放行了什么。核对后由主人普通确认一次。
- 写入是分步的，沿用现有的「先保存决定，再写登记」。中断后只能完成同一张开通单或取消，不能只留下一半生效（例如有专员没有岗位）。
- 开通单里任何一条不满足登记规则（5.2 的组合规则、5.5 的保留动作），整张单拒绝。
- 开通单只用于**新建**。修改已有登记仍然逐项提议，避免把一次扩权藏在一堆不相关的改动里。
- `staff_plan` 现在输出「下一步建议」，改为输出一张完整的开通单草稿。它仍然只读，不写登记。

### 3.4 手机上批普通卡片（A4）

现状：专员审批卡的通知写的是「到 Desktop 核对」。主人不在电脑前时，任务就停着，24 小时后过期。

改动：

- 卡片的级别沿用已有划分：读、自己的事项、草稿是普通级别，签名的手机写入可批准；其余是仅 Desktop 级别，使用普通主人确认。
- 普通级别的卡片出现在手机的待处理里，展示完整动作内容和污点标记，用现有的签名确认卡批准或拒绝。服务端核对的内容与 Desktop 相同：任务、轮次、卡片编号、内容摘要、nonce 和运行实例；手机写入另沿用已有设备签名与防重放机制，不能仅凭未签名请求或 IM 回话批准。L6 实现前不开放这一路专员写入。
- 高级别卡片在手机上只读，显示「需要在电脑上批准」。
- 手机不能选 3.2 的「同类不再问」。那个选项只在 Desktop 上提供，因为它实际上是一次小范围授权。

这一条不减少审批次数，减少的是任务被卡住的时间。

### 3.5 自动审核暂不打开（A5）

评审文档 8.9 建议把自动审核做成确认门后面的通用环节。我建议现在不做，理由：

- 3.1 和 3.2 用确定的规则覆盖了最常见的低风险动作，行为可预测、可测试。
- 自动审核是让一个模型判断另一个模型的动作。它适合「规则写不清楚」的情况，但我们还没有数据说明剩下的卡片里有多少属于这种情况。
- 它每次审核都要花一次模型调用，而且判断错了主人不容易发现。

保留现有的两处自动审核（目标的下一步、给登记项目派活）不动。3.8 的统计跑满一个月后，如果「主人批准率接近 100% 且耗时短」的卡片仍然很多，再按那时的数据设计。

### 3.6 重启后的恢复（A6）

现状：服务重启时，所有排队、执行中、等审批的专员任务一律标为中断，例行工作标为「等主人核对」。部署一次，主人就要手动恢复一批。

改动：

- 区分两种任务：
  - **一步都没执行**（状态是排队，没有任何工具调用记录，没有模型调用用量）：重启后自动重新排队，派发前重新核对岗位、专员、部门、额度。对应的例行工作不标错误。
  - **已经开始执行**（执行中、等审批、有任何工具或模型调用记录）：维持现状，等主人核对，不自动重跑。
- 「一步都没执行」必须由持久记录证明，不能靠内存状态推断。证明不了就按已开始处理。
- Desktop 的核对页增加批量操作：列出重启中断的任务，每条显示已执行到哪一步、可能已经生效的动作，主人可以多选后一次「返工」或「放弃」。

### 3.7 记忆检索与污点（A7）

现状：主要聊天每个回合开头会自动检索记忆。检索工具被声明为「来源不可信」，所以检索结果一进上下文，回合就带污点，之后这个回合里所有免确认授权都失效。S9 的实施记录还指出空结果也会触发。这意味着在默认设置下，主要聊天几乎每个回合都是污点回合，「读操作免确认」这个档位形同虚设，也因此才有了 Desktop 上直接提议岗位的表单。

这一条对审批负担的影响可能是全文最大的，但它动的是污点规则，必须谨慎。

改动：

- 记忆条目已经带出处。按出处分两类：
  - **主人确认过的**：主人亲口说的、主人在界面上确认保存的。检索出这类条目不让回合带污点。
  - **其它**：模型提议且未经确认的、从外部内容提炼的、隔离区里的。检索出任何一条，回合照常带污点。
- 一次检索的结果里只要有一条属于「其它」，整个回合按污点处理。不做「部分干净」。
- 空结果不带污点。
- 判定依据是写入时记录的出处，不是内容。出处缺失或认不出的条目按「其它」处理。
- 写入策略（`memory/write_policy.py`）已经禁止污点回合的指令性文本进长期记忆。实现时要核对：污点回合里产生的记忆，是否有任何路径能被标成「主人确认过的」。有的话先堵上，再做这一条。

实现前先用测试复现现状（含空结果的情况），确认问题确实存在。

### 3.8 审批统计（A9）

现状：每次确认都有审计记录，但没有汇总。我们不知道主人一天批多少次、哪一类最多、批准率多少。

改动：

- 从已有的审计记录和任务记录投影出一张每日统计，不新增数据来源：
  - 按来源（主要聊天、哪个专员、哪条例行工作）、操作类别、是否污点分组；
  - 每组的次数、批准数、拒绝数、过期数、从出卡到决定的中位时间；
  - 自动放行的次数，按放行依据分（档位、本轮同类、任务内同类、岗位常设、任务副本、保护性操作）。
- Desktop「团队与权限」里加一个只读的统计页，默认看最近 7 天。
- 只存数字和类别，不存动作正文。

这一步先做。它上线一周后，用它的数字核对本文的假设：如果某一类卡片占了大多数而本文没有覆盖，先改设计再往下做。

### 3.9 去掉 plan / build

评审文档 5.3 已经决定去掉，前置条件（工具显式声明类别、确认收到运行层一处）已由 #828 完成。它和本文的关系：

- plan 模式下「写之前先问要不要切换」排在确认门前面，同一个动作可能问两次。去掉后只剩确认门一处。
- 专员现在按岗位权限在 plan / build 之间选。去掉后专员只按岗位的 `operations` 和 `standing` 判定。

落地要求沿用评审文档 5.3 的五条，不在这里重复。它排在本文各步之后（第 6 节），因为它改动面最大，而且不依赖本文的任何一步。

## 4. 主人会看到的变化

以「事项专员每天早上整理待办」为例，假设主人给这个岗位打开了 `own_data` 常设放行：

| | 现在 | 本文之后 |
| --- | --- | --- |
| 开通 | 逐项主人确认四次 | 核对一页，普通主人确认一次 |
| 每天改 5 条待办 | 5 张审批卡，任务每次停下等 | 不出卡；晚报列出 5 条改动，每条可撤销 |
| 它读了一封外部邮件后想改待办 | 出卡 | 仍然出卡（污点） |
| 它想存一封回信草稿 | 出卡，只能在电脑上批 | 出卡，可以在手机上批 |
| 它想发出这封信 | 做不到，只能准备好 | 不变 |
| 服务重启时它还在排队 | 停下等主人恢复 | 自动重新排队 |
| 服务重启时它做到一半 | 停下等主人核对 | 不变，但可以批量处理 |

## 5. 数据与接口

不新增数据库、任务类型或执行池。

- `staff/roles.json`：岗位 `grants` 增加 `standing`（字符串列表）。旧记录没有这个字段时按空处理，不改写旧文件。
- 原任务记录：`collaboration` 里增加当前轮次的任务内放行（类别、剩余次数、版本）。
- 提议记录：增加 `bundle` 类型。
- 确认门：增加「本会话额外免确认的类别」参数，取值在内核里限定为 `own_data`、`draft`。
- 接口（都有前端调用方，需同步路由基线）：
  - 读取审批统计；
  - 批量处理重启中断的任务；
  - 手机端读取和决定普通级别的专员审批卡（走手机网关现有的签名写入）。
- 审计记录的 `approval_scope` 增加两个取值：岗位常设放行、任务内同类放行。

### L1 实施记录（2026-11-12，PR #858）

- 已用实际工具运行和自动召回复现：空结果、只含主人确认来源的记忆都会因静态声明加污点。现在召回按实际交付条目的持久来源判定；混入一条外部或未知来源即整次加污点，空结果不新增污点，也不清除已有污点。
- 来源写入原记忆元数据，不新增数据库。主人来源要求真实人工确认收据及干净的原始来源；CLI 预授权、模型传入的字段不能充当人工确认。提案批准从原提案列保留来源与污点，批准外部材料不改变它的出处，隔离记录仍不可批准。
- 旧 `confirmed=true` 曾包含预授权写入，无法仅凭它证明人工确认；旧记录照常可读，来源证据不足时按未知处理，不回写旧库、不自动提升。完整的新来源字段由可信写入服务生成，调用方自带元数据不能覆盖。
- 结果来源通过宿主的类型化文本向运行层追加污点，不提供清除静态外部来源的能力。并发结果向父回合汇合，外部结果保留历史标记；自动背景资料不改变冻结的系统前缀。IM 的入口污点及既有外部历史照旧生效。
- 后台提炼采用原回复保存的本轮污点快照，不能用下一回合的状态覆盖旧回合；没有快照的旧记录保守按未知来源处理。第 2 节八项权限边界不变，没有新增接口或授权类别。对应 issue：#844。

### L2 实施记录（2026-11-12，PR #859）

- 创建专员首轮任务时，在原协作任务中持久记录初始快照摘要；领取任务先使证明失效再执行。重启只重排仍与证明完全一致的原任务，缺证明的旧记录、有日志、模型或工具记录、审批、用量、后续轮次均不自动重放。派发重新核对岗位、专员、部门、例行工作绑定和现有额度。
- 对应例行工作保留原任务、原时段和去重认领，不另建任务；不把可靠的未开始队列记为错误。已经开始的任务仍等主人核对，主助理或协调人不能自行返工中断的专员任务。
- Desktop「团队与权限」增加中断任务核对，可看进度、旧审批及可能生效的动作，多选后一次普通主人确认返工或放弃。服务端先核对全组选中任务的摘要和运行实例，再逐条写审计及决定，逐条报告失败，不自动重试；旧审批不复活。达到原有返工轮次上限、登记变化或小组阶段不允许时照常拒绝。
- 沿用原任务台账、执行池与额度等待，不新增数据库、任务类型或调度器，不改漏跑、总时限或确认门。对应 issue：#845。

### L3 实施记录（2026-11-12，PR #860）

- `staff_plan` 返回完整的新建开通单草稿；工具结果保留完整提议输入，避免重复快照挤占结果长度。`staff_propose` 可保存 `bundle` 待批记录，仍走原提议工具确认路径，不授予权限。主人在 Desktop 核对各岗位的动作、来源、联网、项目限制及每条例行工作的时间和时区后，一次批准整单登记。
- 整单最多新建一个岗位、一个专员、一个部门和四条例行工作，全部用现有校验器预演；已有登记只能引用，不能在开通单里修改。引用的岗位、成员、笔记和排期也纳入完整摘要，变化后不能套用旧决定。日历只读、草稿逐次确认、部门资料边界及禁用动作不变；本步尚未开放 L4 的常设放行。

- 沿用主人令牌写入路由、摘要、nonce、轮次、运行实例及审计先行；未增加 API 路由或批准通道，旧单项提议仍可用。对应 issue：#846。

## 7. 测试

契约测试断言行为，不查源码字符串；全部离线、确定。

1. **不放宽项**：对外发送、交互、不可撤回三类，在岗位打开了 `standing`、任务内放行有效、最高档位、无头自动批准这些条件的任意组合下，仍然等到主人确认才执行。
2. **`standing` 的取值**：登记时写入这两类以外的类别被拒绝；写入不在 `operations` 里的类别被拒绝；不经 owner 写入路由的主人确认不能生效。
3. **污点**：`standing` 和任务内放行在污点回合里都不生效，动作变成审批卡。
4. **每次确认的工具**：存邮件草稿在 `standing` 含 `draft` 时仍然出卡。
5. **可撤销**：`standing` 放行的 `own_data` 动作都出现在操作日志里并能撤销；没有登记撤销的工具不能被这样放行。
6. **任务内放行的边界**：次数用完、返工、版本变化、重启、污点后各自失效；不能跨任务、跨专员使用；手机端的批准不能产生这种放行。
7. **开通单**：摘要覆盖全部条目；任何一条违反登记规则则整张拒绝；写入中断后不存在只生效一半的状态；不能用于修改已有登记。
8. **重启恢复**：有任何执行记录的任务不会被自动重排；自动重排的任务在派发前重新核对权限和额度。
9. **记忆与污点**：只含主人确认条目的检索结果不带污点；混入一条其它出处的条目即带污点；出处缺失按其它处理；污点回合产生的记忆不能获得「主人确认过」的出处。
10. **三端一致**：以上判定在 Desktop、手机、IM、无头 CLI 入口下结果一致，差别只来自能力档案。同步 `tests/unit/test_three_end_contract.py`。
11. **统计**：统计只含数字和类别；与审计记录逐条对得上。
