# 框架问题清单（2026-11-09）

基线：main `b7a0a555`（合并 #822 之后）。范围：任务小组的交付与成员交流、主 Agent 循环，会话、存储、接口、配置等其余框架部分，个人 Agent 方向与现有代码的差距（第 5 节）、还欠缺的方向（第 6 节）、后续阶段（第 7 节），以及其它方向的问题与优化办法（第 8 节）。

方法：读代码为主，另有一次离线装配测量（第 4.1 节）。**没有实跑复现**，也没有在常驻主机上核对数据量。每条都标了依据：

- **已核对**：代码里能直接看到这个行为。
- **推断**：由代码推出的后果，需要复现后才能当成事实。

这份清单只列问题和建议顺序，不代表已修复。要动手修的，先看第 10 节的规则和批次。上一轮检查见 `FRAMEWORK_RELIABILITY_REVIEW.md`（2026-10-30）；其中「开发目标保存失败仍可能提交执行」一项现已改为 `save_required`，这里不再列。

## 总体判断

主循环、确认门、污点和工具运行层没有需要推翻的结构问题。问题集中在三处：

1. 任务小组的交付没有终点：主人验收通过后，系统不做任何事。
2. 成员之间的信息只靠协调人转贴，超长部分被悄悄截掉。
3. 「一回合前后要做的事」在三个入口各写了一遍。安全规则已经收到内核一处，这部分还没有。

## 1. 交付

### 1.1 验收通过后没有后续动作（P1，已核对）

位置：`src/web/routers/teams.py::apply_decision`、`src/workflow/tasks/team.py::TeamService.decide`。

通过只把根任务状态改成 `done`。开发成员的成果是常驻主机上的本地分支，不推送、不开 PR（`src/agents/team_delivery.py::describe` 的文案也这样写）。主人点了通过，代码仍留在那台机器上，要另外手工取回。

建议：验收通过后给一个明确的后续动作。推送是对外动作，建议做成主人点的按钮（推分支并开 PR），不自动执行。

### 1.2 三条交付路径终点不同（P2，已核对）

- 隔离开发流水线：落 `vorto/*` 分支并开 PR。
- 任务小组：停在本地分支。
- 助理派活：绑定提交的审查快照（`src/workflow/tasks/assistant_delivery.py`）。

同样叫「交付」，主人拿到的东西不一样，界面和通知也只能各说各的。

建议：定一份共同的交付记录（分支、提交、验证结果、是否已推送、PR 链接），三条路径都填它。

### 1.3 验收证据是协调人自己写的文字（P1，已核对）

位置：`TeamService.submit`。

只检查每条验收标准有一段非空文字，不核对这段文字是否对应某条成员结果、某个分支或某次验证记录。助理派活那条路径的证据是绑定提交的（`delivery_evidence` 会核对分支和提交），两者标准不一致。

建议：证据项必须引用一条已接受的子任务；开发类标准必须引用交付记录里的分支和验证结果，由代码填事实，协调人只写说明。

### 1.4 待验收、等主人的状态只提醒一次（P2，已核对）

位置：`src/scheduling/task_notices.py::_key`。

同一任务同一状态只推一次，没有再提醒，也没有期限。错过那一条通知，任务就一直挂着。

建议：超过一定时间未处理的「待验收」「等你」并进每日早报，或按天再提醒一次，次数有上限。

### 1.5 成员交回的内容最多保存 8000 字符（P2，已核对）

位置：`src/workflow/tasks/collaboration.py::_message`（`submitted` 上限 8000，带 `truncated` 标记）。

长报告被截断，返工时成员拿到的是截断稿。结果也没有存成文件或制品，主人只能在群聊视图里看。

建议：成员的完整结果落成文件，任务记录里只存路径和摘要。

## 2. Agent 之间的交流

### 2.1 转贴内容超长时被悄悄截掉（P1，已核对）

位置：`src/agents/team_coordinator.py::cross_review`、`TeamService.assign`（`_MAX_INSTRUCTION = 16000`）。

成员看不到彼此，交叉审查靠协调人把「原要求 + 结果 + 最多 12000 字符的改动」拼进要求里，总长超过 16000 字符的部分直接丢掉，不提示。审查员可能审的是缺了尾巴的改动而不知情，并给出「没有问题」。

建议：超长时不派发，改为报错让协调人收窄范围；或者把材料存成文件，给审查员只读工具去读。

### 2.2 审查员没有工具，只有 2 步（P2，已核对）

位置：`src/workflow/tasks/team.py::ROLES`、`src/agents/team_members.py`。

审查员读不了仓库，只能看贴给它的片段。审代码改动时看不到上下文和调用方。

建议：给审查员只读的文件工具，范围限定在这一轮的交付分支。

### 2.3 成员每轮都是全新会话（P3，已核对）

返工靠把上一轮稿子贴回去，受 1.5 的 8000 字符限制，最多 3 轮。1.5 解决后这条的影响会小很多。

### 2.4 后台回合遇到模型错误不重试（P2，已核对）

位置：`src/llm/client.py`（`max_retries` 默认 0）。

对话里不自动重试是合理的，主人可以手动重发。但成员和协调人是后台回合，一次 502 整轮就失败；连续 3 次失败小组转「等你」。

建议：只对后台回合开启有上限的重试（成员是只读或在一次性副本里改，重发的代价可控）。

### 2.5 重启可能让进行中的小组不再被叫醒（P2，推断）

位置：`src/scheduling/team_runner.py::recover`、`_drive`。

「回合结束后没人在跑就补叫一次」只存在内存里。小组处于进行中、没有排队任务、也没有未读结果时，重启后 `recover` 只调用 `kick`，不叫醒协调人。常驻主机部署频繁，这个空档可能踩到。需要复现确认。

建议：`recover` 对这种状态补一次叫醒，连续无进展仍由 `end_wake` 转「等你」。

## 3. 主 Agent 循环

### 3.1 两套协议写在同一个函数里（P3，已核对）

位置：`src/agents/agent_loop.py::_run_turn_body`。

原生 function-calling 和提示式协议各占约 80 行，收尾、纠偏、预算处理几乎重复。文件共 2113 行，构造函数约 30 个参数。改一处行为要改两遍，容易漏。

建议：把「拿到一步模型输出 → 归一成（正文，调用列表）」抽成一个函数，循环主体只留一份。

### 3.2 只附在当次请求的内容让前缀缓存每回合断一次（P2，推断）

位置：`agent_loop.py::_request_messages`。

日期提示和自动召回的记忆附在本回合的用户消息上，但不写进历史。下一回合，同一条消息的内容就少了这一段，上游前缀缓存从这里开始失效，上一回合的工具结果要按全价重算。无目录会话（常驻助理）每回合都会遇到。需要用上游的缓存命中数据确认影响大小。

建议：把这类内容作为单独一条消息追加在本回合末尾，或者写进历史保持不变。

### 3.3 模型窗口未知时历史预算只有 8000 token（P2，已核对默认值）

位置：`agent_loop.py::_base_context_budget`。

窗口未知的模型按保守默认 8000 token 留历史。协调人读几条成员结果就会触发压缩。需要核对常驻主机上实际使用的模型是否已配置窗口。

## 4. 其余框架部分

### 4.1 每次请求的固定开销偏大（P2，已测量）

离线装配一个项目会话（`build_session(kind="web", workspace_scope="project")`）：56 个工具，工具声明约 2.1 万字符，系统提示约 1.27 万字符。通用会话是 29 个工具、约 1.0 万加 0.89 万字符。常驻助理还会再加助理专用工具，这次没有量到。

固定部分已经明显大于默认的 8000 token 历史预算。工具多也会让模型更容易选错工具。

建议：按会话用途分组装配，低频工具（任务依赖、模型评估、流水线续跑等）按需加入。

### 4.2 一回合前后的处理在三个入口各写了一遍（P1，已核对）

位置：`src/web/routers/realtime.py`（1677 行）、`src/im/bridge.py`（1591 行）、`src/gateway/app_turns.py`。

会话存盘、回合摘要、记忆提议、对话记录这些步骤，Desktop、IM、手机各有一份实现。`realtime.py` 是 Web 路由文件，却承担了建会话、排队、存盘、摘要的逻辑。项目约定里写的是 `gateway/` 管会话装配，这部分实际在 `web/` 里。

后果和早先的安全规则一样：加一端或改一步，就要记得改三处。

建议：在 `gateway/` 里提供一个「执行一回合」的函数，包住回合前后的全部步骤，三个入口只传各自的输出回调。

### 4.3 任务台账没有清理，多处全量读取（P2，已核对代码，未核对数据量）

位置：`src/workflow/tasks/tasks.py::TaskLedger.list`。

每个任务一个 JSON 文件，没有保留期限。`list()` 会读取并解析目录里的全部文件，调用它的地方有十多处，包括小组列表、决定列表、工作日志。任务越积越多，这些接口会越来越慢。需要到常驻主机上数一下现有文件数。

建议：终态任务超过保留期后归档到单独目录；常用查询按状态或所有者建一个小索引。

### 4.4 任务锁只在单进程内有效（P3，已核对）

位置：`tasks.py::TASK_STATE_LOCK`（`threading.RLock`）。

目前各服务用各自的状态目录，没有冲突。如果以后两个进程指向同一个状态目录，读改写会互相覆盖。建议在文档里写明这个前提，或者换成文件锁。

### 4.5 没人使用的旧代码（P3，已核对）

- `src/models/router.py`（452 行）：仓库内没有任何导入。
- `src/core/monitoring.py`（333 行）：只有 `HealthChecker` 和三个检查函数被 `web/routers/ops.py` 用到，指标采集部分没人用。
- `src/tools/registry.py`、`executor.py`、`permission.py`：只经 `ToolManager` 给 MCP 接入用，是与 `agents/tool.py`、`agents/permissions.py` 并行的第二套工具和权限定义。
- 已冻结的任务协作高级功能（ADR-008 列出的十个模块）合计约 3180 行，仍在装配和测试里。

建议：前两项直接删；第四项定一个删除日期。第三项已在后续核对（见 8.1）：MCP 调用确实经过内核确认门，没有缺口，但「这个工具算读还是写」是由 `src/tools/permission.py` 里另一套按名字匹配的规则判断的，应并入 5.7 的统一操作类别。

### 4.6 环境变量太多（P3，已核对）

代码里读取的 `VORTOONE_*` 变量有 131 个。多数没有集中的清单和默认值说明，行为取决于哪台机器的哪个配置片段设了什么。

建议：集中到一个配置模块，启动时打印生效值（不含密钥），`vc doctor` 报告未识别的变量。

### 4.7 吞掉异常的地方多（P3，已核对数量）

`src/` 里有 473 处 `except Exception`，其中 85 处直接 `pass`。多数是有意的旁路（通知、界面提示失败不影响主流程），但出问题时没有任何记录。

建议：旁路失败至少记一条 debug 日志；Desktop 已有错误报告通道（#820），引擎侧的这类失败可以计数上报。

### 4.8 Desktop 两个超大文件（P3，已核对）

`desktop/src/App.tsx` 3597 行、141 处 hook 调用；`desktop/src-tauri/src/lib.rs` 4677 行。样式已经整理过，状态管理还集中在一个组件里。

建议：按功能把状态拆进独立的 hook 或 store，先从助理面板和更新流程开始。

### 4.9 接口数量（P3，已核对）

路由基线里有 282 条接口。2026-10 清理过一批无人调用的接口，之后又增加了不少。建议再跑一次「前端是否调用」的核对。

### 4.10 对话的压缩纪要不落盘，重启后只剩最近 40 条（P1，已核对）

位置：`src/gateway/session_store.py`（`_MAX_HISTORY = 40`、`_MAX_TRANSCRIPT = 200`）、`src/agents/agent_loop.py`（`_summary`、`_task_anchor`）、`src/workflow/tasks/team.py::save_history`。

对话超出预算时，主循环把老的部分压成一段纪要，放在 Agent 对象的 `_summary` 里，并把那些消息从历史里移走。存盘时只保存历史的最后 40 条，**纪要和任务锚点都没有保存**，仓库里也没有任何地方读回它们。

后果：

- **主要聊天**是一段不结束的对话。主机每重启一次（部署很频繁），之前压出来的纪要就丢了，助理只记得最近 40 条消息。一个用了较多工具的回合就可能占掉二十多条。更早的内容只能靠长期记忆和对话检索找回。
- **小组协调人**更严重：每次被叫醒都新建 Agent、只读回历史。上一次醒来时如果发生过压缩，那段纪要在回合结束时就被丢弃。长时间运行的小组里，协调人会忘掉早先做过的决定（任务目标和验收标准在系统提示里，不受影响）。
- 界面上的对话记录只保留最近 200 条。

建议：纪要和锚点随会话一起存盘、一起读回；协调人的历史文件同样带上纪要。给「重启后继续同一段对话」补一条测试。

### 4.11 公网手机入口没有限频（P2，已核对）

位置：`src/web/mobile_server.py`、`src/web/auth.py`。

手机网关是整套系统里唯一直接面向公网的服务。请求签名、防重放、配对审批都做得很完整，但应用层没有按来源限制请求频率，也没有失败次数锁定；全仓只有运维心跳一处有限流。目前依赖前面的反向代理只放行手机路径。

建议：在网关里加按来源的限频和失败退避，不依赖用户把反向代理配对。对自建主机的用户（5.5），这一条应当是默认行为。具体细节不写在公开文档里。

验证与修复（2026-11-10）：离线行为测试 `tests/unit/test_mobile_server.py::test_gateway_limits_requests_per_source`
及 `test_gateway_backs_off_after_authentication_failures` 复现了缺少限频与失败退避的行为。
手机网关现默认按来源限制请求，并对认证失败退避；受限请求返回 429 和等待提示，来源状态有容量与过期回收边界。
使用虚拟时钟验证正常请求、来源隔离、窗口恢复及退避上限；未进行线上或真机验证。阈值已由主人确认，具体参数不在公开文档展开。

### 4.12 Desktop 和手机连主机走两条不同的网络路径（P2，已核对）

位置：`desktop/src-tauri/src/lib.rs::validate_remote_server_url`、`deploy/Caddyfile.mobile*`。

Desktop 连主机要求内网地址或 HTTPS，完整的助理接口按文档不应暴露到公网，所以实际要靠内网或虚拟专用网。手机走的是另一条：公网域名、证书、只放行手机路径的反向代理。两条路各有一套配置和排障方法。

对主人自己已经跑通。对自建主机的用户，这意味着要同时搭两套网络。

建议：给一条默认路线并写进安装流程。例如两端都走同一个虚拟专用网（配置最少，不需要域名和证书），公网 HTTPS 作为可选的进阶配置。

### 4.13 CI 不覆盖 Rust 和 Swift，类型检查范围窄（P3，已核对）

- Desktop 的 Rust 层约 1.28 万行，`cargo test` 只在本地门禁里跑，GitHub CI 的 desktop 任务只跑 tsc 和 vitest。
- iOS 约 5800 行 Swift，有单元测试和界面测试目录，但 CI 不构建也不运行。
- mypy 只圈了 `llm/` 和几个安全模块。`tool_runtime.py`、`tool.py`、任务小组相关模块不在范围内，而它们正是 5.7 要改的地方。

建议：CI 加一个 `cargo test --lib`（有缓存后约一分钟）；mypy 范围先扩到工具运行层，再做 5.7。

### 4.14 IM 桥是一个 1591 行的类（P3，已核对）

位置：`src/im/bridge.py::IMBridge`（约 60 个方法）。

会话装配、命令解析、回合执行、存盘、摘要、文件收发都在这一个类里。没有发现具体缺陷；它是 4.2「回合前后处理写了三遍」里的一份。4.2 做完后这个类会自然变小，不建议单独重构。

### 4.15 账号服务（另一个私有仓库，P2，已核对代码）

账号服务负责注册登录、设备授权、会员与购买，以及 Desktop 的错误报告、反馈和使用计数。代码量小（约 2450 行）、有测试和 CI、部署脚本会核对线上版本。整体是这套系统里比较整齐的一块。问题在它和其它部分的关系上：

1. **错误报告、反馈、使用计数的接收端还没上线。** Desktop 一侧（#820～#822）已经合并，账号服务一侧的改动还在待合并的分支上。在它部署之前，Desktop 发版后这三项都不会真正工作。
2. **表结构变更靠手写的补列清单。** 目前只有加列，够用。telemetry 加了三张新表之后，下一次要改列类型或拆表时就需要正式的迁移工具，建议在那之前引入。
3. **与模型中转服务共用同一台机器和同一个数据库实例**（独立的库和账号）。一台机器出问题，登录、会员、模型调用同时受影响。备份是否覆盖账号库没有核对。
4. **限频组件出故障时的行为需要复核。** 具体细节不写在公开文档里。
5. **Desktop 对账号服务的依赖没有写清楚。** 不登录也能用自己的模型密钥；登录后会员、模型密钥下发、手机同账号连接都经过它。账号服务不可用时各功能分别怎样降级，没有一页说明，也没有对应的测试。
6. **常驻主机与账号的绑定还没上线。** `ACCOUNT_RUNTIME_BRIDGE.md` 写明「本地联调通过，未部署」。对自建主机的用户（5.5），「买了会员之后主机怎么拿到模型服务」这一步目前靠脚本手工绑定。

建议：先部署 telemetry 接收端再发下一版 Desktop；把账号库纳入已有的备份和恢复演练；写一页「账号服务不可用时」的降级说明并补测试；主机与账号的绑定并进 5.5 的安装流程。

### 4.16 Desktop 前端：状态集中在一个 3400 行的函数里（P2，已核对）

位置：`desktop/src/App.tsx`。这一条替代 4.8 里关于 `App.tsx` 的简述。

- `App()` 一个函数从第 195 行到文件末尾，里面有 83 个 `useState`、26 个 `useEffect`、34 个 `useRef`。任何一个状态变化都会让整个函数重新执行。已经抽出了 29 个 hook，但会话、连接、弹窗、面板开合这些核心状态仍在根组件里。
- 没有状态库，跨组件的数据靠一层层传参数。加一个功能通常要改 `App.tsx`，多人同时改就容易冲突。
- **工作台的面板还在。** ADR-015 决定撤掉工作台，但文件、Git 审查、目标、预览、运行与终端这些面板仍被 `App.tsx` 引用，代码编辑器和终端两个大依赖（Monaco、xterm）也还在安装包里。这是 5.1 在前端的表现。
- **小组页面靠定时轮询。** 小组群聊和小组交付每 8 秒请求一次接口，而主对话是靠事件推送的。两种更新方式并存，小组里的新消息最多要晚 8 秒，窗口开着就一直在请求。
- Rust 层的 `lib.rs` 4677 行，情况类似，已经拆出了十几个模块，剩下的仍然很大。

建议：

1. 先删：撤掉工作台面板和两个大依赖（ADR-015 的 W1），`App.tsx` 会直接变小，安装包也会变小。
2. 再拆：按「连接与会话」「对话」「助理面板」「设置与更新」分成几个独立的状态模块，根组件只做布局。
3. 小组页面改为订阅事件，与主对话一致；等 5.10 的队列落地后，小组事件本来就要经过它。

## 5. 个人 Agent 方向

方向本身（ADR-011：个人 Agent 做底座、能力以插件接入、主人终端与团队通道分开）没有问题：它和实际使用一致，安全内核也不用动。问题在于代码还没有长成这个方向描述的样子。

### 5.1 决定下得比落地快（P1，已核对）

11 月 1 日到 8 日写了 ADR-011 到 ADR-018 八个决定，同期合并了约 150 个 PR。ADR-011 自己写的是「每阶段稳定两周再开下一阶段」，实际没有做到。

后果是三代产品叠在一起：编码框架（隔离开发流水线、`vc agent`、项目运行时）、研发工作助手（工作台、目标、任务协作）、个人 Agent（主要聊天、任务小组、手机）。ADR-015 的 W2（删工作台接口）、W3（退役流水线）还没做，ADR-008 冻结的模块也还在。第 1.2 节的三条交付路径、第 4.1 节的 56 个工具、第 4.9 节的 282 条接口都是这件事的表现。

建议：先把 ADR-015 的 W2、W3 做完再开新方向。每撤掉一层，后面每一项改动都更便宜。

### 5.2 「底座」在代码里还不是一层（P2，已核对）

ADR-011 列的底座是：身份与信任、唯一一本事项台账、个人模型、主动循环、投递路由、运行时。对照代码：

- 事项不止一本：开发目标（`workbench/goals.py`）、个人目标（`workbench/personal_goals.py`）、后台任务、任务小组、定时作业、Codex 观察各有各的记录，「今日工作」是读它们拼出来的。
- 个人目标、常驻项目登记放在 `workflow/workbench/` 里，而工作台是要撤掉的那一层。
- 主动循环仍是 `scheduling/` 下的几个大模块（`assistant_watch` 927 行、`codex_watch` 1177 行、`codex_supervisor` 698 行、`codex_observer` 603 行），ADR-011 背景里指出的「功能焊在一起」没有变。
- 插件目前是 `src/plugins/` 下四个文件（日历两个、邮件、Notion），还没有 ADR 里说的最小 SDK。

建议：不需要大重构。先做两件小事：把属于底座的模块搬出 `workbench/`；定一份「事项」的共同只读投影，让动态、早报、手机都读它，而不是各自拼。

### 5.3 plan / build 模式已经名存实亡，但整套机制还在（P2，已核对；已决定去掉）

位置：`src/agents/agent_loop.py`、`src/agents/tool_runtime.py`、各入口。

plan / build 是为写代码设计的：plan 只读摸底，要动手时先问一句「切到 build 吗」。现在各入口实际这样用：

| 入口 | 模式 | 依据 |
| --- | --- | --- |
| Desktop | 固定 build | `desktop/src/App.tsx` 里 `const mode = "build"` |
| 手机 | 固定 build | `src/gateway/app_turns.py` |
| 任务小组协调人 | 固定 build | `src/agents/team_coordinator.py` |
| Telegram / 钉钉 | 默认 plan，可用 `/mode` 切 | `src/im/bridge.py` |
| 无头 CLI | 默认 plan | `src/cli.py` |
| 小组成员 | plan | `src/agents/team_members.py` |

两个主人终端都已经绕过了 plan。带来的问题：

1. **同一段主要聊天，从不同入口进来行为不同。** 在 Telegram 里让助理记一件事，会先被问「切到 build 吗」；在 Desktop 和手机上不会。
2. **一个开关管了三件不相干的事。** 模式同时决定能不能写、单段能跑几步（plan 默认 6 步，build 16 步并自动续跑）、系统提示怎么写。只读地多查几步资料，在 plan 下也会撞上步数上限，然后弹出「是否切到 build」，这个问题对只读任务没有意义。
3. **权限其实已经有更细的一层。** 确认门、能力档案和操作类别（自己的事项、草稿、对外发送、不可逆）已经在内核里逐个工具判定。plan 的「写之前问一句」排在确认门前面（`tool_runtime.py` 先判模式再进工具），有人值守时可能同一个动作问两次。
4. **遗留物仍在每次请求里。** `request_build` 工具、模式说明文字都还装配在会话里；系统提示随模式变化，切换一次前缀缓存就断一次。

**决定（主人 2026-11-09）：不再有 plan / build 模式。放行到什么程度，由安全监管判定，不由模式开关判定。**

「安全监管」指内核里已有的这几层：确认门（`agents/gate.py`）、操作类别与信任档位（`agents/trust.py`）、能力档案（`agents/capabilities.py`）、污点（`agents/taint.py`）、本轮范围授权（`agents/scoped_approval.py`），以及后台提议的自动审核（`scheduling/auto_review.py`）。它们按「这个动作是什么、谁发起的、上下文干不干净」逐个判定，比「整个回合只读 / 可写」精确。

落地时要做的事：

1. **先补缺口，再拆模式。** plan 模式过去顺带挡住了所有非只读工具。拆之前逐个核对：每个会改东西的工具都经过确认门，并且登记了操作类别。没接的先接上。这一步要有契约测试（遍历全部工具，非只读的必须有类别和确认路径），不靠人工清点。
2. **各入口行为统一。** Telegram、钉钉、无头 CLI 与 Desktop、手机用同一套判定；入口之间的差别只来自能力档案（例如 IM 入口按不可信处理、手机用 `owner_device`），不来自模式。
3. **步数预算单独设。** 原来 plan 6 步、build 16 步加自动续跑，改为按会话用途定一个预算，与权限无关。
4. **「动手前先看计划」改成监管的一种结果。** 写代码这类大改动仍然需要先给计划再动手，但由监管按动作的类别和范围要求（例如首次写文件、派开发成员前出一张确认卡），不再是用户手动切换的开关。
5. **删除遗留物。** `request_build` 工具、模式升级回调、按模式分支的系统提示、IM 的 `/mode` 命令、CLI 的 `--mode` 参数、协议里的 `mode` 字段。系统提示不再随模式变化，前缀缓存也更稳。
6. **无人值守不变。** 定时和心跳回合继续 fail-closed，不因为去掉模式而放宽。

验收：`tests/unit/test_three_end_contract.py` 的能力矩阵覆盖去掉模式后的全部入口；同一个动作从 Desktop、手机、Telegram 发起，得到相同的放行或确认结果（能力档案不同的除外，并在矩阵里写明）。

### 5.4 记忆是词法检索（P2，已核对）

位置：`src/memory/`（`lexical.py`、`active_recall.py`）。

个人 Agent 的核心价值是「记得你」。目前召回靠词面匹配，`ASSISTANT_MUSE_GAP.md` 自己记录了上限（「做财务」对不上「什么工作」）。加上 3.3 的 8000 token 历史预算，长期使用的体验上限在这里。

建议：在现有写入策略不变的前提下，给召回加一层向量检索，用已有的召回评测集对比。

补充核对（`active_recall.py`、`assistant_profile.py`）：

- 记忆是一张平铺的事实列表，没有「人、项目、偏好、约定」这样的结构，也没有时效（某条事实什么时候起不再成立）。
- 每回合最多召回 3 条，候选只取按重要度和时间排前 512 条。记忆超过这个数之后，排在后面的永远不会被想起。
- 新记忆一律先成为提议，等主人逐条确认。安全上是对的，但提议积压后主人不会去点，记忆就不再增长。
- 没有整理：重复、过时、互相矛盾的条目只在确认时按用词提示一次，之后不会再合并或淘汰。

方向：记忆从「事实列表」变成「个人模型」——按对象归档、带时效、定期由助理起草合并和淘汰（仍由主人批准，但一次批一批）。低风险的类别（主人亲口说的偏好）可以按 5.3 的思路由监管直接放行，不必逐条确认。

### 5.5 部署形态：一台 24 小时在线的主机（主人 2026-11-09 定）

决定：产品以一台常开的主机为前提。主人自己用现有的常驻电脑；其他人使用时，建议他们自己准备一台 24 小时在线的虚拟机或云主机。不做托管。

这个形态可行，而且和现有设计一致：数据留在用户自己的机器上，安全内核不用改，Desktop 和手机本来就是这台主机的客户端。它也避开了托管带来的成本和数据责任。

但现在只有主人这一套环境能跑起来。要让别人照着装，还缺下面这些（均已核对）：

1. **没有一步到位的安装。** 现在要手工克隆仓库、建虚拟环境、配四个 systemd 用户服务（项目服务、常驻助理、项目运行时、手机网关），环境变量散在各个配置片段里（见 4.6）。`docs/OPS.md` 的 Linux 部分只有几行，指向一个示例单元文件。没有安装脚本，也没有容器镜像。
2. **手机接入门槛高。** 手机要经公网 HTTPS 连到这台主机，需要域名、证书、反向代理和动态域名（`deploy/` 下有 Caddy、证书、DDNS 的单元文件）。云主机有固定公网地址会简单一些，但证书和域名仍要用户自己办。
3. **主机没有自己的升级路径。** Desktop 现在能自动更新，主机要靠 SSH 上去拉代码、重启四个服务。而 Desktop 与引擎的协议版本要求完全相等（`desktop/src/gateway.ts` 里版本不一致就拒绝），Desktop 自动升级后，主机没跟上就连不上。
4. **云主机上的密钥更敏感。** 主机上放着模型密钥、邮箱和日历凭据、机器人令牌，目前模型配置是明文（`CURRENT_ARCHITECTURE.md` 已记为未完成项）。放在家里的机器上风险可控，放到公网云主机上需要先把这一条补上。
5. **诊断只对主人友好。** 出问题时靠读日志和 `vc doctor`。别人的主机出了问题，目前只有 Desktop 的错误报告（#820）能回传，主机一侧没有。
6. **每个用户还要自备模型服务。** 这一点已有账号服务和模型配置界面承接，问题不大，但要写进安装步骤。

建议顺序：

1. 一个安装命令：装依赖、生成令牌、写好服务单元、打印 Desktop 要填的地址和令牌。优先做成容器镜像加一个 compose 文件，云主机和家用机器都能用。
2. 主机自升级：`vc update`（拉取指定版本、重启、自检、失败回滚），并让 Desktop 在版本不一致时提示「请升级主机」而不是连接失败；协议改为允许相邻版本兼容。
3. 手机接入给一条默认路线（云主机：域名加自动证书），其它方式放进高级文档。
4. 明文模型配置迁到受保护的存储，再推荐云主机。
5. 把上面写成一页「搭建常驻主机」的文档，找一台全新的云主机按文档走一遍作为验收。

在这些做完之前，对外的说法应当是：Desktop 单机可用；常驻主机是进阶功能，目前需要一定的运维能力。

### 5.6 没有衡量方向是否走对的数据（P3，已核对）

`CURRENT_ARCHITECTURE.md` 定的价值标准是减少遗漏、重复解释、盯进度和追问结果。目前只有派活成绩和刚加的匿名使用计数（#822），没有对应这四项的记录。ADR-011 的依据是「每天在用的是常驻助理和 Codex 监管」，这类判断以后应该能用数据回答。

建议：使用计数上线后，每两周看一次各入口的实际使用，再决定下一个阶段做什么。

### 5.7 安全监管要成为唯一判定点，还差一层声明（P1，已核对）

位置：`src/agents/tool.py`、`src/agents/trust.py`、各工具的处理函数。

5.3 决定由安全监管判定放行程度。现在的监管有一个结构上的缺口：**一个工具属于哪类操作、要不要过确认门，写在它自己的处理函数里，不在工具声明上。**

- `Tool` 声明上只有 `read_only`、`outward`、`untrusted_source` 等几个布尔值，没有操作类别。
- `read_only` 的默认值是 `True`。新工具忘了写，就被当成只读。（确认门那边的默认是按最重的算，方向相反。）
- 离线装配两类会话共 72 个工具，27 个声明为会写。声明为只读的 45 个里，有派子 Agent 的（`task`、`research_parallel`）、改任务状态的（`task_review`、`task_acknowledge`）、给主人发文件的（`send_file` 等）。抽查 `send_file`，它在处理函数里确实过了确认门，所以这不是漏洞；但说明 `read_only` 的实际含义是「plan 模式下不拦」，不是「没有副作用」。
- 因为类别在处理函数里，内核无法在不执行工具的情况下回答「这个工具会被怎样判定」，也就写不出 5.3 要求的那条契约测试。

建议（这是去掉 plan / build 的前置工作）：

1. `Tool` 声明上增加必填的操作类别（读、自己的数据、草稿、写、执行、对外发送、交互、不可逆），不给默认值。
2. 由 `tool_runtime` 在调用处理函数之前统一过确认门。处理函数里不再各自调用；需要按参数细分的（例如只读命令和写命令）提供一个分类函数。
3. 契约测试遍历全部工具：每个都有类别；非读类的必须走统一入口。
4. 这样做完，「放行程度」才真正只有一处在判，权限页面也能直接列出每个工具会被怎样对待。

### 5.8 主动循环按来源轮询，没有统一的触发模型（P2，已核对）

位置：`src/scheduling/assistant_watch.py`、`patrols.py`、`goal_advancer.py`、`codex_watch.py`。

「主动」目前是若干个定时巡视：每分钟刷新派活单状态、早晚报、目标推进、Codex 观察、日程和邮件提醒。每个来源各自轮询、各自判断要不要推送、各自记状态。其中分量最重的仍是派活单和 Codex，也就是上一代「研发工作助手」的内容。

后果：新增一种触发（某个页面变了、某封邮件到了、某个期限快到了）要新写一个巡视；「主人现在在不在、该不该打扰」这类判断没法共用（ADR-011 的背景里已经指出过）。

方向：定一个小的触发器合同（来源、事件、去重键、紧急程度），巡视只负责产出事件；要不要打扰、走哪个终端、是否并进早报，由一处投递路由决定。这也是 ADR-011 里「投递路由」那一项，至今没有开始。

### 5.9 定时任务：安全设计合适，作为个人助理的功能不够（P2，已核对）

位置：`src/scheduling/cron.py`、`scheduler.py`、`src/gateway/session.py`、`src/agents/tools/cron.py`、`src/web/routers/cron.py`。

**做得对、应当保留的部分：**

- 每次在全新的隔离会话里跑，不读写主要聊天。
- 无人值守默认拒绝一切需要确认的操作；默认不给联网，要联网必须逐个作业由主人授权。
- 定时回合里没有排班工具，作业不能给自己再排作业。
- 联网的作业看不到记忆和私人资料，不联网的作业才能看本机状态（对应 ADR-012 的两种档案）。
- 失败会留记录并通知，连续失败会升级提醒。

**不合适的部分：**

1. **作业一个接一个跑，会卡住整个调度。** 调度循环每分钟醒一次，到点的作业在循环里逐个等待执行。提示类作业没有总时长上限（`timeout` 字段只对命令类作业生效），默认也没有 token 预算。一个作业跑十分钟，这十分钟里其它作业、心跳、安静时段汇总都不动。
2. **五段式排期错过那一分钟就不补。** `at HH:MM` 和 `every` 会在之后补跑；五段式（如 `0 9 * * 1`）只在当前这一分钟匹配时才跑。主机恰好在重启，或者上一条说的循环被占住，这次就被跳过，没有任何记录。主机部署频繁，这个情况会实际发生。
3. **没有时区。** 排期按主机的本地时间算。主人的主机和人在同一时区，没有问题；别人用云主机时，主机多半是协调世界时，「每天 9 点」会差出几个小时。
4. **没有一次性的定时。** 三种排期都是重复的。「明天下午三点提醒我」只能走个人目标的单次提醒，那是另一套机制。
5. **能做的事很窄。** 联网作业只能搜索和读网页；不联网作业只能读本机的动态、任务单和定时事项。两者都用不了日历、邮件、Notion 这些插件，也不能产出待批的动作。ADR-012 说定时任务的动作「一律变审批卡」，现在的实现是直接拒绝，没有审批卡这条路。所以「每天早上看我的日程和未读邮件，有要回的列给我」这类最典型的个人助理定时任务，目前做不了，只能靠写死在 `assistant_watch` 里的早晚报。
6. **管理不完整。** 工具和接口能新建、启停、改内容、手动跑、看历史，但不能删除，也不能改排期时间。工具说明里写的是「改已有作业请人工编辑 cron.yaml」。对主人可以接受，对自建主机的用户意味着要登录主机改文件。
7. **配置是靠改文本维护的 YAML。** `cron.py` 里约三百行是按行插入、替换 YAML 文本并回读校验。能用，但每加一个可改字段就要再写一段文本编辑。
8. **「定时」其实有好几套。** `cron.yaml` 作业、写死的早晚报、巡视（`patrols.py`）、目标推进、个人目标提醒、心跳，各有各的排期方式和状态记录。主人曾因为早报在两套里各有一份而收到重复内容。这与 5.8 是同一个问题。
9. **结果只是一条通知。** 正文截到 800 字推给主人，不进主要聊天。主人想接着问「第二条展开说说」，助理要先去翻通知记录。

**方向：**

- 近期（可靠性）：作业并发执行并设总时长上限；五段式排期记录上次应跑时间，错过后补跑一次；作业带时区，默认取主人设置的时区。
- 中期（能力）：给定时回合一个「只读私人上下文加只读插件」的档案，动作一律生成审批卡而不是拒绝；支持一次性定时；补齐删除和改时间。
- 长期（结构）：把早晚报、巡视、提醒收到同一个触发器模型里（5.8），`cron.yaml` 改为结构化存储，定时任务的结果作为一条带来源标记的消息进入主要聊天。

### 5.10 用消息队列的机制统一后台工作（主人 2026-11-10 提出，建议采用机制、不引入中间件）

主人的问题：定时任务、触发、通知这些，能不能做成类似 RabbitMQ 的机制。

**判断：机制合适，RabbitMQ 这个软件本身不合适。**

消息队列解决的正是前面几节反复出现的问题：

| 队列的能力 | 对应现在的问题 |
| --- | --- |
| 生产和消费分开 | 调度循环自己等作业跑完，被一个作业卡住（5.9 第 1 条） |
| 消息先落盘，消费完才确认 | 五段式排期错过就丢（5.9 第 2 条）；小组的补叫醒只在内存里，重启就没了（2.5） |
| 失败重试、超过次数进死信 | 后台回合遇到一次模型错误整轮失败（2.4）；通知没送达靠各模块自己补发 |
| 多个消费者、各自限并发 | 小组成员、定时作业、派活单各有各的执行池和上限 |
| 按主题路由 | 每个来源自己决定推不推、推到哪（5.8） |

现在仓库里已经有好几个各自实现的「小队列」：通知的未送达队列和安静时段暂存（`scheduling/notices.py`）、后台任务池加台账（`workflow/tasks/tasks.py`）、对话的输入排队（`gateway/session_actor.py`）、IM 入站回执（`gateway/im_input_store.py`）、会话事件流（`gateway/session_event_stream.py`）、小组调度的待处理事件（`scheduling/team_runner.py`，只在内存）。它们各自解决了落盘、去重、重试里的一部分，做法都不一样。

**不建议直接装 RabbitMQ（或 Redis、Kafka）的原因：**

- 5.5 已定用户自备主机。多一个要安装、升级、备份、监控的服务，安装难度和出故障的地方都会增加。
- 规模对不上。这是一个人的助理，一天几百到几千条事件，单进程就能处理。
- 状态会分成两处。任务台账、会话都在本机文件和 SQLite 里，队列放到另一个服务后，备份和迁移（6.4）要同时保证两边一致。
- 安全内核按「单主机、本机状态」设计，多一个网络服务就多一个要鉴权和加固的入口。

**建议的做法：用已有的 SQLite 做一个进程内的持久队列，语义照着消息队列来。**

1. 一张事件表：主题、内容、去重键、可见时间、尝试次数、状态（待处理、处理中、完成、死信）。
2. 生产者只管写入：定时到点、成员交回结果、邮件到了、主人留言，都是往表里放一条。到点的定时任务就是一条「可见时间在将来」的消息，一次性定时（5.9 第 4 条）不需要另做。
3. 消费者按主题领取，领取时标记处理中并带租约；处理完确认；进程崩溃后租约过期，消息重新可见。
4. 失败按退避重试，超过次数进死信并通知主人。死信数量显示在主机健康页面（6.3）。
5. 每个主题单独设并发上限，花费总闸（6.1）也在领取这一步判断。
6. 投递路由（要不要打扰、走哪个终端、是否并进早报）作为「通知」这个主题的唯一消费者。

**必须保持的边界：**

- 队列只负责「这件事要有人处理」，不负责「能不能做」。每条消息被消费时，仍然按它的来源重新过确认门和能力档案；消息里不能带「已授权」这样的字段。
- 消息内容如果来自外部（网页、邮件、成员结果），入队时就带上出处标记，消费时照常算污点。
- 已有的执行台账不搬进队列。队列里放的是「去处理任务某某」的指针，任务状态仍以台账为准。
- 重试只用于没有副作用或者能确认没生效的步骤。「是否已生效不确定」的消息不自动重发，转给主人核对（与 `EXECUTION_RECOVERY.md` 的规则一致）。

**落地顺序（每步单独可用）：**

1. 队列本身加通知主题：把通知的未送达队列和安静时段暂存迁上来。行为不变，风险最小，先验证机制。
2. 定时作业：到点只入队，由独立的消费者并发执行。5.9 的卡住、漏跑、一次性定时一起解决。
3. 小组：成员交回和补叫醒改为消息，2.5 的重启问题随之消失。
4. 早晚报、巡视、提醒改为生产者，完成 5.8 的触发器模型。

以后如果真的需要多台主机或多个进程，这张表的接口可以换成真正的消息中间件，上层不用改。

## 6. 还欠缺的方向

前五节是「已有的东西哪里有问题」。这一节是「还没有、但这个产品需要的东西」。按对个人 Agent 的重要程度排列。

### 6.1 花费有提醒，但没有总闸（P1，已核对；2026-11-10 更正）

更正：这一条最初写的是「没有上限，也没有提醒」。后来核对 `src/llm/usage_ledger.py`，提醒是有的，原说法不准确。

已有的：

- 每天按来源（对话、早晚报、定时任务、Codex 判断、自动审核等）累计调用次数和 token，保留 60 天。
- 早报附一行「昨天用了多少」。
- 当天用量超过 200 万 token 且达到前 7 天日均的 3 倍时，巡视会提醒主人一次，并指出用得最多的来源。

仍然缺的：

1. **只提醒，不会停。** 没有「超过多少就暂停后台回合」的硬上限。提醒发出后如果主人没看到，失控的任务会继续跑。`src/llm/hard_budget.py` 只接在单次只读检查和少数任务路径上。
2. **小组和成员的用量没有单独标来源。** 标了来源的只有早晚报、定时任务、目标推进、任务复盘、Codex 判断、自动审核、对话摘要。任务小组的协调人和成员没有标，会全部记在默认的「对话」名下。小组不设额度（主人 2026-11-04 定），所以最可能失控的恰好是这一块，而提醒里会把它说成「对话用得最多」。
3. **外部执行框架的用量不在账上（推断）。** OpenCode 等外部框架自己调用模型，不经过本仓库的模型客户端，这本台账记不到。
4. **记的是 token，不是钱。** 不同模型单价不同，token 数不能直接对应花费。
5. **阈值是写死的。** 200 万和 3 倍在代码里，主人不能在设置里改。

建议：小组、成员、专员各自标来源（之后按部门汇总，见 9.6）；加一个主人可设的每日硬上限，到了就暂停后台回合并通知，对话不受影响；阈值进设置页面；外部框架的用量至少记调用次数和时长。

### 6.2 质量没有持续评测（P2，部分核对）

`evals/` 下有助理评测的场景、评分和基线，但发版流程（`release:verify`）里不包含它，也没有记录显示它定期在跑。改系统提示、换模型、去掉 plan / build 这类改动，目前只能靠真机用几天来感觉好坏。

建议：定一小组固定场景（记事、查日程、派小组、返工、拒绝注入），每次发版前跑一遍并和上一次对比。

### 6.3 主机一侧没有可观测性（P2，已核对）

Desktop 有了错误报告（#820）和使用计数（#822）。主机一侧出错只写本机日志，后台回合失败、通知没送达、小组卡住，都要登录上去看。`src/core/monitoring.py` 里的指标采集没人用（见 4.5）。

建议：主机提供一个「健康」页面，Desktop 设置里能看到：各后台循环上次成功时间、近 24 小时失败次数、未送达通知数、台账大小。主机的错误报告复用 Desktop 的上报通道，同样默认开、可关。

### 6.4 备份和迁移没有闭环（P2，按现有文档）

加密备份脚本和定时单元已有，`CURRENT_ARCHITECTURE.md` 记录异机存放位置和定时任务尚未启用。另外没有「换一台主机」的步骤：记忆、目标、会话、配对的手机钥匙怎样搬到新机器。个人 Agent 的数据是越用越值钱的，丢一次就前功尽弃。

建议：启用每日异机备份并做一次恢复演练；写一条 `vc migrate`（或文档步骤），在新主机上从备份恢复并重新配对。

### 6.5 能做的事还窄（P2，已核对）

插件只有日历、邮件、Notion 三类，其中写入只有新建日程和存邮件草稿。ADR-012 的阶段 C（主动想法、目标细化、上手引导、记忆导入）和阶段 D（凭据、连接、资料库、语音）大多还没开始。现在的助理更像「会盯进度、会派活的提醒工具」，离「替你办事」还有距离。

建议：不追求插件数量。选两三件主人每周都在做的事（例如改期日程、整理某类邮件、定期汇总某个来源），把它们从头到尾做通，包括失败和撤销。

### 6.6 新用户上手没有路径（P2，已核对）

第一次打开 App，要自己配模型、自己搭主机、自己配对手机。没有引导告诉用户助理现在能做什么、还缺哪一步。记忆是空的，也没有导入入口。这一条与 5.5 的安装是同一件事的两半。

### 6.7 平台只有 macOS 和 iPhone（方向问题）

Desktop 只打 macOS 包，手机只有 iOS，浏览器对话台已经退役。主机在 Linux 上。主人自己用没有问题；给别人用时，Windows 和 Android 用户完全进不来。

这不一定要现在做，但要有一个明确说法：近期只支持 macOS 加 iPhone，还是给主机保留一个轻量的网页入口作为兜底。

### 6.8 对外的自我描述还停在上一代（P3，已核对）

- `desktop/src-tauri/tauri.conf.json`：类别是 `DeveloperTool`，描述是「Local-first agent development workspace」。
- `CLAUDE.md` 开头仍把项目描述为「AI 编码 agent 框架」。
- `docs/` 下有 95 个文件、约 1.9 万行，没有一页是「现在这个产品是什么、怎么装、怎么用」的唯一入口；README 已经改成个人 Agent 的说法，和上面几处不一致。

建议：随 5.1 的清理一起，把历史文档移到 `docs/archive/`，保留一份当前说明。

### 6.9 只有一个主人（记录前提，不建议现在做）

接口令牌是单用户的管理员凭据，记忆、目标、会话都按一个主人设计。这是有意的。记在这里，是因为如果以后要支持家庭成员或小团队，这是要重新设计的地方，而不是加个字段能解决的。

## 7. 后续方向（建议的阶段）

把前面各节按先后排成四个阶段。每个阶段有一句话的目标和判断是否完成的标准。

**阶段一：收口。目标是只剩一代产品。**

- 做完 ADR-015 的 W1（前端面板，4.16）、W2、W3，删掉冻结模块和无人使用的代码（5.1、4.5）。
- 工具声明加操作类别、确认门收到运行层一处，然后去掉 plan / build（5.7、5.3）。
- 一回合前后的处理收到一处（4.2）；三条交付路径共用一份交付记录，验收通过后有明确动作（1.1～1.3）。
- 完成标准：工具数、接口数、环境变量数明显下降；同一动作在三个入口结果一致。

**阶段二：可托付。目标是敢让它自己跑一周不看。**

- 本机持久队列，先迁通知和定时作业（5.10 第 1、2 步）。
- 验收改为必须主人确认（8.12）；删除类与对外发送类工具补上正确的操作类别（8.14）。
- 花费硬上限与按来源记账（6.1）；审计日志轮转（8.13）；后台回合重试、重启补叫醒（2.4、2.5）；待处理事项定期提醒（1.4）；压缩纪要落盘（4.10）；定时作业并发、限时、补跑、时区（5.9 近期）。
- 部署账号服务的接收端、账号库纳入备份（4.15）。
- 发版前评测（6.2）；主机健康页面与错误上报（6.3）；备份启用并演练恢复（6.4）。
- 完成标准：连续一周没有需要登录主机才能发现的问题。

**阶段三：可安装。目标是别人能在一台新主机上装起来。**

- 容器镜像与一条安装命令；主机自升级与版本兼容；手机接入的默认路线；明文配置迁走（5.5）。
- Windows 的「只连主机」版 Desktop（9.7）；主人时区（8.15）。
- 两端统一的默认网络路线、公网入口限频（4.12、4.11）。
- 上手引导与记忆导入（6.6）；统一对外描述和文档入口（6.8）。
- 完成标准：一个没接触过项目的人，按文档在全新云主机上装好并连上手机，全程不需要问人。

**阶段四：更像个人 Agent。目标是它替你办成事，而不只是提醒你。**

- 记忆升级为个人模型（5.4）；触发器合同与投递路由（5.8）；定时任务能读私人上下文和插件、动作变审批卡（5.9 中期）。
- 选两三件每周都在做的事，从头到尾做通（6.5）。
- 完成标准：用使用计数（5.6）看，每周由助理主动发起并被主人采纳的事项数在增长。

顺序的理由：阶段一让后面每项改动变便宜；阶段二是给别人用之前必须有的底线；阶段三、四可以按主人更看重「给别人用」还是「自己用得更好」来调换。

## 8. 其它方向的问题与优化办法

### 8.1 MCP 工具：过了确认门，但分类是另一套规则（P2，已核对）

位置：`src/agents/mcp_tools.py`、`src/tools/executor.py`、`src/tools/permission.py`。

第三方能力只走 MCP（ADR-011）。核对结果：MCP 工具执行前会进入内核确认门（`executor.py` 里调用 `agents/gate`），返回内容一律按外部内容打污点，只读连接器只放行标了只读的工具。安全上没有发现缺口。

问题是分类：一个 MCP 工具算读、写还是执行，由 `permission.py` 里一套按工具名和类别匹配的默认规则加配置文件决定，与内核的操作类别（5.7）是两套。去掉 plan / build 之后，MCP 写工具的放行程度完全取决于这套规则判得准不准。

优化：做 5.7 时把 MCP 工具也映射到同一组操作类别（没有声明的按最重的算），第二套规则只保留「额外禁止」的用途。

### 8.2 模型服务是单点，没有备用（P2，已核对）

位置：`src/llm/providers.py`、`src/llm/client.py`。

所有回合都依赖配置的那一个模型端点。按角色选模型靠一个环境变量；端点不可用时没有自动换到备用端点，默认也不重试（2.4）。主机 24 小时在跑，模型服务一出问题，对话、小组、定时、早晚报同时停，而且各自单独报错。

优化：

- 配置里允许给每个角色写一个备用端点；连接失败或连续几次 5xx 后切到备用，并通知主人一次。
- 模型服务整体不可用时，由一处统一判定并暂停后台回合（配合 5.10 的队列，消息留着等恢复），而不是每个回合各自失败、各自通知。
- 角色到模型的对应关系放进设置页面，不用改环境变量。

### 8.3 Codex 监管是主人专用的，仍然焊在主程序里（P2，已核对）

位置：`src/scheduling/codex_watch.py`、`codex_supervisor.py`、`codex_observer.py`、`codex_goal.py`（合计约 2650 行），以及 `agents/backends/codex.py`。

这部分服务于「主人在 Mac 上用 Codex 写代码，助理在旁边看进度、提建议」。这是主人每天在用的功能，但它对别的用户没有意义，除非他们也用 Codex。它占了主动循环里最大的一块，早晚报、动态、审批卡里都有它的分支。之前关闭的几个 Codex 监管修复里指出的缺陷也还在。

ADR-011 已经定了「执行者以插件接入」，这一块还没有按插件的方式拆出来。

优化：把 Codex 监管做成一个可以整体关闭的插件：不启用时，主程序里不出现它的工具、巡视和界面。先做「可以关」，再考虑搬代码。这同时为以后接别的执行者（例如别的编码工具）留出位置。

### 8.4 系统提示靠补丁累积（P3，已核对）

位置：`src/agents/agent_loop.py::SYSTEM_TEMPLATE` 及各段附加说明。

基础提示里大部分是「不要……」式的规则，从注释能看出每一条都对应一次真机事故。这些规则是有价值的，但它们按时间堆在一起，与写代码有关的（分支、测试、验证命令）和与个人助理有关的混在同一段；模式说明也在里面。项目会话的系统提示有 1.27 万字符（4.1）。

没有评测（6.2）的情况下，没人敢删其中任何一条，所以只会越来越长。

优化：把提示分成三层：所有会话共用的原则、按会话用途的说明（助理、写代码、成员）、按已装配工具附加的说明。去掉 plan / build 时顺手做这次拆分；每一条规则对应一条评测场景，之后才能安全地删改。

### 8.5 手机端有三份东西（P3，已核对）

`mobile/ios`（原生 App，主线）、`mobile/src` 加 `packages/mobile-client`（一个只读的网页入口，说明里写着聊天、批准、推送都未接入）、`prototypes/mobile-assistant`（只用模拟数据的原型）。

优化：只保留原生 App。如果采纳 6.7 里「给主机留一个网页入口兜底」，那就把网页入口做成正式的；否则删掉它和原型。

### 8.6 改名没有做完（P3，已核对）

产品已改名（ADR-018），仓库里还有约 116 个文件提到旧名字：服务单元名、手机工程名、部署文件、脚本，以及 10 处仍在读取的旧前缀环境变量。批次 E 尚未进行。

这本身不影响运行，但它会直接出现在 5.5 的安装流程里：新用户按文档装出来的服务叫旧名字。

优化：在做安装脚本和容器镜像之前完成改名，避免新装的主机再带一轮迁移。

### 8.7 技能有三套（P3，已核对存在，未核对使用情况）

项目技能（`skills/`、`project_skills.py`）、个人技能（`personal_skills.py`）、技能学习（`skill_learning.py`），各有各的存储和工具。前两套是给写代码用的，个人技能是给助理用的。

优化：看使用计数。如果项目技能和技能学习没人用，随工作台一起撤掉，只留个人技能。

### 8.9 自动审核只接了一处（P2，已核对）

位置：`src/scheduling/auto_review.py`。

5.3 决定由安全监管判定放行程度。监管里「替主人先看一眼」的那一层是自动审核：一个拿不到任何工具的隔离模型，判断放行、拒绝还是交给主人。设计是对的，硬规则在送审之前就由代码挡住（污点的不送审、只有指定类别可以被放行、每天有上限）。

但它现在只用在后台目标推进这一个循环里，只覆盖两类提议（改主人自己的事项、给常驻电脑项目派活）。对话里的动作、定时任务的动作、专员的动作都不经过它：要么直接问主人，要么直接拒绝。

优化：把自动审核做成确认门后面的一个通用环节：凡是「问不到人」或「主人设了可以代看」的场合，低风险类别先送审，其余直接变审批卡。可放行的类别仍由主人在权限页面逐项打开，默认全关。每次审核的记录现在只是一个本地文件，应当进审批历史。

### 8.10 角色有三套定义（P2，已核对）

- 子 Agent 角色：`.vortoone/agents/*.md`，工具面三选一（read / dev / deliver），见 `agents/subagents.py`。
- 小组成员角色：代码里写死的三种（研究员、审查员、开发），见 `workflow/tasks/team.py::ROLES`。
- 外部执行框架：OpenCode 等，按角色逐次判定权限，见 `agents/team_engines.py`、`agents/backends/acp.py`。

三套的字段、存放位置、权限表达都不同。9.9 的专员登记应当取代前两套，第三套作为专员的「由谁来执行」这一个字段。

### 8.11 插件清单写死在代码里，凭据是明文文件（P2，已核对）

位置：`src/plugins/__init__.py`。

插件的形状是清楚的（名字、凭据、只读工具、要确认的写入工具、早报段落、提醒），写入工具每次都过确认门，带回的内容一律算外部内容。问题有两处：

1. 可用插件是一个写死的列表，加一个插件要改主仓库的代码。ADR-011 说的最小 SDK（插件只经 SDK 导入）还没有。
2. 凭据是 `~/.vortoone/connectors/` 下的明文文件（仅本人可读）。放在家里的主机上可以接受；按 5.5 让别人放到云主机上，邮箱和日历的凭据就以明文躺在公网机器上。

另外插件现在直接向「早报」和「提醒」提供内容，这是 5.8 里各来源各自对接的又一个例子。

优化：插件改为从目录发现并声明自己需要的操作类别；凭据放进受保护的存储（至少用主机上的一把密钥加密）；插件只产出事件，由 5.10 的队列和投递路由决定何时告诉主人。

### 8.12 验收小组交付被当成「可免确认的自有数据操作」，但它不能撤回（P1，已核对代码，未实跑）

位置：`src/agents/tools/team.py`（`team_decide`、`team_reply`）、`src/agents/trust.py`、`src/agents/undo_log.py`。

`undo_log.py` 开头写明了一条规矩：只有登记了撤销的动作才可以申报为「主人自己的数据」这一类，因为这一类在「读操作免确认」的授权档位下不再问主人，换来的是事后可以一键撤销。

主对话里的 `team_decide`（验收通过或退回）和 `team_reply`（把话转给小组）申报的正是这一类，但它们没有登记撤销；小组一旦验收通过就进入结束状态，也没有重新打开的路径。

后果：主人把授权档位设为「读操作免确认」时，在没有读过外部内容的回合里，主 Agent 调用 `team_decide(accept=true)` 不会弹确认。文档和提示里说的「只有主人能验收」，在这种情况下靠的是模型遵守工具说明，不是代码保证。小组里有联网成员时，读交付会让回合变成污点，仍然会问；全部由不联网成员组成的小组（例如开发加审查）不受这层保护。

建议：验收通过改为申报不可撤回的类别（任何档位都问），或者只允许由界面上的按钮触发、不作为模型可调用的工具。这一条应当在 1.1（验收通过后推分支、开 PR）之前修，否则验收会直接带出对外动作。

验证与修复（2026-11-10）：离线行为测试 `tests/unit/test_team_tools.py::test_team_accept_requires_owner_confirmation_at_every_trust_level`
复现了干净回合在 READS、FULL 下不询问即完成验收；`test_team_accept_without_a_human_is_denied_even_with_auto_approve`
另复现了无人可问时自动批准也能完成验收。验收通过现申报 `IRREVERSIBLE`，覆盖各档位下同意、拒绝及无人可问的状态保持。
本项只修验收通过；退回与回话的类别和行为保持原样。

### 8.13 审计日志只追加不清理，写失败不报（P2，已核对）

位置：`src/gateway/audit.py::append_audit`。

每次工具调用和每个放行决定都往 `audit.log` 追加一行。文件没有轮转，没有大小上限，也没有保留期限。主机 24 小时在跑，这个文件只会一直变大。通知台账、撤销日志、用量台账都有上限，唯独审计没有。

另外写入失败时函数只返回 False，注释写的是「审计失败不阻塞产品工作」。多数调用方不看返回值，所以磁盘满或文件不可写时，动作照常执行而没有任何记录，也没有人被告知。

建议：按月分文件并设保留期限；连续写失败时通知主人一次，并在主机健康页面（6.3）上显示；对外发送和不可撤回的动作，在审计写不进去时应当拒绝执行。

### 8.14 「不可撤回」和「对外发送」两个类别定义了，但没有工具申报（P1，已核对）

位置：`src/agents/trust.py`，以及全部调用确认门的地方。

`trust.py` 定义了八个操作类别，并写明其中两类任何授权档位都不免确认：替用户在界面上点击输入的（交互），以及删除、付款、合并主分支这类不可撤回的。ADR-011 把后者列为必须落地的防线。

逐个核对所有调用确认门的地方：

- 明确申报类别的一共 17 处：交互 10 处、主人自己的数据 4 处、读 1 处、写 1 处、执行 1 处。
- **「不可撤回」一处都没有。「对外发送」「草稿」也没有。**
- 其余调用都不带类别，按默认的「写」处理。默认按重的算是对的，所以在多数档位下结果仍是「问主人」。

差别出现在内核最高授权档位及 CLI 的自动批准路径：这一档对「写」是免确认的。于是删除制品、开 PR 并推送、发布制品这些本应属于「不可撤回」或「对外发送」的动作，在这一档下和普通写文件一样不再询问。原文说「只在 Desktop 本机会话可以选」不准确：当前 Desktop 可信装配已把有效授权夹到 READS，并关闭自动批准；这里验证的是仍支持 FULL/自动批准的内核与工具路径。ADR 里「不可撤回的动作任何档位都不免」这句话，在本条审查基线上还没有工具落实。

这与 8.12 是同一类问题：类别体系设计得对，但工具没有按它申报，而且没有测试能发现漏报。

建议：这是 5.7（工具声明上加必填的操作类别）最直接的理由。在那之前可以先做一个小修：给删除类和对外发送类工具补上正确的类别，并加一条测试，列出「不可撤回」的工具名单，名单为空就失败。

验证与更正（2026-11-10）：`tests/unit/test_operation_kinds.py` 的行为测试复现了 FULL 下删除制品、
发布及更新制品、开 PR 未询问，实际调用收集的不可撤回工具名单为空。原描述遗漏了一点：`DELIVER`
本来就在 FULL 的免确认名单中，仅补类别不能满足 10.2。主人确认所有外发均须先询问后，现移除这项免确认，
并为制品发布/更新、开 PR、开发流水线推送、媒体发送和对外工序申报 `DELIVER`，删除制品申报 `IRREVERSIBLE`。
更新已发布制品同样要求确认。测试覆盖拒绝不执行、同意后执行，并在三端契约中覆盖 FULL/自动批准仍询问、无人可问则拒绝。

合并前补充核对（2026-11-10）：ADR-011 修订与命令行帮助已同步。另以离线测试复现了 attach
丢失操作类别、旧流水线命令直接批准外发的问题；经主人确认在 #825 一并修复，两个入口都按类别经过内核判定，
无人可问时拒绝外发，交互终端要求真实的主人答复；缺失类别不自动放行。

### 8.15 全系统没有「主人的时区」（P2，已核对）

5.9 第 3 条说定时任务没有时区。继续核对后发现这是全系统的问题：

- 代码里有 33 处直接取主机本地时间，包括早晚报的发送时刻、安静时段、「今天」的工作日志、对话数据库的时间戳，以及每回合告诉模型的「当前日期」。
- 只有日历插件处理了时区。没有任何地方保存「主人在哪个时区」。

主人自己的主机和人在同一时区，没有表现出来。按 5.5 让别人用云主机时，主机通常是协调世界时：早报在下午到，安静时段错开，「今天做了什么」按另一条日界线算，助理在每天的头几个小时里会把日期说错一天。

建议：在主人资料里加一项时区，默认取 Desktop 或手机上报的系统时区；所有「几点做什么」「今天是哪天」的计算都经过同一个函数；存储一律用协调世界时。这一条应当在阶段三（可安装）之前做完。

### 8.8 怎么优化：三条通用办法

前面八节的问题有一个共同来源：加得快、删得慢，同一件事有多套实现。单独修每一条会继续产生新的重复。建议在流程上定三条：

1. **每个阶段先删后加。** 阶段一的验收不是「做了什么」，而是这几个数字降了多少：工具数（现在项目会话 56 个）、接口数（282）、环境变量数（131）、`src/` 行数（8.2 万）、Desktop 安装包大小。把这几个数字写进本地门禁的收尾输出，每个 PR 都能看到。
2. **同一件事只留一个实现，写成契约测试。** 安全规则已经这样做了（三端能力矩阵）。照同样的办法补四条：回合前后的处理（4.2）、交付记录（1.2）、操作类别（5.7）、后台事件（5.10）。新入口、新工具不满足契约就过不了测试。
3. **决定和落地一比一。** 新的方向决定（ADR）要写明它替换掉哪些旧东西、哪一天删。上一个决定的删除项没做完，不开下一个。ADR-015 的 W1～W3 是第一批要补的。

## 9. 定位：哪些已经明确，哪些还没有

主人的问题（2026-11-10）：未来的方向定位是否已经明确。

**判断：产品的形态已经明确，「给谁用、主要帮他做什么」还没有明确。**

### 9.1 已经明确的

| 问题 | 结论 | 出处 |
| --- | --- | --- |
| 它是什么 | 个人 Agent：一个主 Agent，你只和它对话，它记住、跟进，下面带多个部门（见 9.4～9.6） | ADR-011、ADR-014、README |
| 用什么用它 | Desktop 和 iPhone，结构相同，以会话为中心 | ADR-012、ADR-016、ADR-017 |
| 跑在哪 | 用户自己的一台 24 小时在线主机，不做托管 | 本文 5.5 |
| 谁决定能不能做 | 安全监管逐个动作判定，没有模式开关 | 本文 5.3 |
| 写代码算什么 | 一种能力（由小组里的开发成员做），不是产品本身 | ADR-011、ADR-015 |
| 明确不做 | 每人一台云端虚拟机、自带邮箱、订阅对比等 | ADR-012 |

### 9.2 还没有明确的

1. **主要场景：研发工作，还是整个个人生活。** 三处自我描述不一致：README 写「替你盯着事情的个人 AI Agent」；`CURRENT_ARCHITECTURE.md` 写「面向个人研发工作的 AI 工作助手」；系统提示写「个人工作助手」。代码的重心在研发这一边：主动循环里最重的是派活单和 Codex 监管（5.8、8.3），而日历、邮件这些生活侧的能力只有读和存草稿（6.5）。两种定位对应的下一步完全不同：研发助手要把 Codex、PR、CI 做深；生活助理要把日历、邮件、提醒、资料做通。
2. **用户是谁。** 5.5 定了「别人用就自备主机」，这实际上把用户限定为会自己搭云主机的技术型个人。这个限定没有写进任何对外说明。如果接受它，很多事可以不做（网页入口、Windows、傻瓜式引导）；如果不接受，5.5 的决定就要重新看。
3. **这是自用工具，还是要经营的产品。** 仓库是开源许可、公开的；账号服务里有会员、套餐和购买；最近在做更新镜像、错误报告、使用统计。这些是「要给别人用并且收费」的投入。但 6.7、6.6 这些给别人用的前提又还没有。两种目标的优先级相反：自用应当先做阶段四（更像个人 Agent），经营应当先做阶段二和阶段三（可托付、可安装）。
4. **和同类产品比，凭什么选它。** ADR-012 说向 Muse 一类产品靠拢，并列了三点更强的地方：污点状态下预授权失效、撤销时列出撤不回的影响、数据在自己的机器上。这三点是真实的，但都是「更安全」，不是「能办成更多事」。对外的一句话里没有体现它们，README 强调的是「带一支团队」。
5. **成功的标准。** `CURRENT_ARCHITECTURE.md` 写了四个问题（今天有哪些事、推进到哪、哪些已核实完成、什么需要我决定），但没有数字，也没有数据（5.6）。

### 9.3 建议的定位（供主人定）

把上面五条合成一句话，建议是：

> **给技术型个人用的、跑在自己主机上的个人 Agent。它替你盯住工作上的事，需要你决定时才来找你；数据和权限都在你自己手里。**

对应的选择：

- 主要场景先定为**研发工作者的日常工作**（这是现在代码最强、主人每天在用的部分），生活侧只做日历和邮件两项并做通，不铺开。
- 用户明确为**会自己搭主机的技术型个人**，写进 README 和上手文档；不做 Windows、Android 和傻瓜式安装。
- 差异点对外说成两条：**数据在你自己的机器上**；**它不会在你不知情时替你做不可撤回的事**。
- 先自用到稳定（阶段一、二），再决定要不要经营。在此之前，会员、购买、分发相关的新投入暂停，只维持现有的。
- 成功标准用一个数字：每周由助理主动发起、并被主人采纳的事项数。

需要主人定的是 9.2 的第 1、2、3 条。（三条均已定，见 9.4。）

### 9.4 主人的补充决定（2026-11-10）

1. **不止一个小组，相当于多个部门。** 主 Agent 下面是若干个长期存在的部门，不是临时拼起来的一个小组。
2. **用户现在是主人自己，未来要给别人用。** 9.2 第 2、3 条因此定为：先自用，目标是给别人用。

第 2 条的影响：阶段二（可托付）和阶段三（可安装）不能省，顺序仍在阶段四之前；9.3 里「不做傻瓜式安装」的建议收回，改为按 5.5 的顺序把安装做到「一个没接触过项目的人能装起来」。9.2 第 1 条（主要场景）仍待定。

3. **主要场景是主人的个人生活，研发工作包含在其中**（2026-11-10 定）。9.2 第 1 条因此有了结论：不是在「研发」和「生活」之间二选一，研发是个人生活里的一个领域，与日程、邮件、资料、账单并列。对应的影响：现有的研发能力（派活、开发成员、Codex 监管）保留，作为若干部门中的一个；6.5（能做的事还窄）的优先级提高，日历、邮件要从「读和存草稿」做到完整可用；Codex 监管做成可关闭的插件（8.3），让不写代码的用户不受它影响。9.3 里「主要场景先定研发工作者的日常工作」改为「研发是第一个做深的领域，同时把日程、邮件、资料三项做通」。

专员、团队与部门的具体设计见 `STAFF_DESIGN.md`。

### 9.5 从「一个任务小组」到「多个部门」：现状与差距（已核对）

位置：`src/workflow/tasks/team.py`、`src/agents/tools/team.py`、`src/agents/team_members.py`、`src/scheduling/team_runner.py`。

现在的任务小组是为「一件大任务」设计的，和「部门」有六处本质不同：

| 方面 | 现在的任务小组 | 部门需要的 |
| --- | --- | --- |
| 寿命 | 为一个目标建立，主人验收后就结束 | 长期存在，持续接活 |
| 职责 | 目标和验收标准，一次性 | 固定的职责范围（例如研究、开发、运营、个人事务） |
| 成员 | 每次建组时临时指定，最多 6 个 | 固定编制，可以调整 |
| 角色 | 只有三种：研究员、审查员、开发 | 每个部门有自己的角色和工具面 |
| 记忆 | 成员每轮全新会话，没有记忆；协调人的纪要不落盘（4.10） | 部门有自己的知识和做事惯例，越用越熟 |
| 主动性 | 只在被派活、成员交回、主人留言时醒来 | 有自己的例行工作（定时、巡视），不等主 Agent 派 |

另外有四个现成的限制，多个部门同时工作时会直接碰到：

1. **可以同时开多个小组，但共用一个很小的执行池。** 代码不限制小组数量，但所有成员任务都进同一个后台池，默认并发只有 2（`VORTOONE_BG_TASKS`），每个小组自己的并发上限是 1～4。三个部门同时干活，实际是在排队。
2. **部门之间不能交接。** 小组只和主 Agent（经主人）对接。一个小组的产出要给另一个小组用，现在只能由主人或主 Agent 手工转述，而且受 2.1 的截断限制。
3. **花费不分部门。** 用量只在每个小组内计数，没有总闸（6.1），也没有「这个部门这个月花了多少」。
4. **主 Agent 不知道该把事交给谁。** 现在是主 Agent 每次临时提议开一个小组并列出成员。有了部门之后，需要一份部门名录（各自管什么、现在忙不忙），由主 Agent 按职责分派。

### 9.6 多部门的建议做法

不建议把「部门」做成一套新系统。建议在现有任务小组上加一层，复用它的派活、审查、验收和安全规则：

1. **部门是一份长期存在的登记。** 内容：名字、职责说明、固定成员（角色、执行框架、模型）、开放档位（能不能联网、能不能看私人资料、绑定哪个项目）、并发和花费上限。放进 5.2 说的底座里，和个人目标同级。
2. **部门里的每一件事仍然是一个任务上下文。** 也就是现在的小组，带目标和验收标准，做完就结束。部门提供的是成员、档位和上限的默认值，主 Agent 不用每次重新拼成员。这样现有的无进展判定、验收证据、污点规则都不用改。
3. **部门有自己的知识。** 每个部门一份「工作笔记」（惯例、常用资料、之前被退回的原因），在建任务上下文时注入协调人和成员。写入走现有的记忆写入策略：来自外部内容的不能直接进，主人或主 Agent 确认后才保存。这同时解决 2.3 的成员没有记忆。
4. **角色从三种扩成可登记的。** 现在角色是代码里写死的三项。改成登记表：每个角色声明工具面、能力档案、步数和时限。新角色必须落在已有的能力档案之内，不能自带权限（ADR-013 已有「子 agent 只从登记角色创建」的规定，沿用它）。
5. **跨部门交接走文件，不走转述。** 一个任务上下文的交付物存成文件（1.5 的建议），另一个部门拿到的是文件引用加只读权限。外部内容的出处标记随文件走。
6. **调度和花费按部门算。** 用 5.10 的队列：每个部门一个主题，各自的并发上限；全局再有一个总上限和花费总闸（6.1）。主机健康页面（6.3）按部门显示在忙什么、排队多少、花了多少。
7. **例行工作挂在部门下。** 定时任务（5.9）可以指定由哪个部门执行，用该部门的档位和上限，结果作为一个任务上下文交回。
8. **主 Agent 做分派。** 主 Agent 拿到的是部门名录而不是成员清单；提议时只说「交给哪个部门、目标和验收标准是什么」，主人确认一次。跨部门的大事由主 Agent 拆成几个任务上下文，各部门各自交付，主 Agent 汇总后交主人验收。

**安全上必须保持的：**

- 部门的权限来自登记并由主人批准，不来自派活的一方（见 9.10；此前写的「只能比主会话更窄」不成立，已更正）。
- 联网的部门看不到私人资料，能看私人资料的部门不能联网（现有 open / private 的规则），不因为「同一个公司」而互通。
- 部门之间传递的内容只要有外部出处，接收方那一回合照常算污点。
- 仍然只有主人能验收；部门和主 Agent 都不能宣布完成。

**界面：** 侧栏现在是「主要聊天、任务小组、旁聊」（ADR-016）。改成部门后，建议侧栏列部门，点进去是这个部门的群聊和它手上的几件事；等你处理的仍然只在主要聊天顶部出现一次。

**先做哪一步：** 部门登记加默认成员（第 1、2 条）改动最小，可以先做，让主人实际用两三个部门跑一段时间。知识、交接、按部门调度在阶段二的队列和交付收口做完后再接上。

### 9.8 临时团队和长期队伍：两种都要，但只做一套机制（主人 2026-11-10 提出）

主人的问题：一个是临时的团队，一个是长期的队伍，是不是都需要。

**判断：都需要。它们解决的是不同的事，但底下应当是同一套东西，只是寿命和成员来源不同。**

| | 临时团队 | 长期队伍（部门） |
| --- | --- | --- |
| 用在什么时候 | 一次性的、跨领域的、以后大概不会再做的事 | 反复出现的同一类事 |
| 例子 | 「调研三家供应商并给出建议」 | 「所有代码改动」「每周的资料整理」 |
| 成员 | 这一次临时挑，可以从各个长期队伍里借人 | 固定编制 |
| 结束 | 主人验收后解散 | 不解散，一件事做完接下一件 |
| 知识 | 做完后只留交付物 | 积累工作笔记，越用越熟 |
| 例行工作 | 没有 | 可以有定时和巡视 |
| 现状 | 已经有了，就是现在的任务小组 | 还没有 |

只要长期队伍会出现三个问题：每件小事都要先归到某个部门，归不进去就做不了；跨领域的事要么硬塞给一个部门，要么得为它新设一个部门；部门越设越多。只要临时团队就是现在的状态：每次重新拼成员、没有积累、不能有例行工作。

**一套机制怎么做：**

- 执行的单位只有一种：任务上下文（目标、验收标准、成员、档位、上限）。现有的派活、审查、无进展判定、验收、污点规则全部作用在它上面，不分临时还是长期。
- **临时团队** = 一个不属于任何部门的任务上下文，成员是这一次指定的。也就是现在的做法，不用改。
- **长期队伍** = 一份部门登记（9.6 第 1 条）加它名下先后出现的多个任务上下文。部门提供成员、档位、上限和工作笔记的默认值。
- 临时团队可以**借用**长期队伍的成员定义（角色、执行框架、模型），但不带走那个部门的工作笔记和权限档位；档位按这次任务单独定，由主人在确认开团队时一并批准（见 9.10）。

**主 Agent 怎么选：**

1. 这件事落在某个部门的职责里：交给那个部门。
2. 跨两个以上部门，或者哪个部门都不管：开临时团队。
3. 小事：自己做，不开团队（现有规则）。

选择由主 Agent 提议、主人确认一次，和现在提议开小组一样。

**从临时变长期：** 同一类临时团队出现过几次之后，由主 Agent 提议「把它固定成一个部门」，主人确认后才建立。不自动转，避免部门越来越多。反过来，一个部门长期没有接活，在健康页面上提示主人是否撤掉。

**要防的两件事：**

- 临时团队做完后，它里面有用的经验会丢。解散时由协调人起草一条小结，主人确认后归到最相关的部门笔记或长期记忆里；不确认就不保存。
- 两种团队同时存在时，抢同一个执行池。并发和花费上限要有三层：全局、每个部门、每个任务上下文（9.6 第 6 条），临时团队直接占用全局额度。

**界面：** 侧栏分两组：上面是长期队伍（固定几项），下面是进行中的临时团队（做完就消失，进历史）。等你处理的仍然只在主要聊天顶部出现一次。

**顺序不变：** 临时团队已经存在，先把它的交付和交流问题修好（第 1、2 节）；长期队伍在它之上加登记这一层（9.6 的第一步）。

### 9.9 只有一个成员的形式：需要，而且应当是最常用的（主人 2026-11-10 提出）

主人的问题：成员可以只是一个人，专门负责一件临时任务或者一项长期任务，这种形式是不是需要。

**判断：需要。多数事情一个人就够，为它配一个协调人加几个成员是浪费。但现在「一个人去做一件事」已经有四种做法，应当合成一种。**

现状（已核对）：

| 现有做法 | 位置 | 特点 |
| --- | --- | --- |
| 子 Agent（`task` 工具） | `agents/delegation.py` | 主 Agent 当场派一个子 Agent，可用 `.vortoone/agents/` 里自定义的角色；结果回到主对话 |
| 派活单 | `workflow/tasks/assistant_dispatch.py` | 助理起草、主人批准后交给开发流水线；有提问、复盘、重试 |
| 定时作业 | `scheduling/cron.py` | 到点起一个隔离会话跑一段提示 |
| 一个成员的任务小组 | `workflow/tasks/team.py` | 代码允许只有 1 个成员，但仍然会起一个协调人去管这一个成员 |

四种做法的状态记录、角色定义、权限装配、结果交回方式都不一样。其中第四种最不划算：每一步都要协调人先醒来、派活、再醒来读结果，模型调用翻倍，信息还要经过 2.1 的转贴。

**建议：把「一个成员」作为基本单位，叫专员；团队是多个专员加一个协调人。**

四种组合对应四种用法：

| | 临时 | 长期 |
| --- | --- | --- |
| 一个人 | 临时专员：做完一件事就结束 | 常设专员：长期负责一项事务 |
| 多个人 | 临时团队（9.8） | 长期队伍、部门（9.6） |

具体规则：

1. **一个人时不设协调人。** 主 Agent 直接派活、读结果、决定返工或交主人验收。现有子任务的审查和返工（`task_review`、`task_followup`）已经是这个流程，沿用它。协调人只在两个以上成员需要互相配合时才出现。
2. **专员和团队成员是同一种东西。** 同一份登记：角色、执行框架、模型、工具面、能力档案、步数和时限。一个专员可以单独接活，也可以被编进某个团队；被借进团队时不带走自己的笔记和权限（与 9.8 的借人规则相同）。
3. **常设专员就是只有一个人的部门。** 它有自己的职责说明、工作笔记、例行工作和花费上限。例如「账单专员：每月初核对订阅和扣款，有异常告诉我」「论文专员：每周看某几个来源的新文章」。这比现在的定时作业多了记忆和可追问，比部门少了协调开销。
4. **定时作业并进来。** 现在的定时作业相当于「一个没有名字、没有记忆、每次全新的临时专员」。改成「到点把这件事交给某个专员」之后，5.9 里能力窄、结果不能追问的问题一起解决：专员用它登记的档位，结果作为一件事交回。
5. **派活单并进来。** 派活单相当于「交给开发专员的一件临时任务」。提问、复盘、重试这些已有的能力保留，变成所有专员共用的。

**什么时候从一个人变成多个人：** 不让模型自由决定。规则是：需要两种互相隔离的权限（例如一个要联网、一个要看私人资料）、需要有人独立审查、或者工作可以明显并行时，才开团队；否则一个专员。主 Agent 提议时写明理由，主人确认。

**这样合并之后减少的东西：** 子任务、派活单、定时作业、单人小组四套状态和四套角色定义变成一套；9.5 里「主 Agent 不知道该交给谁」的名录里同时列专员和部门。

**安全上不变的：** 专员的权限按 9.10 的规则登记和批准；常设专员的例行工作仍按无人值守处理，默认拒绝需要确认的操作，动作一律变审批卡；只有主人能验收。

**顺序：** 先定专员的登记格式，让子任务和单人小组共用它（改动小）；再把定时作业和派活单迁过来（与 5.9、5.10 一起做）；常设专员和部门最后加上笔记与例行工作。

### 9.10 专员的权限不一定比主会话小（主人 2026-11-10 更正）

此前 9.6、9.8、9.9 里写过「专员、部门的权限只能比主会话更窄」。主人指出这不对，核对代码后确认：**现在就不是这样，也不应该是这样。**

- 常驻助理的主会话（通用范围）不能执行命令、不能改项目文件。而开发成员可以在一次性副本里改代码，开发型子 Agent 可以调用隔离开发流水线。
- 研究员可以联网；带私人资料的主会话在某些档位下反而不联网。
- 专员存在的意义之一，就是去做主会话不该直接做的事：把危险的能力关在一个范围更小、看不到别的东西的执行者身上。

所以正确的约束不是「更小」，而是下面七条。前四条现有代码已经部分做到，后三条是合并成专员时要补的。

1. **权限来自登记，由主人批准，不来自派活的一方。** 专员能做什么，写在它的登记里；新建专员、给专员加权限，都要主人批准（ADR-013 已规定角色由主 Agent 提议、主人批准，污点回合不能提议）。主 Agent 派活时不能临时给专员加权限。
2. **危险的组合不放在同一个专员身上。** 「能看私人资料」「会读到外部内容」「能对外发送或改东西」三样不同时给一个专员。现有规则是其中一部分：带私人资料的小组不能有联网成员。登记专员时由代码检查这条，不靠人记。
3. **专员的结果一律当外部内容。** 读过网页或别的外部来源的专员，交回的内容带出处标记，主 Agent 读到它的那一回合算污点（现有做法）。
4. **不可撤回的动作和对外发送仍然过确认门。** 专员在后台问不到人时，动作变成审批卡等主人，不是直接执行，也不是直接拒绝。
5. **防止主 Agent 借专员的手。** 专员权限比主会话大的时候，主 Agent 就成了一个可以被利用的中间人：主 Agent 读了一段恶意内容后，被诱导去给高权限专员派一件有害的活。规则：主 Agent 处于污点回合时，派给「权限超出主会话」的专员的任务，必须主人确认，且确认卡上显示完整的任务原文。
6. **专员不能再派专员。** 沿用 ADR-013 的「子 agent 不递归」。需要多人配合时由主 Agent 或团队的协调人安排。
7. **权限要看得见。** 权限页面按专员列出：能用哪些工具、能看到什么、能不能联网、能不能对外发送、最近做了什么。主人随时可以收回某一项。

对 5.7 的影响：工具声明加操作类别之后，专员的登记就可以写成「允许哪些类别、在什么范围内」，上面第 2 条的组合检查也才写得出来。

### 9.7 Windows：之后也要支持（主人 2026-11-10 定）

6.7 里「平台只有 macOS 和 iPhone」的问题因此有了结论：近期 macOS 加 iPhone，之后要有 Windows 的 Desktop。

现状（已核对）：

- Desktop 用的框架本身跨平台，前端代码基本可以直接用。
- Rust 层里只有 1 处为 Windows 写的分支；另有约 60 处用到 macOS 专有的东西：系统钥匙串（账号令牌、主机令牌、模型密钥都存在里面）、用 `open` 重启应用（更新流程，#805）、系统原生对话框的调用方式、本地网络权限的处理。
- 发布脚本只认一个平台：更新清单里写死 `darwin-aarch64`，校验脚本在非 macOS 上直接退出，安装包只有 DMG，签名和公证走的是苹果的流程。
- 本机引擎（随 App 一起装的 Python 运行时）的打包脚本需要为 Windows 另出一份。
- 引擎的命令沙箱只有 macOS 和 Linux 两种后端（seatbelt、bwrap），没有 Windows 的。

这对 5.5 的形态是有利的：其它人用的是「Desktop 加一台自备主机」，主机在 Linux 上，重活都在主机上做。Windows 上的 Desktop 可以先只做**连接主机的客户端**，不带本机引擎，也就不需要 Windows 的沙箱和 Python 打包。

建议顺序：

1. 现在就做、成本很低的准备：新写的 Rust 代码把系统相关的调用收进一个模块（钥匙存取、重启、对话框），不再散在各处；更新清单的格式改成支持多个平台。
2. 阶段三里做 Windows 的「只连主机」版本：钥匙改用 Windows 的凭据管理器，安装包和签名走 Windows 的流程，更新镜像按平台分目录。
3. Windows 上的本机引擎放到最后，等确认有人需要不搭主机单机使用时再做。

Android 没有提到，暂按不做记录。

## 10. 交给执行者的清单

前九节是问题和研判，不是任务单。这一节把其中可以直接动手的部分排成批次，供执行的 Agent（或人）按顺序做。

### 10.1 通用规则

1. **先复现，再修。** 本文全部来自读代码，标了「推断」「未实跑」的条目尤其如此。每一项先写一条能失败的测试证明问题存在；复现不出来就在本文对应条目下注明并跳过，不要照着描述硬改。
2. **一项一个 PR。** 每个 PR 只解决一个条目，标题带条目编号（例如「8.12 验收必须主人确认」）。不顺手重构。
3. **用自己的分支**（`codex/*` 或 `vorto/*`），只走 PR，不在别人的分支上叠提交，不在 main 上提交。
4. **合并前跑 `./scripts/ci-local.sh`。** 测试必须离线、确定；断言行为，不断言源码里有没有某个字符串。
5. **不扩大范围。** ADR-008 冻结的模块只修明确的缺陷；改到安全内核（确认门、污点、能力档案、信任档位）时同步更新 `tests/unit/test_three_end_contract.py`。
6. **不发版、不部署。** 合并、部署常驻主机、发 Desktop 版本都由主人决定。
7. **做完回写。** 在 10.4 的表里把状态改成已修并写上 PR 号；发现描述有误就直接更正本文。
