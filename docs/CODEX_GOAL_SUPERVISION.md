# 目标与 Codex 跟进

2026-10-31。复用 General 助理的私人目标、逐会话交接、原监督巡检与批准动作。
目标文件是验收事实来源，Codex 是执行状态来源；没有新增任务库、执行器或自动发话权限。

## 使用

1. 在助理目标面板创建目标及可核对的验收标准。
2. 助理通过 `personal_goals` 和 `codex_status` 读取目标版本、验收项 ID、精确 Codex 会话。
3. 用户要求交接后，调用 `codex_handover`，传入 `thread`、`goal_id`、`goal_revision`。
   可用 `criterion_ids`（英文逗号分隔）限定本次范围，例如仅 `criterion-1`，其他事项留到以后。
   `review_limit` 默认 4、最多 12，表示这个目标从首次交接以来累计最多几次模型推进判断。
   确认内容显示目标、版本、本次范围和累计上限。增加上限、改变范围也需要重新确认。
4. 每条消息/叫停仍走原批准卡片。目标是否达成仍由目标面板逐项用户验收决定。

新目标交接需要带宿主身份的当前 execution 观测，不接受靠同名会话或报告里的目录寻找目标文件。
目标必须位于当前 General runtime 的原私人目标目录；本轮不把仓库 development Goal 跨宿主搬过来。
已有无目标交接保持兼容；它不因此获得长期目标验收能力。

## 判断与停止

- 监督材料包含原目标、验收项、当前未通过项、本次授权范围和各项最新证据摘要。
  不把全部历史证据塞进模型；完整证据仍在原目标记录中。
- `continue` 必须带有效的本次未通过验收项 ID 和失败类别。额外想法不能成为返工条件。
  这是结构化范围校验，不能证明模型生成的自然语言完全符合范围，用户仍需审阅具体指令。
- 模型 `done` 仅表示本轮结束，不能写入目标验收、标为 achieved 或据此收回目标交接。
  原目标已有逐项、最新、明确的用户通过证据时，规则检查可以结束交接，无需再调模型。
- 同一验收项集合及失败类别连续两次出现，且没有新验收证据，第二次就不再拟推进消息。
  指纹使用验收项 ID、失败类别、证据版本，不使用模型措辞。换说法不清零。
- 目标阻塞、本次范围完成、累计额度耗尽、目标/目录/宿主变化、记录不可读时暂停自动判断。
  用户延期应收回交接，或把延期事项排除在本次范围外；当前提示词也禁止擅自继续延期事项。
- 需求、证据或进展在模型等待期间变化，旧判断丢弃，但已预留的次数不退还。
  目标更新或交接变化后，旧提议/待执行批准不能再通过批准或认领边界。

累计次数存于原 `supervisor.json.goal_reviews`，按 goal ID 计数，先持久化再调用模型。
它不会因为新轮次、换会话、收回/重新交接或进程重启而清零；最多保留 128 个目标的计数，不自动淘汰。
已绑定目标的额度记录丢失时暂停，不自动重建。增加累计上限可明确批准更多判断，最高 12；
新证据可解除无进展暂停，但不能补回已用次数。

这是**逻辑推进判断次数额度**，不是供应商请求次数或 token/金额硬预算，也不能停止已在 Codex 执行的工作。
监督器不重启失败的判断；模型客户端沿用现有连接失败恢复与用户配置的 SDK 重试策略。
沿用原巡检节奏（默认 30 分钟、每次最多 2 个判断、总等待最多 90 秒、每次输出最多 800 token）。
每个目标输入材料另限 32,000 字符，超过则失败并要求人工核对；失败也计次且不自动重试。
真实启用监督会产生模型请求及供应商费用，实际价格取决于用户配置的模型。

## 可见性与恢复边界

`codex_status` 展示关联目标、未验收项、累计次数及暂停原因。
原 `/api/codex/status` 的只读 `goal_supervision` 投影也接入 Desktop 的「今日工作」：
原目标条目显示等你验收、跟进暂停和累计判断次数；原 Codex 详情展示关联目标、本次范围及验收导航。
绑定与增加额度仍通过助理的原交接确认门，没有新增 Desktop 绑定编辑器或执行按钮。

Desktop 同时核对当前运行端、读取时效、报告时效、执行身份、目标版本和未验收项。
旧服务未提供关联字段时兼容原展示；未知状态、重复关联、版本不符或失联只显示待核对。
缺失次数不补零，历史次数标为上次记录。目标源未取得当前记录时禁用验收导航。
关联目标的确切验收记录独立于 Codex：执行完成不增加已完成目标，Codex 失联也不抹掉已确认的目标证据。
目标与执行沿用原来源各自计数，不把关联投影另算作一个任务。

浏览器组件验收可打开 `ui-harness.html?view=goal-progress`，所有记录为虚构数据，不连接模型或执行服务。
它验证组件展示和回调，不等于已安装应用或真实主机链路验收。
模型判断本轮结束但仍需验收、需要用户决定、或建议超出本次范围时，等待原因保存在原监督记录中，
刷新后显示 `awaiting_user`。原因绑定原交接、目标版本和轮次；新版本、新轮次或重新交接不会继承旧原因。
这不写入 Goal 状态，也不取代用户验收；额度耗尽、无进展和阻塞等规则暂停仍优先显示。

拟动作、批准/拒绝、认领、结果回执、过期清理和超时对账对原动作文件使用同一跨进程锁，
避免一条动作的保存把另一条已认领动作覆盖回 approved。需要同时核对交接时，固定先锁交接再锁动作。
锁内不调用模型、外部 RPC 或通知。写入繁忙时拒绝操作；只读查询中的超时对账可以暂缓，
进度报告仍可先保存。批准与认领会再次核对最新轮次和交接，不能利用暂缓的清理执行旧动作。

Goal 变化不重放执行；审批失效不撤销已提交的 RPC。已受理或结果不明的动作仍按原不重发规则处理。
通知持久投递、供应商硬费用控制、跨宿主自动恢复和备份灾备不属于此合同。
