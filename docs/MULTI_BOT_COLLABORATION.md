# 总助手与专职 bot 的协作方向

详细方案见 [多 bot 工程设计 v1.4](MULTI_BOT_DESIGN.md)：身份、角色工具面、多入口生命周期、
任务回流、预算与取消准入、验收矩阵和实施切片。该 RFC 待评审，未继续扩产品实现。
第一轮 [对抗审核](MULTI_BOT_ADVERSARIAL_REVIEW.md) 已识别准入缺口并修订到 v1.1；
结构复核后分开总助手模型、确定性任务控制、独立执行轮次与渠道入口；第二轮补充有界
控制受理、升级恢复和版本证据合同，以 v1.4 为准。[官方架构对照与采用决策](MULTI_BOT_ARCHITECTURE_REFERENCES.md)
记录 Anthropic/Claude Code、OpenAI、Google ADK 与 xAI grok-build 的公开机制及适用限制。
规范补齐不代表运行时验证通过，完整任务联动仍有明确上线门禁。

2026-10-31。用户已明确选择：总助手协调专职 bot，必要时有独立 Telegram/微信入口。
本方向保留现有单一 runtime、任务台账、隔离工作台和人工交付门。角色按需要启用，
不恢复早期每件事固定经过五个角色的流水线。

用户进一步明确希望不止双 bot：目标是 **一个总助手 + N 个按需专职 bot**，两 bot 只是
首个连通场景。名册与绑定使用集合，登记数、入口数和执行并发分别控制；不要求所有 bot
同时推理，也不要求每个 worker 都有外部账号。[grok-build 规模与联动复核](MULTI_BOT_ARCHITECTURE_REFERENCES.md#grok-build规模与联动复核)
记录多执行者准入、排队、根血缘和可选消息机制，及其不能替代本项目 IM 托管的边界。

## B1 实施：实际 N 入口托管

[N 入口托管](IM_MULTI_HOST.md) 已由 `runtime_lifespan` 消费：显式 Project 宿主配置分开
登记 bots/bindings/primary 与共享模型槽，运行 1/2/4/8 个绑定的真实 poll 循环。新增入口
全部只读，主协调入口也不继承普通 Project 助手的公网/开发/审批面。General 和正式项目
派活沿原路径保留；此处的 primary 只指定模型预留与唯一文字通知目标。

绑定关闭等待真实清理，旧句柄不能移除新注册；主入口故障不改投其他 bot。一个 bot 多
入口共享聊天占位，默认不共享历史。繁忙明确拒收，没有先添加一套内存队列并宣称持久受理。
旧单入口模式继续兼容；原开发 TaskRunner/worker 未为每 bot 复制。尚未完成持久输入/事件
去重、原 actor 统一控制、General 授权映射和正式研究往返，因此完整 B/C/D 门禁仍保留。

## 首个实施切片：项目只读研究角色

已接入单一 `build_session` 工厂及现有 standalone/embedded IM 入口：宿主选择
`research_read` 后只装配 `read_file/list_files/grep`，并在共享工具运行层持续限制工具名、
只读/外向元数据和原敏感路径规则。后续追加的写、命令、联网、MCP、递归任务工具也不能
靠 build 模式或确认放行。旧 `researcher`/`with_dev=False` 仍是可写脚本的旧用途，不作替换。
该角色的项目权限配置损坏时拒绝装配/读取，不按空规则放行；新 deny 在下一次调用前核对。
装配时已有的 deny 也保留，放宽规则需重新装配会话。其他角色的旧配置兼容行为保持原状。

该角色不自动加载用户全局指令、主助手资料、项目/仓库记忆、技能、插件、hooks 或流水线
状态；按明确问题读取项目证据。每次装配有独立 MainAgent/history，步数最多 12，关闭 build
自动续跑和模型摘要。它沿用宿主原模型配置，步数不是 token、费用或墙钟硬预算。
读到的内容会进入已配置模型请求；本轮验证全部使用离线替身，没有真实模型调用。

需在已选择的 Project 目录中显式配置下列组合；沿用已配对账号凭据，不在示例中填写密钥：

```bash
VORTOCODE_WORKSPACE_SCOPE=project \
VORTOCODE_IM_CONVERSATION=isolated \
VORTOCODE_IM_ROLE=interactive \
VORTOCODE_IM_POLICY=research_read vc im telegram
```

同样策略由 `vc server --im telegram` 的内嵌入口消费；原 runtime/account lease 不变，不能
在同目录为凑两个 bot 启动第二个状态所有者。钉钉沿原适配器与配对配置使用。错误策略、
General/Scratch、主通知模式、扩大的入站白名单拒绝启用；不会退回权限更宽的普通角色。
研究会话身份包含固定工具策略摘要，不能导入同账号原 standard/isolated 的历史或人设。
相同策略正常重启保留自己的历史，已保存的 build 模式也不扩权；策略换代保留旧记录但不
自动导入。这个摘要只标识固定工具策略，不是后台任务授权或完整升级迁移证明。

离线测试覆盖真实 IM 入站→共享核心→项目读取→回复，以及越权工具、历史隔离和原权限
规则。并修复共享批量读取的一处缺口：`grep` 和枚举不再沿符号链接访问项目外的普通文本，
实际读取前也重新核对范围；Git 与非 Git 目录均有回归用例。
追加 1/2/4/8 个只读角色实例的并发回合测试，确认实例、历史和各自回复不串；这些调用
不经过待实施的宿主注册/聚合槽准入，不能据此声称 K 并发限制或 N 账号托管已经通过。

以上是 A 切片的角色工具面；B1 已增加 Project 的 N 入口托管，但仍未完成
actor/持久输入去重迁移或 General→Project 研究任务卡往返。当前读取活动工作区不等于
固定提交/完整证据清单，R8—R10 等门禁未由本切片关闭。真实渠道、模型效果与成本未验收，
没有开启自动接力、自动审核循环或改动运行中的机器人配置。

## 三种身份分开

| 概念 | 作用 | 不能代替什么 |
| --- | --- | --- |
| bot | 持久职责、会话、许可范围与任务归属；例如项目推进、资料研究、验证 | 不是每个 bot 都要新建一套 runtime 或拥有全部凭据 |
| IM 账号 | Telegram/钉钉或未来微信中的外部入口，可绑定某个 bot | 名称、聊天内容和转发消息不能自称为可信 bot 身份 |
| 执行者 | 内置子 Agent、隔离工作台或已授权的外部 Codex 会话 | 模型和后端选择不能授予跨 bot 权限或替用户验收 |

建议先有一个总助手，按任务需要启用研究、实施、验证等专职角色，不要求每次全部参与。
只有需要独立聊天/职责记录的角色才绑定 IM 账号；同一角色可以有内部执行与外部入口，
外部聊天入口本身不会自动成为后台协作协议。

## 联动方案：沿任务传递，不靠群聊互相触发

```text
用户 → 总助手 → 任务合同与确认 → 专职 bot / 原执行者
             ↑                         ↓
             └── 原任务收件箱 ← 结果与证据、精确轮次
```

总助手负责目标、范围、分配和最终汇报；专职 bot 只处理领取的明确任务。共享的是已授权
任务材料与项目进展，各自的完整聊天不自动混入其他 bot。专职 bot 提问或提交结果，
由总助手关联原任务处理；需要另一专业角色时，先向总助手提出有证据的请求。

现有 task/research_parallel、SubagentRegistry、CollaborationService、TaskRunner、
TaskLedger 和 CompletionInbox 提供可复用基础。General 的主助理当前不暴露项目研究委派；
assistant_dispatch 当前主要下发开发任务，不能把角色文件存在说成已能从总助手路由专职 bot。
后续应在原助理派活/项目执行入口补精确角色目标与结果投影，不新建平行任务数据库。

后续跨 bot 合同应包含 root_task_id、请求幂等身份、发起 bot、接收 bot、项目/目标版本、
范围与非目标、验收项、执行轮次、结果版本和取消/预算状态。字段映射到原领域记录；
这里是设计要求，尚未实现新的跨 bot 投递接口。

## 防止无限联动的准入条件

1. 初版只允许总助手向专职 bot 下派；专职 bot 不递归派活，不从群聊消息自动接单。
2. 同一任务/轮次只能认领一次，完成回报按结果版本去重。accepted 仅表示受理，
   done 仅表示执行结束，仍需证据与用户验收；未知回执不重放副作用。
3. 用原有每任务最多三轮作为返工边界；跨 bot 转派不能新建根任务重置次数。
   在允许自动转派之前，必须先有持久的根任务累计执行次数/超时准入，缺失则不自动启动。
   默认并行两路的既有研究工具只是单次调用限制，不冒充多 bot 全局并发或供应商金额硬预算。
4. 没有新产物/证据、相同缺口重复、范围变化、取消或累计额度耗尽时，保留原因并等待用户。
   不靠加评审角色、重新交接或换 bot 清零；总助手停止后，不被子 bot 的迟到报告重新叫醒。
5. 先采用原 Inbox 的被动收件，不为每个进度事件启动模型。后续若启用完成唤醒，
   应显式选择、有总额度、先持久认领，汇报成功后才确认；失败不能形成自我通知循环。

## 本轮已实现：会话身份与独立入口底座

- Telegram 使用 token 中公开账号 ID，钉钉使用 client ID，与主人、渠道、会话模式一起
  计算会话键；密钥不进入会话键。换账号不读旧账号历史，同一账号换密钥仍能恢复。
- 原主入口默认 primary；显式设置 VORTOCODE_IM_CONVERSATION=isolated 后，拥有自己的
  历史、活动、模式、人设和横幅记录，不进入主要聊天，也不生成主要聊天的摘要/记忆候选。
- General 助理工具的任务归属与回合绑定使用该 bot 会话键；Project 原委派工具面保持兼容，
  其专职路由身份仍待后续托管阶段实现。独立入口只处理自己的即时确认，不处理
  其他入口的持久派活/Codex 按钮；不接全局通知、补发队列、后台任务广播或 im-dev worker。
  直接 /task、流水线审批及 /mode 等命令要求回总助手；/status /stop /new /persona /help 可用。
- primary 保留原工作区人设与主要聊天合流；isolated 使用独立人设。这里隔离上下文和入口，
  不把人设当权限。模型工具仍受已有能力档、污点与确认门约束；专职工具白名单尚未单独绑定。
  isolated 是会话模式，尚不是受限专职角色，也不防已有文件读取工具访问同工作区的其他记录。
- 所有旧、缺少账号来源的会话文件保留，不自动猜测归属后迁移；新账号键默认开始新历史。
  原主要聊天保留在原主聊天记录中。需要迁移旧 IM 上下文时，须先备份并人工核对账号归属。
- 自定义旧 adapter 可在 primary 兼容原键；isolated 必须提供稳定非凭据身份，配置拼错拒绝启动。

上述配置用于一个入口的独立会话验证，不是启动完整多 bot 团队的命令。当前一个 runtime
仍只允许一个内嵌 IM 桥，同一工作区的跨进程所有权锁也保留；不能多开进程绕过它。
当前只有 Telegram/钉钉适配，微信尚未实现，不能说已接入。
