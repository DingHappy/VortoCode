# 安装引导与个人空间改版

2026-11-13 主人确认：每个运行端先有一个个人空间，里面管理多个项目；退出面向用户的
`vc` / `vortocode` 产品入口，保留内部启动、诊断与第三方执行器。参考 agentes.chat 的
安装与空间组织方式，沿用现有 Python runtime、主人确认、污点、岗位、任务和调度合同。

## 概念与当前实现（P0）

| 概念 | 含义 | 当前兼容映射 |
| --- | --- | --- |
| 运行端 | 保存资料并运行助理的实例 | 原 Desktop 连接登记；登记 ID 只代表客户端连接，不证明实际实例 |
| 个人空间 | 一个运行端的日常工作入口 | `personalSpaceRef` 提供稳定的客户端引用，沿用原主要聊天键 |
| 项目 | 空间内明确登记的工作对象 | 旧项目条目保持原 ID；旧记录没有所属空间字段时保留未知 |
| 会话、任务、审批 | 各自已有权威记录 | 引用原 SID、task_id、digest/nonce/轮次/实例，不新增台账 |

`desktop/src/lib/personalSpace.ts` 是只读兼容投影，现有 `assistantHost` 的选择、项目过滤和
聊天键共用它。远端 `@assistant` 条目投影为个人空间；待连接完成的 pending 条目不参与
自动选择，也不冒充项目。本机同名目录仍是项目。临时本机引擎保留原聊天键与生命周期。

P0 不写回登记、不搬历史或配置，也不猜测项目归属：同名目录、相同服务器地址甚至同一
电脑上的不同服务，都不足以证明是同一运行端或空间。新引用不授予资料读取或执行权限。
实际运行身份继续由原 `instance_id` / generation 合同核对，重启失效的审批不复用。

P0 只完成读取映射，不声称所有页面已改用一个新上下文。P3 继续复用
`SessionConnection` 的唯一 client owner 与代次，不创建第二个连接状态源。连接失败显示
原目标状态；后续引导不会静默把远端工作转交本机。项目授权仍由原 scope 与固定绑定决定。

首次流程为：选择运行位置 → 核对已有环境/准备缺项 → 建立主人连接 → 配置模型 → 进入
个人空间。已有用户恢复原明确选择。开发能力启用时再准备第三方执行器，不将它们作为聊天
前置条件。本机常驻的独立生命周期和显式复制模型配置继续遵守 [原合同](LOCAL_RESIDENT.md)。
空间不引入多人租户、第二套任务库或资料同步；项目页面沿用隔离开发，不恢复旧编码工作台。

## P3 主壳与当前目标

侧栏保留主要聊天、小组、部门和旁聊，在品牌下显示当前运行端、空间与连接状态。
空间选择只列连接已登记完成的常驻助手，沿用原来的预检、连接、持久化选择和激活流程。
同名空间显示连接来源与登记 ID，失败保持可见，不把失败的远端选择转交本机。
管理入口仍进入「电脑与连接」。断线重试和助理面板名称读取当前目标，不改回旧默认助手。

`desktopContext` 是原 `ConnectionCoordinator`、runtime 和 `SessionConnection` 的只读投影。
它组合连接登记、地址、scope、项目目录、SID、client 代次及原连接 epoch，供助理快照、目录、
动作卡的已有 scope 核对共用。`GatewayClient.desktopSource` 不含凭据，也不代替服务端实例证明。
临时本机引擎与常驻助手仍是不同目标；没有所属空间字段的旧项目保持「归属待核对」，不按
目录名或地址归并。审批的 digest、nonce、轮次与服务实例继续由原流程核对。

文字与已读完的附件按运行目标、scope、目录和 SID 暂存于当前窗口内存；切回原会话可继续。
未发送的旁聊出现在原空间侧栏，关闭应用后这些草稿不保留，也不写入任务库或同步到运行端。
离开草稿会取消未完成文件读取，并作废旧发送恢复凭据。重连同一目标保留草稿；修改已登记
远端的地址则使用另一份草稿。本机临时引擎启动换端口时仍保留当前输入。
迟到的发送失败只处理原来的 client/连接 epoch，不能覆盖新草稿或给另一目标插入失败活动。

选择空间或完成引导时，读取本机运行身份后、保存默认助手前再次核对原 client 与连接 epoch。
连接更换或同一 client 重连会作废旧选择；迟到读取不能再发起原生保存，引导保留待完成状态。

依赖链为 P0 → P2 → P3，P1 已合入 main；P3 只展示主壳与本步联调修复。设置写入目标的整理属于 P4，实际
安装、重启和真实任务验收属于 P6，本步不将离线组件验收当作这些流程已经完成。

## P4 设置的保存位置与目标校验

保留八个设置分类和原搜索入口，每个实际区块标明保存位置。搜索结果也显示归属；
MCP 服务与项目规则/Skills/Hooks 分开定位，不把整页都解释为同一份配置。

| 归属 | 内容与实际目标 |
| --- | --- |
| 这台 Mac | 模型服务/Key/分工、界面外观、本机全局指令、浏览器/桌面配置、客户端账号、更新与诊断、连接登记和本机进程管理；模型配置独立，不自动同步；全局指令共享范围见下文 |
| 个人空间 | 当前已连接空间的资料；当前已登记常驻助手的专员与手机关联。没有相应空间时不读另一台默认助手的登记 |
| 当前工作区 | 原工作区授权级别、MCP 管理入口；继续使用既有后端权限与确认流程 |
| 项目 | 当前项目的规则/Skills/Hooks 与 Hook 信任，显示目录；旧项目没有所属空间记录时仍为「归属待核对」 |

`settingsTargetLease` 在设置打开时捕获 P3 的目标和原 client。运行端操作在派发前、异步
结果返回后核对相同的 client、readKey 和连接 epoch，保留原方法接收者和请求参数。
卡片明确展示连接登记，避免只凭同名助手判断目标。它仅是界面的来源校验，不能替代
服务端的权限、原生确认、digest/nonce/轮次/实例和配置 revision 核对。

空间、会话或连接变化后，原运行端表单隐藏并停用；不自动改绑或重试，关闭后重新打开
设置才能核对新目标。本机表单及切分类保留草稿的行为不变。全局指令是原本的用户目录文件：临时引擎与同一
用户目录下的本机常驻助手都在新会话/任务中读取它；其它电脑不自动同步。P4 只标清此
共享范围，不改变 HOME 或搬迁指令文件，也不把模型配置独立误写为所有配置独立。本机模型配置仍可保存，但
来源变化后不自动重启别的引擎，后续由主人在对应工作区重新加载。已经发出的写入若失去
回执，需要读取原目标核对，不表示写入已撤销，也不自动重复批准或保存。

授权级别、项目 Hook 和扩展读取共用 P3 的来源 key，并核对 client/epoch；旧回包和旧按钮
回调不能把新工作区当作原工作区。助理资料编辑也捕获打开时的目标。Codex 观察员开关
仍是本机配置，接收位置沿用原引擎启动时的连接，不随空间选择自动更换。

本步叠在 P3 上，仅展示 P4 差异；不新增路由、不搬数据、不改确认门或污点规则，不调整
无人值守能力。P5 的 CLI 依赖迁移和 P6 的真实环境验收继续单独进行。
