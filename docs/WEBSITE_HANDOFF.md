# 当前任务中的网站连接与人工接管

2026-11-01。建立在网站连接、浏览器驱动和运行端身份分支之上；这是源码实现，未安装或部署。
只对原有已启用浏览器操控的 Desktop 原生 Agent 回合接入自动接管。不自动启用浏览器工具，
不替换 MainAgent、确认门、会话 actor 或任务台账。

## 用户流程

1. 用户交代目标。需要登记网站时，在当前对话看到“这个任务需要连接网站”，显示精确站点、
   账号标签、网页模式和本次会话的浏览器宿主说明；批准仍走原 INTERACT 门。连接属于工作区，
   可持续使用到撤销，不因当前任务结束自动失效；卡片明确说明这一范围。
2. 使用已登记连接导航前，显示“这个任务需要打开网站”。登记连接和批准导航不等于已登录。
3. 专用浏览器首次需要核对登录，或页面检测到登录/敏感表单时，当前工具直接进入一次人工
   接管确认，不依赖模型再调用 browser_login。专用窗口由人完成登录、SSO、扫码或验证码。
   等待期间不读取页面正文、不截图、不点击或输入。账号标签不代表实际站点账号身份。
4. 用户点击“我已完成，核对并继续”。发送成功先显示等待原运行端回执，不提前声称已恢复。
   执行层重新核对浏览器存在、授权有效、原站点、受限地址及敏感表单，再生成页面投影。
   匿名窗口的接管也绑定卡片所示站点；默认 HTTPS 443 与同一 origin 等价。
5. 仍在登录/SSO 页、跳到其他站点、连接撤销或最终投影发现新敏感表单，继续暂停。
   点击“保持暂停”、超时或取消后不自动重问。同一真实用户回合中，连接/导航拒绝按相同
   站点、账号和模式去重，人工接管最多请求一次；模型重试不能刷新额度。新用户消息才能
   再次请求接管核对。窗口仍保留，原关闭/清理路径继续负责资源与租约。
6. WebSocket 重连恢复原 pending Future 对应的确认 ID 和展示数据；其他会话不能代答。
   重启、超时或回合取消不把历史展示数据变成有效批准。回复丢失沿用原确认状态核对机制，
   不自动重发批准。

## 工程合同

- `agents/confirmation_context.py` 只保存可信工具当前 await 链中的展示信息及原生回合标识。
  ContextVar 隔离并发链，展示内容在 finally 恢复；不从模型文本、页面内容或参数读取 UI 指令。
  每次原 run_turn 开始创建回合标识；内层模型继续、工具重试与重新打开窗口都不刷新它。
- `website_browser.py` 在原 gate 外提供公开 origin/账号标签/模式元数据；人工接管与拒绝去重
  留在原 BrowserSession。没有新增浏览器状态数据库、执行循环或绕过确认的客户端 RPC。
- 原 `agent_confirm` 增加可选 `website` 展示字段，旧端继续显示原文本；审批仍只有原 id/ok
  及所属会话校验。pending/replay 保留同一元数据，未改变五分钟确认期限。
- Desktop 严格校验展示版本、动作枚举、精确 origin、标签与模式；未知/无效结构退回普通
  确认卡。原污点警示保留，网站操作不展示提高授权档位的建议，INTERACT 仍逐次审批。
- 已完成导航/点击等先前动作的结果保留，不因接管等待而改写为“尚未执行”。恢复确认不是
  站点账号身份的独立验证，也不是任务业务验收。

## 验证与范围

`tests/unit/test_browser_handoff.py` 用真实 gate、WS 确认 Future、原网站适配器和假浏览器覆盖：
立即接管、其他会话拒绝、同回合去重/新用户消息、SSO、匿名站点变更、撤销、取消/迟到批准、
重连原卡、投影阶段出现敏感表单，以及真实 MainAgent 脚本模型回合。没有真实模型请求。

前端覆盖合法/无效协议、连接/导航/登录文案、污点提示、断连和回执不明。可复现组件夹具：
`desktop/qa/website-handoff.html`，运行现有 Vite 开发服务器后打开该路径；全程合成数据，
不连接 Gateway、网站、凭证或模型。窄窗口只验证组件，夹具覆盖 Desktop 的 720px 最小宽度，
不声称完整应用支持 390px。浏览器截图和检查 JSON 留在
`/private/tmp/vortocode-task-browser-handoff-ui/`，临时文件不保证长期保留。

`tests/e2e/test_browser_handoff_delivery.py` 还把原 MainAgent、接管确认、假网站内容、
真实本机制品写入和最终回复串成一次合成交付；三次脚本模型响应，没有额外 browser_login
模型请求，不调用真实模型。制品实际保存在测试临时目录，结果仍待人工验收。

真实站点、专用 Chromium 窗口与完整已安装应用仍需单独验收。本次没有实现密码保险箱、
安全表单输入、OAuth 新流程、后台无人值守登录、手机原生接管、跨主机凭证同步或受限委托。
插件和设备统一状态、成功任务到 Skill 提案是后续切片，不由本次卡片推断已完成。

## 采用的交互思路

先把访问不足和人工决策放回当前任务，再从可靠的一次性任务沉淀技能。参考 Grok 的
[连接与人工接管](https://docs.x.ai/grok-bot/computer-and-apps)、
[区分审批/连接/敏感输入](https://docs.x.ai/grok-bot/approvals-security-and-privacy) 和
[技能到自动任务](https://docs.x.ai/grok-bot/skills-routines-and-automations)。
这些是 2026-11-01 读取的公开设计说明，不是 Grok 登录后的运行验证。
本项目仍保留本机工作区与账号范围，未采用同账号所有 Bot 共享全部登录态的模式。
