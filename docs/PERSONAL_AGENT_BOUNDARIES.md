# Personal agent：宿主、凭证与云端协作

2026-10-31，源码核对与实施顺序。当前定位继续是个人工作的常驻助理：收集事项、提议执行、
持续跟进、汇总证据，在需要决定时找到主人。沿用原 MainAgent、SessionActors、TaskRunner
和各领域台账；不新建通用编排器、任务库或全局凭证数据库。

本文的目标结构与当前实现分开。子进程凭证继承修复之上，已补本机网站连接与人工登录接管，
均未部署；模型凭证迁移、跨主机发现和受限委托仍是独立工作，不能据此认定完整云端/本机闭环已完成。

用户当前优先需求是浏览器网站登录，而非搬迁模型 API Key。网站连接通过独立本机目录保留
Cookie，密码、扫码与验证码交给真人；手机网页已接源代码，Android/iPhone 原生 App 待适配。
完整流程、过滤局限与设备接入路线见 [网站连接与手机操作](WEBSITE_CONNECTIONS.md)。

## 方向：一个明确的主助手，执行发生在资源所在处

“云端”需要区分账号服务、模型服务与运行助手的宿主。把模型调用放在云端，并不自动使
云端模型拥有本机文件、登录态或执行权。常驻宿主可以是一直开机的个人电脑或自己的云主机；
选定哪个实例拥有主要个人事项，其他设备观察和提交请求。当前没有主助手自动迁移或双活协议。

| 位置 | 应承担的职责 | 凭证与执行边界 |
| --- | --- | --- |
| 常驻主助手 | 个人事项、下一步、跟进、通知、经确认的派活及原来源的状态汇总 | 保管自己使用的 IM/模型凭证；引用执行端的原任务，不复制成第二个执行台账 |
| 本机/项目执行端 | 本机仓库、工具、桌面、独立开发分支、检查与产物 | 保管本机 Git/CLI/模型登录；按原确认门执行；本机凭证不随工作记录同步 |
| 云端账号服务 | 登录、设备身份与归属核验 | 账号登录只证明身份，不直接授予项目写入、桌面控制或审批权；跨主机助手目录尚未接入 |
| 云端/本机模型服务 | 接收该回合明确提供的上下文并推理 | 仅获得请求内容；实际工具调用仍由资源宿主的原工具运行层核验 |
| Desktop / 手机 / bot | 查看状态、交代任务及各自范围内的确认 | 使用对应入口的独立凭证；手机现有只读能力不能被当作管理员或执行权限 |

本机离线时可以继续本机已有工作，并保留自己的原记录。远端进展显示最后核对时间和未知
状态；重连应从原来源对账。没有执行回执的请求不能因网络恢复就换一个身份再次下发。
本机临时聊天也不能自动提升为另一份主要个人事项，再以“最后写入”为规则覆盖常驻记录。
上述跨端归属/对账需要补合同，当前的 IM 单机去重不能替代它。

## 已有基础与确认的缺口

| 项目 | 当前代码证据 | 判断 |
| --- | --- | --- |
| 账号与远程连接 | `desktop/src-tauri/src/account.rs` 的刷新令牌与 `lib.rs` 的 remote token 使用独立 Keychain 服务；访问证明留原生/内存，原生代理注入远端凭证 | 已有分离基础；同账号不等于同权限，不应统一成一把全能 Key |
| 模型凭证存储 | `llm_profile.rs:save_llm_profile_file` 把含 API Key 的配置按 600 写入 `llm-profile.json` | 仍是明文文件，600 不是加密或 Keychain；后续须在原配置事务内迁移 |
| 宿主到工具子进程 | 原 `sandbox/policy.py` 只有固定密钥名单；动态 provider、Codex 上报和自定义 bot 前缀未完整覆盖 | 本轮已修；既有 shell、测试、MCP 继承与外部执行者复用同一规则 |
| 常驻助理到项目 | `assistant_dispatch.py:_headers` 仍使用运行端管理员令牌访问同机项目服务 | 目前是可信同机部署约定；没有按目标/动作/期限约束的完整跨主机委托 |
| 本机与常驻项目配对 | `desktop/src/lib/residentPlace.ts:projectKey` 按目录名匹配；远程匹配还使用 hostname | 名称不是唯一项目身份；重复目录名、多个端口或迁移时仍需显式稳定身份 |
| 账号与网络发现 | 已有运行端实例 ID、归属与短期只读授权；`discovery_scope=current_runtime` | 不等于云端发现目录、穿透网络或自动执行端选择；参见 [账号桥](ACCOUNT_RUNTIME_BRIDGE.md) |

这些是不同层的问题。增加 bot 数量或换模型不能修好凭证生命周期、目标身份与跨端授权。
目前可以沿用执行核心，近期投入应放在这些边界和一个真实项目的完整交付链。

## 本轮实现：限制宿主凭证的隐式继承

原 `sandbox.policy.child_env` 与 `is_stripped_env` 现在共用三个来源：

1. 固定运行端凭证：已有管理员/中转/IM 密钥，以及 Codex 上报、运维报到、语音入口令牌。
2. 精确的 `VORTOCODE_PROVIDER_<NAME>_KEY` 命名空间，包括已无 BASE 的残留 Key。
3. 经可信宿主配置校验后登记的自定义 bot 秘密变量名：Telegram 的 `<prefix>_TOKEN`、
   钉钉的 `<prefix>_CLIENT_SECRET`。整个配置的名称先登记，再开始构造任何适配器。

登记只保存变量名，不读取或复制凭证值，不由项目文件触发。保护持续整个进程：启动失败、
回滚或关闭绑定后，父环境仍可能保有这些值，不能因此重新允许子进程继承。

保留原宿主环境的 `VORTOCODE_ENV_PASSTHROUGH` 精确放行；名称拼错或通配符不生效。
token 预算、模型名称、PATH、代理与普通任务环境不因包含 KEY/TOKEN 字样被整体删除。
原外部 CLI 的显式个人模型设置仍按其原合同提供；本轮不接管其原生登录或扩展工具权限。

这只限制环境变量继承，**不是完整凭证隔离**：原 OS 沙箱仍主要限制写入，未禁止同用户
读取所有宿主文件；600 明文模型配置、CLI 自己的登录文件、显式 MCP env 及凭证的网络
目的地/轮换/吊销仍需各自合同。测试和源码修复不证明真实主机上旧凭证已迁移或轮换。

## 接下来的实施顺序

| 顺序 | 有界改动 | 验收依据 |
| --- | --- | --- |
| 1，已实现 | 子进程凭证继承统一覆盖 | 合成秘密在真实命令中不可见；多 bot 启动/回滚/停止、外部 CLI 配置与 MCP 继承回归 |
| 2，当前优先 | 网站连接与设备操作 | 已接本机连接、独立目录、人工登录和手机网页；补真实网站验收，再按 Android / iOS 分别接设备适配器，不同步 Cookie |
| 独立草稿 #682 | 模型凭证保管迁移 | 不作为网站连接的前置条件；原 `profile_store` 版本/CAS 与保存确认保留，真实迁移另行验收 |
| 3 | 稳定目标身份 | 复用已有 runtime 实例/ExecutionRef，显式登记项目 ID 和执行位置；同名目录不能自动取得另一项目授权，旧请求不能命中新实例 |
| 4 | 收窄跨端委托 | 在原派活/控制入口核对目标、动作、期限、来源、撤销和固定请求身份；远端模型不保管本机管理员主钥，不新增第二条执行循环 |
| 5 | 一个真实闭环 | 选定项目：提出任务→主人确认→指定本机执行→回报当前分支/检查/证据→主人验收；断网、休眠、拒绝及回执丢失单独验证 |

本轮没有读取、改写或搬迁真实 Keychain/配置或网站登录态；网站会话从新的专用目录开始。
第 4 项不在本轮直接扩大权限。完整待审的多 bot 合同仍见 [设计](MULTI_BOT_DESIGN.md)，
当前单机只读托管见 [实施范围](IM_MULTI_HOST.md)，手机权限见 [手机账号入口](MOBILE_ACCOUNT_ACCESS.md)。
