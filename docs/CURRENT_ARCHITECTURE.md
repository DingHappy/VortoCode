## 当前结构与维护入口

产品仍以一个主人的日常对话为中心。主助理接收目标，借助登记的专员、临时团队和隔离开发执行，进展、交付和待确认回到主人。部门是人员、资料边界、笔记与额度的长期登记，本身不另起 Agent。例行工作沿用原调度，派到原任务系统。跨真人助理互通保留为方案，不在本次整理中实现。

| 要解决的问题 | 权威模块或合同 | 修改边界 |
| --- | --- | --- |
| 页面、输入、主人决定的展示 | Desktop、iPhone；`web/`、`im/`、CLI 适配 | 端声明身份与能力，业务判定调用公开服务 |
| 会话身份、队列、传输与事件回放 | `gateway/` 的 SessionActors、SessionStore、事件合同 | 不在传输层另建任务或执行循环 |
| 派活、登记、交付、例行与验收 | `workflow/staff`、原 CollaborationService / TeamService / TaskRunner；[专员设计](STAFF_DESIGN.md) | 复用原任务记录、执行池、登记与额度 |
| 一次执行的身份、状态和能力 | `agents/backends/execution.py`；[执行合同](EXECUTION_CONTRACT.md) | 只读投影，不授予权限、不替代任务与验收 |
| 外部进程和原生会话调用 | `external_workers.py`、`team_engines.py`、`backends/acp.py`、`backends/codex.py` | 各适配器保留自己的进程、协议和原生权限语义 |
| 模型连接、工具能力、业务指令 | `llm/`、ToolRuntime / MCP / 助理插件、Skill | 模型、执行器和工具分别扩展；Skill 不提供额外权限 |
| 确认、污点、资料边界、预算与恢复 | 原安全内核及各领域的批准、预算和恢复合同 | 不因换执行器而扩大授权、清除污点或重置额度 |

任务是要交回什么；执行尝试是这次由谁来做；会话/轮次是执行器自己的上下文；审批是对具体动作的决定。它们可以相互关联，但不能用一个 `done` 字段互相替代。原领域记录继续是权威来源，执行快照只用于观察与关联。

### 已确认的收敛路线

2026-11-12 主人同意先做前 3 步，每步一个 PR；后续步骤单列。这里的层次是职责关系，不要求每层独立部署，也不要求整个 `agents/` 包只有一个依赖方向；现有分层契约继续有效。

```mermaid
flowchart TD
    U["Desktop / iPhone / CLI / IM"] --> G["Gateway：身份、会话、传输"]
    G --> W["业务服务：对话、专员、团队、例行、开发"]
    W --> E["薄执行入口：能力核对、执行关联、操作转交"]
    E --> B["受信执行适配：内置 / CLI / ACP / 原生会话"]
```

薄入口只转交已授权的调用，依赖宿主显式提供的实现和回调，不读写第二套任务库、不创建执行池、不根据模型或远端字段安装/加载程序。适配器声明支持哪些操作不等于已登录、当前可用或已获授权。审批仍回原来源，资料、预算、污点和实例/轮次核对保持原合同。现有安全内核和 backend 合同不得反向导入业务或传输层。

| 步骤 | 范围 | 完成标准 | 当前状态 |
| --- | --- | --- | --- |
| 1 | 架构地图、职责与迁移边界 | 能从本表找到修改落点，当前与目标分开 | 本文档 PR，不改运行行为 |
| 2 | ACP 共同执行报告、原专员任务的报告关联和只读投影 | 原身份、轮次与尝试可核对；旧记录可读；迟到或未知报告不能冒充新执行或成功 | 待实现 |
| 3 | 薄执行入口，先迁 OpenCode 开发专员 | 业务端通过显式绑定调用；目录、权限、模型配置、测试、分支交付与失败语义不变；独立实跑验证 | 待实现 |
| 4 | 迁移 CLI 开发执行 | 独立 PR，保留实验开关和原恢复策略 | 本批不做 |
| 5 | 迁移已有 Codex 会话控制 | 独立 PR，保留原会话与轮次绑定、受理/完成区分 | 本批不做 |
| 6 | 统一前端投影、清理无调用兼容入口 | 原状态继续权威，界面不判断厂商协议，兼容清理有调用证据 | 本批不做 |

第 2 步沿用 ExecutionSnapshot v1，不改变任务状态和验收规则。报告保存在原任务的协作元数据中；宿主绑定当前执行与任务轮次，旧实例、旧尝试、终态后的迟到回调不能覆盖当前观察。读取旧任务或没有报告的任务保留未知，不凭任务结束补造执行证据。只接已有读取路径，不新增无人调用的 API 或新的概览界面。

第 3 步先提供一次性执行的有界入口，不强迫执行器支持续聊、恢复或运行中补充，不用重新执行模拟这些能力。既有 MainAgent、CLI 和 Codex 调用路径保留，新增同类执行器的工作集中到受信绑定、适配器和合同测试。模型选择、岗位授权及运行环境可用性继续分别判断。

各步同步已有职责/合同文档并跑本地门禁；新增 API 才更新路由基线。行为测试覆盖身份、未知状态、取消、回执不明与原权限；结构分层测试只用于检查依赖。真实执行器的版本和实际任务验收另行记录，假进程、合成模型或离线测试不记成真实模型效果。主会话核心切换、跨框架上下文迁移、常设放行、统一触发器和 ADR-008 冻结模块均不在本批范围。

## 定位与主线

VortoOne 是面向个人研发工作的本地优先、可常驻的 AI 工作助手：记住工作背景，协调执行，持续跟进，核对交付依据，在需要用户决定时找到用户。

近期所有能力围绕四个问题收敛：

1. 今天有哪些事：当前事项与未结束的前期工作。
2. 推进到哪里：进展、阻塞、下一步和最近核对时间。
3. 哪些已核实完成：给出与当前工作对应的验收依据。
4. 什么需要我决定：清楚展示正文、依据和操作对象，由用户确认。

多核心是执行能力的演进方向。产品价值用减少遗漏、重复解释、盯进度和追问结果来衡量；支持的核心数量不作为近期目标。

## 工程分层

| 层 | 当前职责与实现 | 边界 |
| --- | --- | --- |
| 用户入口 | Desktop（Tauri / React）、iPhone（SwiftUI）、CLI、IM 桥接；Web 提供 API、审批和制品查看 | 界面展示与输入不自建任务执行状态 |
| 会话与传输 | `gateway/` 会话装配、actor、输入队列、事件回放、连接与审计 | 一个会话的前台回合由现有 actor 管理；断开连接不等于任务停止 |
| 自有 Agent | `agents/agent_loop.py` 模型回合、上下文、历史与媒体 | Gateway 主会话目前仍使用 MainAgent |
| 工具执行 | `agents/tool.py` 与 `tool_runtime.py` 提供声明、能力检查、调度、Hook、审计与污点传播；确认由运行层统一交给内核 | 可独立于 MainAgent 使用；不因此接管外部核心的原生工具 |
| 工作领域 | `workflow/staff` 岗位/专员/部门/例行与批准，`workflow/tasks` 任务与交接，`workflow/workbench` 目标与运行，`workflow/review` 审查交付 | 复用现有台账、执行池和公开 API；不因增加核心另建一套任务系统 |

| 模型服务 | `llm/` 配置与角色路由，连接云端或本机的兼容模型端点 | 换模型属于自有 Agent 的模型选择，不能直接称为换核心 |

外部 CLI 路径在 `agents/external_workers.py`，复用流水线的 `run_turn` 调用方式；ACP 路径由 `team_engines.py` 装配后交给 `backends/acp.py`；已有 Codex 会话使用 `backends/control.py` 和 `codex.py`。进程启动、通信协议和会话控制是不同职责；统一报告和业务入口时保留各自生命周期，当前没有整会话自由切换。

专员 S1～S9 的实施边界以 [STAFF_DESIGN](STAFF_DESIGN.md#实施状态) 为准。L1 记忆出处、L2 保守恢复、L3 整张开通单与 L6 手机普通动作通道已合并；iPhone 新客户端发布与真机审批验收另算。L0 审批统计仍在独立 PR，专员的常设放行、任务内同类放行和去掉 plan/build 尚未实施，见 [审批负担设计](APPROVAL_LOAD_DESIGN.md)。

## 当前业务闭环

交代目标 → 形成目标/任务单或继续已有会话 → 用户确认关键操作 → 执行 → 记录进展与阻塞 → 核对结果和验收 → 汇总今日事项与下一步。

| 状态或记录 | 可以说明什么 | 仍需核对什么 |
| --- | --- | --- |
| 请求已受理 | 核心收到操作请求 | 操作是否实际结束、后续工作结果 |
| 任务 done / Codex 轮次结束 | 一次执行结束 | 产物、检查、验收及未完成事项 |
| 当前提交验证通过 | 验证证据绑定当前提交 | 目标条件、审查与部署等业务验收 |
| 今日已核实完成 | 当前实现只统计个人目标中用户逐项确认且证据完整的当天记录 | 不自动外推为真实部署、设备或商业结果 |
| 状态无法确认 | 数据过期、失联或回执不明 | 从原来源对账；不能直接推断失败，也不能盲目重复发送 |

今日概览已接入目标、助理任务单、Codex 报告/建议与当前会话确认；Codex 观察员经现有 API 提供共同执行快照，概览优先消费并保留旧观察员兼容。尚未覆盖所有来源的所有决策，计数只代表已读取记录。详细规则见 [今日工作](ASSISTANT_WORKDAY.md)。

## 已清楚的边界与尚待收敛之处

产品定位、默认入口、记录归属和人工决策边界已经明确。工程主干可继续沿用，近期重点是补齐以下实际断点：

| 事项 | 当前情况 | 收敛方向 |
| --- | --- | --- |
| 完成与证据 | 目标确认、提交验证、执行结果已区分；跨来源覆盖仍有限 | 补真实验收依据与来源定位，不依据模型总结自动提升为完成 |
| 执行适配 | 共同执行快照 v1 已接入三类来源；CLI 与常驻控制接口仍分别存在 | 逐步让业务读取共同投影，补事件、待决策与真实版本验收，保留各自生命周期 |
| 恢复与对账 | 已有持久状态与部分恢复；发送不明、崩溃后的 sending 等仍需专项核对 | 先把当前 Codex / 助理链路跑稳，再扩核心 |
| 前端组织 | 已拆出领域 hook、操作控制器和今日投影，App 与原生入口文件仍较大 | 围绕实际改动继续拆分与测试，保持原有授权和来源隔离 |
| 验收证据 | 有离线合同测试和合成交互检查 | 补已安装 Desktop、常驻主机和真实核心的端到端证据 |
